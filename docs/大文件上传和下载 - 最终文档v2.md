### **第一部分：方案设计文档 (Solution Design Document)**

#### 1. 概述与目标

本文档为 Flutter 云相册应用设计一套完整的、支持后台持续运行的大文件（建议阈值 > 50MB）上传与下载方案。方案旨在解决应用生命周期限制导致的网络传输中断问题，并提供媲美原生应用的健壮性和用户体验。

**核心目标**:
1.  **后台持续性**: 即使用户关闭应用或设备重启，传输任务也能继续，并在网络恢复时自动续传。
2.  **系统级进度通知**: 在移动设备系统通知栏中实时显示传输进度。
3.  **断点续传**: 所有传输任务原生支持，节省用户流量和时间。
4.  **状态持久化与UI同步**: 前后端状态一致，应用重启后能准确恢复并显示所有任务的当前状态。
5.  **原子性与一致性**: 确保上传的文件要么完全成功，要么不产生任何垃圾数据。
6.  **资源友好**: 方案需高效管理客户端和服务端的内存、CPU及存储资源。

#### 2. 总体技术架构

本方案采用前后端分离但紧密协作的模式：

*   **客户端 (Flutter)**: 使用 **`background_downloader`** 插件，将所有网络传输任务委托给操作系统（Android `WorkManager` / iOS `URLSession`）管理。客户端内部通过一个 `TransferService` 和本地数据库（Drift/SQLite）来编排和追踪这些后台任务。
*   **服务端 (Golang)**: 提供一套全新的、支持分片上传的原子性API，并增强现有下载接口以支持HTTP `Range`请求。服务端负责分片的接收、临时存储、校验、合并和清理。

#### 3. 分片上传方案设计 (Chunked Upload)

##### 3.1. 总体流程

上传一个大文件被定义为一个“作业 (Job)”，遵循 **“初始化 -> 并发分片传输 -> 合并确认”** 的三阶段流程。

  *(示意图：客户端发起`initiate` -> 服务端创建`UploadTask` -> 客户端并行上传`chunks` -> 服务端存储临时分片 -> 客户端发起`complete` -> 服务端合并文件、清理、创建`Media`记录)*

##### 3.2. 服务端 (Golang) 设计

**3.2.1. 数据库模型变更**

*   **文件**: `models/models.go`
*   **新增 `UploadTask` 模型**: 用于追踪进行中的上传作业。
    ```go
    // UploadTask represents an in-progress chunked file upload.
    type UploadTask struct {
        ID        string    `gorm:"primaryKey;type:varchar(36)"` // Unique Upload ID (UUID)
        UserID    uint      `gorm:"index"`
        FileHash  string    `gorm:"index;type:varchar(64)"` // SHA256 hash of the complete file
        TotalSize int64
        ChunkSize int
        NumChunks int
        Status    string    `gorm:"type:varchar(20)"` // INITIATED, COMPLETED, FAILED
        CreatedAt time.Time
        ExpiresAt time.Time `gorm:"index"` // Used by a cleanup job to remove stale tasks
    }
    ```
*   **文件**: `database/database.go`
*   **操作**: 在 `AutoMigrate` 函数中添加 `&models.UploadTask{}`。

**3.2.2. API 接口设计**

*   **`POST /media/upload/initiate` (初始化上传)**
    *   **功能**: 客户端请求开始上传。服务端进行秒传检查。若文件不存在，则创建并持久化一个 `UploadTask`，并准备临时存储空间。
    *   **请求 Body (JSON)**:
        ```json
        {
          "original_filename": "my_large_video.mp4",
          "hash": "sha256_hash_of_the_entire_file",
          "total_size": 524288000,
          "item_type": "VIDEO"
        }
        ```
    *   **响应**:
        *   **秒传成功 (200 OK)**: 返回 `core.ApiResponse{data=MediaResponse}`。
        *   **需要上传 (201 Created)**: 返回 `{ "upload_id": "...", "chunk_size": 5242880, "uploaded_chunks": [...] }`。`uploaded_chunks` 用于断点续传，服务端通过检查临时目录中已存在的分片文件来生成此列表。

*   **`POST /media/upload/chunk` (上传分片)**
    *   **功能**: 接收单个文件分片。
    *   **请求类型**: `multipart/form-data`
    *   **表单字段**:
        *   `upload_id` (string)
        *   `chunk_index` (int)
        *   `chunk` (file)
    *   **核心逻辑**: 校验 `upload_id` 的有效性，并将分片文件保存到指定的临时目录，如 `<UploadDir>/tmp/<upload_id>/<chunk_index>`。

*   **`POST /media/upload/complete` (合并分片)**
    *   **功能**: 通知服务器所有分片已上传。服务器执行**原子性**的合并操作。
    *   **请求 Body (JSON)**:
        ```json
        {
          "upload_id": "...",
          "original_filename": "my_large_video.mp4",
          "hash": "sha256_hash_of_the_entire_file",
          "item_type": "VIDEO"
        }
        ```
    *   **核心逻辑**:
        1.  锁定该 `upload_id` 防止并发操作。
        2.  校验所有分片是否完整。
        3.  创建一个最终文件，按顺序合并所有分片。
        4.  **【关键安全校验】**: 计算合并后文件的哈希，与请求中的 `hash` 严格比对。
        5.  若校验通过，则创建 `Media` 记录，启动后续处理，并返回 `MediaResponse`。
        6.  **无论成功或失败，都必须清理临时分片目录和 `UploadTask` 记录**。

##### 3.3. 客户端 (Flutter) 设计

**3.3.1. 本地持久化模型**

*   **文件**: `lib/data/datasources/local_db/tables/upload_jobs.dart`
*   **`UploadJob` 表**:
    ```dart
    class UploadJobs extends Table {
      TextColumn get jobId => text()(); // Primary Key, client-generated UUID
      TextColumn get uploadId => text().nullable()(); // Server-generated
      TextColumn get filePath => text()();
      TextColumn get fileHash => text()();
      IntColumn get totalSize => integer()();
      IntColumn get chunkSize => integer()();
      IntColumn get totalChunks => integer()();
      TextColumn get status => text().map(const UploadJobStatusConverter())(); // Enum: pending, initiating, uploading, completing, success, failed
      RealColumn get progress => real()(); // 0.0 to 1.0
      DateTimeColumn get createdAt => dateTime()();
    }
    ```

**3.3.2. 核心服务: `TransferService`**
该服务封装所有与 `background_downloader` 和后端API的交互逻辑。

*   **`enqueueUploadJob(File file)`**:
    1.  **创建作业**: 在本地 `UploadJob` 表中插入记录，状态为 `pending`。
    2.  **准备**: 异步流式计算文件哈希，更新DB。
    3.  **初始化**: 调用 `/initiate` API，处理秒传或获取 `upload_id`，更新DB。
    4.  **分片与入队**:
        *   创建所有分片的临时文件。
        *   为每个分片构建一个 `MultipartUploadTask`，**关键**是设置 `group: upload_id`。
        *   批量调用 `FileDownloader().enqueue(tasks)`。
*   **全局监听器 `_onTaskUpdate(dynamic update)`**:
    *   **进度更新 (`TaskProgressUpdate`)**: 根据 `task.group` (`upload_id`) 找到对应的 `UploadJob`，聚合所有分片的进度，计算并更新 `UploadJob` 的整体 `progress`。
    *   **状态更新 (`TaskStatusUpdate`)**: 当一个分片任务完成时，检查该 `group` 下是否所有任务都已完成。
        *   **若是**: 触发 `_completeUpload(uploadId)` 流程：调用 `/complete` API，根据结果更新 `UploadJob` 状态，并清理本地临时分片文件。

#### 4. 大文件下载方案设计 (Resumable Download)

##### 4.1. 服务端 (Golang) 设计

*   **API 接口**: `GET /media/{uuid}/download/original`
*   **核心要求**: 必须正确处理 HTTP `Range` 请求头。
*   **实现**: 在 `handlers/media_handler.go` 中的 `downloadFile` 辅助函数内，使用 `http.ServeFile(c.Writer, c.Request, filePath)`。Go的标准库会为你处理所有关于 `Range` 请求的复杂逻辑。**此项改造简单但至关重要**。

##### 4.2. 客户端 (Flutter) 设计

**4.2.1. 本地持久化模型**

*   **文件**: `lib/data/datasources/local_db/tables/download_jobs.dart`
*   **`DownloadJob` 表**:
    ```dart
    class DownloadJobs extends Table {
      TextColumn get jobId => text()(); // Primary Key
      TextColumn get taskId => text().nullable()(); // background_downloader task ID
      TextColumn get mediaUuid => text()();
      TextColumn get downloadUrl => text()();
      TextColumn get savePath => text()();
      TextColumn get status => text().map(const DownloadJobStatusConverter())(); // Enum
      RealColumn get progress => real()();
      DateTimeColumn get createdAt => dateTime()();
    }
    ```

**4.2.2. 核心服务: `TransferService`**

*   **`enqueueDownloadJob(...)`**:
    1.  **创建作业**: 在本地 `DownloadJob` 表中插入记录。
    2.  **创建任务**: 构建一个 `DownloadTask`，**关键**是设置 `updates: Updates.statusAndProgress` 以启用通知栏进度。
    3.  **入队并关联**: 调用 `await FileDownloader().enqueue(task)`，并将返回的 `task.taskId` 更新到 `DownloadJob` 记录中。
*   **全局监听器 `_onTaskUpdate(dynamic update)`**:
    *   通过 `update.task.taskId` 在 `DownloadJob` 表中找到对应作业，并实时更新其 `progress` 和 `status`。

此计划将整个项目分解为按顺序执行的、可管理的任务包。

*   **[任务 1.2]** **实现分片上传API (Golang)**:
    *   **文件**: `handlers/media_handler.go`
    *   **操作**:

*   **[任务 4.1]** **上传逻辑实现 (最复杂部分)**:

        *   **【关键】** 实现高效、安全的创建临时分片文件的逻辑。
        *   构建和入队 `MultipartUploadTask` 列表。
*   **[任务 4.2]** **上传更新处理**:
    *   在 `_handleUploadUpdate` 方法中，实现：
        *   聚合计算整体进度的逻辑。
        *   检查 `group` 内所有任务是否完成的逻辑。
        *   调用 `/complete` API。
        *   清理本地临时分片文件的逻辑。
*   **[任务 4.3]** **UI 集成**:
