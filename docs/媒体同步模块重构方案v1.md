### **媒体同步模块重构方案**

### 1. 重构目标与核心思想

当前应用的媒体同步架构采用“前台命令式”模型，即在 UI 层（或由其触发）发起一个庞大、阻塞式的同步任务。这种模式在处理大量媒体文件时，已证明会导致应用内存溢出崩溃、UI 线程冻结以及同步任务因应用切后台而被中断等严重问题。

本次重构旨在从根本上解决这些问题，将架构升级为业内领先的**“后台服务化、事件驱动、增量同步”**模型。

**核心思想转变：**

1.  **UI 与同步彻底解耦**: UI 层不再负责触发或管理同步过程。它的唯一职责是作为本地数据库的“只读视图”，通过响应式数据流（Stream）展示数据。本地数据库是唯一的“单一事实来源”（Single Source of Truth）。
2.  **同步任务后台化**: 引入真正的原生后台服务（利用 `workmanager` 等插件），确保同步任务能在独立于 App 生命周期的环境中可靠执行，即使 App 被关闭也能被系统唤醒继续工作。
3.  **从“全量拉取”到“事件驱动”**: 废弃每次都对本地媒体进行全量扫描比对的低效模式。转而采用事件监听机制，实时响应系统相册的变化（新增/删除），实现精准、高效的增量更新。
4.  **健壮的任务队列**: 所有同步操作（上传、下载、删除）都必须先作为一条记录存入持久化的数据库任务队列（`SyncJobs` 表）。后台服务作为一个不知疲倦的“工人”，持续地从队列中取出任务并执行，确保任务的可靠性、可重试性和可管理性。

本次重构不考虑向后兼容性，旨在构建一个长远来看更稳定、更高效、用户体验更佳的系统。

### 3. 分块重构实施计划

我们将分五个阶段进行重构，确保每个阶段都有明确的目标和交付物。

#### **第一阶段：奠定基石 - 强化任务队列**

*   **目标**: 改造 `app_database.dart`，使其 `SyncJobDao` 能够完全支撑一个健壮的生产者-消费者任务模型。
*   **关键文件**: `lib/data/datasources/app_database.dart`
*   **实施步骤**:
    1.  **审视 `SyncJobs` 表**: 确认 `status`, `attempts`, `errorMessage` 等字段满足需求。
    2.  **增强 `SyncJobDao`**:
        *   添加 `getNextPendingJob()`: 获取一个处于 `pending` 状态的任务，并最好能实现原子性地将其状态更新为 `inProgress`，防止多实例竞争。
        *   添加 `updateJobStatus(int jobId, JobStatus status, {String? error})`: 更新任务状态。
        *   添加 `incrementAttemptCount(int jobId)`: 增加重试次数。
        *   添加 `resetStaleJobs()`: 在服务启动时，将所有处于 `inProgress` 状态的任务重置为 `pending`，以处理上次执行意外中断的情况。

#### **第二阶段：构建引擎 - 引入后台服务与任务处理器**

*   **目标**: 创建新的 `services` 目录，并实现后台任务的注册、调度和执行逻辑。
*   **关键文件**:
    *   `lib/main.dart`
    *   (新增) `lib/services/background_service_manager.dart`
    *   (新增) `lib/services/sync_job_processor.dart`
*   **实施步骤**:
    1.  **引入 `workmanager` 插件**: 在 `pubspec.yaml` 中添加依赖。
    2.  **创建 `background_service_manager.dart`**:
        *   定义一个顶层函数 `callbackDispatcher()` 作为 `workmanager` 的入口点。
        *   在该函数内，根据任务标识符，调用 `SyncJobProcessor` 来处理任务。
        *   提供 `initialize()` 方法，在 `main.dart` 中调用，用于注册和调度后台任务（例如，每 15 分钟运行一次）。
    3.  **创建 `sync_job_processor.dart`**:
        *   实现 `processNextJob()` 核心方法。
        *   该方法内部逻辑为：调用 `SyncJobDao.getNextPendingJob()` -> 如果获取到任务 -> 根据 `jobType` 调用 `RemoteMediaDataSource` (上传/下载) 或 `MediaAssetDao` (删除) -> 成功则删除任务，失败则调用 `SyncJobDao.updateJobStatus()` 标记失败并记录错误。
    4.  **修改 `main.dart`**: 在 `main()` 函数中调用 `BackgroundServiceManager.initialize()`。

#### **第三阶段：事件驱动 - 改造本地媒体同步**

*   **目标**: 废弃全量扫描，改为监听系统相册的实时变化，并将变化转化为任务。
*   **关键文件**:
    *   (新增) `lib/services/local_media_observer.dart`
    *   (新增) `lib/services/sync_job_manager.dart`
    *   `lib/data/datasources/local_media_source.dart`
*   **实施步骤**:
    1.  **创建 `sync_job_manager.dart`**:
        *   提供高层 API，如 `createUploadJobForNewAsset(AssetEntity asset)`。
        *   该方法负责：将 `AssetEntity` 转换为 `MediaAssetsCompanion` 并存入本地数据库 -> 获取新生成的 `assetId` -> 在 `SyncJobs` 表中插入一条新的上传任务。
    2.  **创建 `local_media_observer.dart`**:
        *   实现 `startObserving()` 方法。
        *   内部调用 `PhotoManager.addChangeCallback()`。
        *   在回调中，分析 `ChangeDetails`，对每一个新增的 `AssetEntity`，调用 `SyncJobManager.createUploadJobForNewAsset()`。
        *   在 `BackgroundServiceManager` 中或 App 启动时调用 `startObserving()`。
    3.  **重构 `local_media_source.dart`**:
        *   删除 `scanAndIndexLocalMedia()` 方法。
        *   保留或新增处理单个 `AssetEntity` 的辅助方法，供 `SyncJobManager` 使用。
        *   可以保留一个用于首次安装的分页式 `performInitialScan()` 方法，该方法也通过 `SyncJobManager` 创建任务，而不是直接同步。

#### **第四阶段：解耦数据层 - 剥离 Repository 的同步职责**

*   **目标**: 让 Repository 不再执行同步，只负责协调数据访问和创建同步任务。
*   **关键文件**:
    *   `lib/domain/repositories/media_repository.dart`
    *   `lib/data/repositories/media_repository_impl.dart`
*   **实施步骤**:
    1.  **修改 `media_repository.dart` (接口)**:
        *   删除 `syncWithCloud()` 和 `loadAndIndexLocalMedia()` 方法声明。
        *   `downloadAndSaveOriginal` 方法的返回类型可以改为 `Future<void>`，因为它现在只负责创建任务，而不直接返回下载结果。
    2.  **重构 `media_repository_impl.dart`**:
        *   删除 `syncWithCloud()` 和 `loadAndIndexLocalMedia()` 的实现。
        *   重写 `downloadAndSaveOriginal(UnifiedMediaEntity entity)` 方法：其实现不再是直接下载，而是调用 `SyncJobManager.createDownloadJob(entity)` 来创建一条下载任务。数据库状态的更新（如 `downloading`）应在 `SyncJobProcessor` 中处理。

#### **第五阶段：革新 UI 层 - 实现纯粹的响应式展现**

*   **目标**: 移除 UI 层所有与主动同步相关的代码，使其只依赖于本地数据库的数据流，实现即时、流畅的界面。
*   **关键文件**:
    *   `lib/ui/media/viewmodels/media_viewmodel.dart`
    *   `lib/ui/media/pages/media_page.dart`
    *   `lib/providers.dart`
*   **实施步骤**:
    1.  **重构 `media_viewmodel.dart`**:
        *   删除 `syncWithCloud`, `retry`, `_initialize` 中的同步调用。
        *   删除对 `isSyncingWithCloudProvider` 和 `cloudSyncErrorProvider` 的读写。
        *   ViewModel 的核心逻辑简化为：`final mediaStream = _mediaRepository.getUnifiedMediaStream();`，并将这个 Stream 直接暴露给 UI 或转换为 `MediaState`。
    2.  **重构 `media_page.dart`**:
        *   移除 `RefreshIndicator` 或改变其 `onRefresh` 行为（可以设计为向后台服务发送一个“优先检查”的信号，但非必须）。
        *   移除 `ref.listen` 对 `cloudSyncErrorProvider` 的监听和 `SnackBar` 的显示。
    3.  **修改 `providers.dart`**:
        *   删除 `isSyncingWithCloudProvider` 和 `cloudSyncErrorProvider`。
        *   如有需要，添加新 `Service` 层的 Provider，如 `syncJobManagerProvider`。
    4.  **审视 `media_item.dart` 和 `sync_status_icon.dart`**:
        *   确保这些小组件能正确地根据 `UnifiedMediaEntity` 的 `syncStatus` 字段（例如 `uploading`, `downloading`, `error`）来展示正确的 UI 状态。这现在是反馈同步进度的主要方式。
