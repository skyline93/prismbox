### **圈子功能 - 照片删除生命周期与跨空间一致性策略**

| **文档版本** | V1.0 |
| :--- | :--- |
| **主题** | 解决“个人相册删除”操作对“圈子共享”照片的影响 |
| **状态** | **决策建议** |

---

### **1. 问题背景与核心挑战**

“圈子相册”功能旨在建立一个集体记忆空间，而个人相册则是用户的私密保险箱。当一张照片同时存在于这两个空间时，我们在其生命周期的管理上遇到了一个关键的决策点：**如果用户在其个人相册中删除了这张照片，圈子里的这张照片应该何去何从？**

这个问题的背后，是两种核心价值的潜在冲突：

*   **个人数据所有权 (Individual Data Ownership)**: 用户必须拥有对其上传数据的绝对控制权。用户的“删除”意图应该得到尊重和彻底执行。
*   **集体记忆完整性 (Collective Memory Integrity)**: 圈子是一个由多名成员共同构建的故事集。任何单个成员的单方面操作，都不应轻易破坏这个集体资产的完整性和上下文（如附带的评论和互动）。

本篇文档旨在分析各种处理方案，权衡利弊，并提出一个兼顾用户体验、技术可行性和商业模式的最终建议。

---

### **2. 方案对比分析**

我们主要评估以下三种可行的技术与产品方案。

#### **方案一：严格所有权模型 (Strict Ownership Model)**

*   **核心哲学**: “我的照片我做主，删除即全部消失。”
*   **用户体验**:
    *   **删除者**: 在个人相册删除照片时，会收到一个明确的警告弹窗，告知此操作将同时从所有圈子中移除该照片。用户的控制感最强，行为与结果完全一致。
    *   **圈子其他成员**: 体验具有**破坏性**。他们可能会发现圈子中的某张重要照片（连同下面的所有评论）在毫无征兆的情况下突然消失了。
*   **技术实现**:
    1.  客户端发起 `DELETE /media/{uuid}` 请求。
    2.  后端拦截请求，检查该 `media_uuid` 是否在 `group_media` 表中被引用。
    3.  若被引用，返回一个特定错误码（如 `409 Conflict`）和被引用的圈子列表。
    4.  客户端根据该响应，弹出警告框。
    5.  若用户确认，客户端再次发起带 `force=true` 参数的删除请求。
    6.  后端执行级联删除，同时删除 `media` 表和所有相关的 `group_media` 记录。
*   **结论**:
    *   **优点**: 逻辑清晰，技术实现简单直接，数据一致性强。
    *   **缺点**: 严重损害了“集体记忆”的产品核心价值，可能引发圈子成员间的困惑和不满。

#### **方案二：解耦引用模型 (Decoupled Reference Model)**

*   **核心哲学**: “分享如同赠送一份数字副本；删除我自己的原件，不应影响已送出的礼物。”
*   **用户体验**:
    *   **删除者**: 在个人相册中删除照片，照片会如预期般从“我的相册”视图中消失。体验流畅，无干扰。
    *   **圈子其他成员**: **体验最佳**。圈子中的照片和互动**完全不受影响**，集体回忆得以完整保留。
*   **技术实现**:
    1.  在 `media` 表中增加一个 `is_hidden_from_owner` (布尔型) 字段。
    2.  用户的“删除”操作，实际上是调用一个 `POST /media/{uuid}/hide` 接口，将上述字段置为 `true`。
    3.  获取个人相册的接口 (`GET /media`) 必须增加 `WHERE is_hidden_from_owner = false` 的查询条件。
    4.  圈子 Feed 的接口 (`GET /groups/{uuid}/media`) **无需任何改动**。
    5.  需要一个后端的**垃圾回收 (GC) 定时任务**，定期扫描并永久删除那些 `is_hidden_from_owner = true` **且**在 `group_media` 中已无任何引用的照片及其物理文件。
*   **结论**:
    *   **优点**: 完美保护了集体记忆的完整性，最符合“圈子”功能的情感定位。为未来的“回收站”功能奠定了基础。
    *   **缺点**: 技术实现最为复杂，需要修改数据模型并开发后台任务。同时，引出了用户存储空间成本如何计算和释放的问题。

#### **方案三：复制模型 (Duplication Model)**

*   **核心哲学**: “分享即复制，为每个圈子创建独立的照片实体。”
*   **用户体验**:
    *   与方案二类似，删除个人照片不影响圈子。
    *   但用户可能会困惑，为什么上传一张照片，存储空间占用了多份。
*   **技术实现**:
    1.  分享到圈子时，后端不仅创建 `group_media` 引用，还会复制一条新的 `media` 记录，甚至可能复制一份物理文件。
*   **结论**:
    *   **优点**: 逻辑上实现了数据隔离。
    *   **缺点**: **强烈不推荐**。造成巨大的数据冗余和存储浪费，管理极其混乱（一个文件哈希对应多条记录），违反了良好的数据库设计原则。

---

### **3. 推荐方案与疑虑详解：方案二及配套机制**

**我们强烈推荐采用【方案二：解耦引用模型】**，因为它在战略上与产品的核心愿景完全一致。针对其最大的疑虑——“用户存储成本”问题，我们设计了以下配套解决方案。

#### **3.1 疑虑：用户是否需要为其无法直接删除的“圈子共享”空间永久付费？**

这是一个致命的商业模式和用户体验问题。如果用户无法释放这部分空间，将导致用户成本无限增长，最终流失。

#### **3.2 解决方案：引入“圈子共享空间管理”功能**

我们必须赋予用户**主动从圈子中撤回其分享内容**的权利，从而释放相应的存储空间。

*   **功能入口**: 在 App 的“设置” -> “存储空间管理”中，为“圈子共享”部分提供一个“管理”入口。

*   **管理界面设计**:
    1.  **概览页**: 显示用户在所有圈子中分享的照片总数和占用的总空间。
    2.  **聚合视图**: 以列表形式展示每个圈子占用的空间和照片数量，允许用户逐一进入管理。
    3.  **详情管理页**:
        *   进入特定圈子后，以网格形式**只显示当前用户自己上传**的照片。
        *   提供**多选模式**，允许用户批量选中照片。
        *   提供一个明确的**“从圈子移除”**按钮。

*   **操作流程与后端支持**:
    1.  用户选中照片并点击“从圈子移除”。
    2.  App 弹出**二次确认警告框**，强调此操作的后果（其他成员将无法再看到）。
    3.  确认后，客户端批量调用 `DELETE /group-media/{groupMediaId}` 接口。
    4.  后端删除 `group_media` 表中的引用记录。
    5.  被移除的照片如果之前已被其所有者在个人相册中“删除”（即 `is_hidden_from_owner = true`），那么它们现在就变成了无任何引用的孤儿，可以在下一次 GC 任务中被永久清理，从而**真正为用户释放了存储空间**。

*   **商业模式闭环**:
    *   **成本归属清晰**: 照片占用上传者的存储配额。
    *   **控制权交还用户**: 用户可以随时通过管理功能，决定是否继续为某段集体回忆“买单”。
    *   **付费转化自然**: 当存储空间不足时，用户可以在“清理旧照片”和“升级套餐”之间做出选择，这是一个非常合理且强大的付费转化驱动力。

### **4. 其他潜在问题与未来考量 (Unconsidered Edge Cases)**

在确定上述方案后，我们还需要考虑以下与之相关的边缘场景：

*   **问题1：用户注销账户，其分享在圈子里的照片如何处理？**
    *   **场景**: 用户 A 注销了账户。
    *   **建议方案**: 用户 A 的照片**应保留在圈子中**，以维护集体记忆的完整性。在技术上，可以将这些 `media` 记录的 `user_id` 设为 `NULL` 或指向一个虚拟的“已注销用户”ID。在 UI 上，这些照片的上传者可以显示为“已注销用户”。这符合“赠送”的理念。

*   **问题2：用户被从圈子中移除，其分享的照片如何处理？**
    *   **场景**: 圈主将用户 B 从圈子中踢出。
    *   **建议方案**: 默认情况下，用户 B 的照片**应保留**。但在执行移除操作时，可以为圈主提供一个**可选项**：“是否同时移除该成员分享的所有照片？”。同时，系统可以发送一条通知给被移除的用户 B，告知他其照片仍保留在圈内，并引导他通过“共享空间管理”功能去手动移除。

*   **问题3：圈子被解散，其中的照片引用如何处理？**
    *   **场景**: 圈主解散了整个圈子。
    *   **建议方案**: 后端应删除该 `group_id` 对应的所有 `group_media` 记录。这会自动触发 GC 机制，为所有成员释放因此而产生的“孤儿”照片所占用的空间。

*   **问题4：圈子内的不当内容管理**
    *   **场景**: 用户 C 在圈内分享了一张不合适的照片，圈主希望将其删除。
    *   **建议方案**: 圈主/管理员应有权**从圈子中移除任何照片**（即删除 `group_media` 记录），而无需操作原始上传者的 `media` 数据。这实现了圈子内的内容审核，同时尊重了个人数据的所有权。

---

### **5. 最终结论**

经过全面分析，**“方案二：解耦引用模型”** 配合精细化的 **“圈子共享空间管理”** 功能，是实现“圈子相册”功能在产品体验、技术架构和商业模式上三者统一的最佳路径。

该方案不仅解决了核心的删除一致性问题，还为处理各种复杂的边缘场景提供了清晰、健壮的逻辑框架，能够支撑产品未来的长期发展。建议团队采纳此方案作为最终的技术与产品决策。
