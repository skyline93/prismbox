## **Flutter 动态并发后台上传架构方案**

### 1. 方案概述

本文档旨在为 Flutter 应用设计一个健壮、可维护且高效的后台上传系统。该系统基于 `background_downloader` 插件，核心思想是**“中心化配置，分布式入队”**。系统将实现动态并发控制，允许应用根据用户设置或网络条件实时调整并发上传数，同时完美解决了 Flutter Isolate 之间状态隔离的难题。

**核心原则：**

*   **一次性全局配置**: `background_downloader` 在应用启动时于主 Isolate 中进行唯一一次初始化配置。
*   **响应式更新**: 配置（尤其是并发数）能够响应用户设置的变化而动态更新。
*   **随处入队**: 应用的任何部分（包括主 Isolate 的 UI 交互和后台 Isolate 的自动化任务）都可以将上传任务提交到全局队列中，而无需关心配置细节。
*   **职责分离**: 各个模块（配置管理、业务编排、任务创建）职责清晰，高度解耦。

### 2. 模块职责定义

| 模块 | 文件路径 | 核心职责 |
| :--- | :--- | :--- |
| **`SettingsService`** | `lib/services/settings_service.dart` | **配置数据源**: 存储和提供应用的各项设置，包括并发上传数。通过 `Stream` 对外暴露设置的变更。 |
| **`TransferManager`** | `lib/services/transfer/transfer_manager.dart` | **配置与生命周期管理者**: 作为应用与 `background_downloader` 交互的唯一配置入口。负责初始化、动态更新配置、注册全局回调。 |
| **`UploadOrchestrator`** | `lib/services/transfer/upload_orchestrator.dart` | **业务流程编排器**: 决定**何时**以及**哪些**文件需要被上传。负责业务逻辑处理，如从数据库查询待上传资产。 |
| **`UploadService`** | `lib/services/transfer/upload_service.dart` | **任务创建与入队器**: 负责将具体的上传信息（文件路径、元数据等）封装成 `UploadTask` 对象，并提交到全局队列。同时，它也作为全局回调的最终处理者，负责更新数据库状态。 |
| **后台任务处理器** | e.g., `lib/features/background_jobs/impl/auto_backup/domain/auto_backup_isolate_handler.dart` | **后台任务触发器**: 在独立的后台 Isolate 中运行，调用 `UploadOrchestrator` 来启动上传业务流程。 |

### 3. 详细设计与代码实现

#### 3.1 `SettingsService`：提供动态配置源

此服务必须提供一个可以监听设置变化的流。

```dart
// lib/services/settings_service.dart

// 假设的设置模型
class BackupSettings {
  // ... 其他设置
  final int concurrentUploads; // 关键字段：并发上传数

  BackupSettings({this.concurrentUploads = 3 /* 默认值 */, /* ... */});
}

@lazySingleton
class SettingsService {
  // 必须提供一个广播流 (BehaviorSubject from rxdart is a good choice)
  // 以便订阅者能立即获取最新值并监听后续变化
  final BehaviorSubject<BackupSettings> _settingsController = BehaviorSubject.seeded(BackupSettings());
  Stream<BackupSettings> watchBackupSettings() => _settingsController.stream;

  // 方法来更新设置并触发流事件
  Future<void> updateConcurrentUploads(int newLimit) async {
    final currentSettings = _settingsController.value;
    // ... 从数据库或 SharedPreferences 加载并更新设置 ...
    final newSettings = currentSettings.copyWith(concurrentUploads: newLimit);
    _settingsController.add(newSettings);
  }
}
```

#### 3.2 `TransferManager`：中心化配置管理者

这是整个架构的核心。它在主 Isolate 中运行，监听 `SettingsService` 并相应地配置 `background_downloader`。

```dart
// lib/services/transfer/transfer_manager.dart
import 'dart.async';
import 'package:background_downloader/background_downloader.dart';
import 'package:injectable/injectable.dart';
import 'package:logging/logging.dart';
import 'package:mobile/services/settings_service.dart';
import 'package:mobile/services/transfer/upload_service.dart';

@lazySingleton
class TransferManager {
  final _log = Logger('TransferManager');
  final UploadService _uploadService;
  final SettingsService _settingsService;
  StreamSubscription? _settingsSubscription;

  TransferManager(this._uploadService, this._settingsService);

  Future<void> initialize() async {
    _log.info('Initializing TransferManager...');

    // 1. 获取初始设置并进行首次配置
    final initialSettings = await _settingsService.watchBackupSettings().first;
    await _reconfigureDownloader(initialSettings.concurrentUploads);
    _log.info('Initial downloader config with concurrency: ${initialSettings.concurrentUploads}');

    // 2. 监听未来的设置变化，以实现动态更新
    _settingsSubscription?.cancel();
    _settingsSubscription = _settingsService.watchBackupSettings().listen((settings) {
      _log.info('Settings changed. Reconfiguring downloader with new concurrency: ${settings.concurrentUploads}');
      _reconfigureDownloader(settings.concurrentUploads);
    });

    _log.info('TransferManager initialized and listening for settings changes.');
  }

  /// 辅助方法，用于执行配置/重新配置
  Future<void> _reconfigureDownloader(int concurrency) async {
    // 每次调用 configure 都会覆盖之前的配置，因此必须提供所有参数
    await FileDownloader().configure(
      // 注册全局回调，这些回调会在主 Isolate 中被触发
      onStatusChange: _uploadService.handleUploadStatusUpdate,
      onProgress: _uploadService.handleUploadProgressUpdate,
      
      // 使用从 SettingsService 传入的动态并发数
      concurrent: concurrency,
    );
  }

  @disposeMethod
  void dispose() {
    _log.info('Disposing TransferManager...');
    // 取消流监听，防止内存泄漏
    _settingsSubscription?.cancel();
  }
}
```

#### 3.3 `UploadService`：任务创建与入队器

`UploadService` 不再持有任何队列引用。它的职责变得非常纯粹：创建任务并将其扔给全局的 `FileDownloader`。

```dart

  Future<void> enqueueMultipleJobs(List<UploadTaskPayload> taskPayloads) async {
      // ...

    // ... (所有创建 UploadTask 的逻辑保持不变)
    
    final task = UploadTask.fromFile(
      // ... configuration for the task
    );

    // [核心变更]: 直接使用全局的 FileDownloader().enqueue()
    // 无需关心队列或并发数，这些都由 TransferManager 在主 Isolate 中配置好了
    await FileDownloader().enqueue(task);
```

这两个模块的实现基本无需改变。它们作为业务流程的发起者，最终会调用 `UploadService` 来完成任务的提交。

### 4. 数据流与执行流程

1.  **应用启动 (主 Isolate)**
    *   `AppInitService` 初始化 `TransferManager`。
    *   `TransferManager.initialize()` 被调用。
    *   它从 `SettingsService` 获取**初始并发数**（如 3）。
    *   调用 `FileDownloader().configure(concurrent: 3, onStatusChange: ...)`，完成**首次配置**。
    *   `TransferManager` 开始**监听** `SettingsService` 的设置变化。

2.  **后台任务触发 (后台 Isolate)**
    *   `Workmanager` 唤醒应用，在一个新的后台 Isolate 中执行 `AutoBackupIsolateHandler.handle()`。
    *   该 Handler 调用 `UploadOrchestrator`，后者准备好需要上传的文件列表。
    *   `UploadOrchestrator` 调用 `getIt<UploadService>()`，获取一个在此后台 Isolate 中的 `UploadService` **新实例**。
    *   `UploadService` 为每个文件创建一个 `UploadTask`，并调用 `FileDownloader().enqueue(task)`。
    *   任务被提交到 `background_downloader` 的**原生层任务池**中。
    *   后台 Isolate 的任务完成并可以安全销毁。

3.  **任务执行 (原生层)**
    *   `background_downloader` 的原生引擎从任务池中拉取任务。
    *   它检查当前正在运行的任务数是否小于**全局配置的并发数**（当前为 3）。
    *   如果小于，则开始执行新任务；否则，等待。

4.  **用户更改设置 (主 Isolate)**
    *   用户在设置页面将并发数从 3 改为 5。
    *   `SettingsService` 更新设置，并向其 `Stream` 发出一个新的 `BackupSettings` 事件。
    *   `TransferManager` 的 `_settingsSubscription` 监听到该事件。
    *   `TransferManager._reconfigureDownloader(5)` 被调用。
    *   `FileDownloader().configure(concurrent: 5, ...)` **再次被调用**，全局并发数被**动态更新**为 5。
    *   原生引擎现在会允许最多 5 个任务同时运行。

5.  **状态与进度更新 (主 Isolate)**
    *   当一个任务的状态或进度变化时，原生引擎会通过平台通道通知 Flutter。
    *   由于回调是在 `TransferManager` 中注册的，这些事件会在**主 Isolate** 中被接收。
    *   `TransferManager` 调用 `_uploadService.handleUploadStatusUpdate`。重要的是，它调用的是主 Isolate 中的 `UploadService` 实例。
    *   这个实例可以安全地更新 Drift 数据库，并触发 UI 的刷新（如果需要）。

### 5. 结论

该方案通过明确划分各个模块的职责，并充分利用 `background_downloader` 的全局配置特性，构建了一个清晰、健壮且灵活的后台上传系统。它从根本上解决了 Isolate 间状态同步的难题，同时提供了响应式的动态配置能力，是 Flutter 中处理复杂后台任务的理想架构。
