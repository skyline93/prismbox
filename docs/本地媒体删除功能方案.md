### **最终方案：本地媒体删除与回收站功能设计**

本方案旨在为您的相册应用构建一个健壮、高效且用户体验良好的删除与回收站功能。它遵循我们在讨论中确立的核心原则，并全面涵盖了状态管理、平台差异、UI性能优化等关键问题。

#### **一、核心设计原则**

1.  **状态分离 (State Separation)**: 媒体的**同步状态 (`SyncStatus`)** 与 **生命周期状态 (`LifecycleState`)** 将作为两个独立（正交）的字段进行管理，确保业务逻辑清晰，互不干扰。
2.  **单一数据源 (Single Source of Truth)**: 所有媒体信息，无论其生命周期状态如何，都统一存储在 `media_assets` 表中。UI层通过不同的查询条件来获取相应的数据集。
3.  **平台感知逻辑 (Platform-Aware Logic)**: 核心业务逻辑层 (`MediaRepository`) 将封装并处理 iOS 和 Android 在文件操作和媒体库管理上的根本差异。
4.  **性能优先 (Performance First)**: 针对回收站中无系统`AssetEntity`可用的媒体，我们将建立一套独立的、高效的缩略图生成与缓存机制，确保UI滚动流畅。
5.  **领域驱动 (Domain-Driven)**: 所有上层业务逻辑和UI交互都将围绕核心领域实体 `UnifiedMediaEntity` 进行，保持架构的一致性和解耦。

---

#### **二、第一层：数据与领域模型 (Data & Domain Model)**

这是整个方案的基石，确保了数据的完整性和扩展性。

1.  **创建 `LifecycleState` 枚举**
    *   **位置**: `lib/core/enums.dart`
    *   **定义**:
        ```dart
        enum LifecycleState {
          active,   // 正常，对用户可见
          trashed,  // 已移入回收站
          // vaulted,  // 为未来的保险箱功能预留
        }
        ```

2.  **扩展 `MediaAssets` 数据表**
    *   **位置**: `lib/data/datasources/local_db/tables/media_assets.dart`
    *   **新增字段**:
        *   `lifecycleState`: 存储 `LifecycleState`，使用字符串类型，默认为 `active`。
        *   `lifecycleModifiedDate`: 记录生命周期状态变更的时间，用于计算回收站保留期。
        *   `trashPath`: **核心字段**。当 `lifecycleState` 为 `trashed` 时，存储该媒体在应用沙盒内 `.trash` 目录的**绝对文件路径**。

3.  **扩展 `UnifiedMediaEntity` 领域实体**
    *   **位置**: `lib/domain/entities/unified_media_entity.dart`
    *   **新增属性**:
        *   `required LifecycleState lifecycleState`
        *   `String? trashPath`
    *   **更新**: `fromDbModel` 工厂方法需同步映射这些新字段。其他工厂方法中 `lifecycleState` 默认为 `active`。

---

#### **三、第二层：核心服务 (Core Services)**

为解决回收站媒体的UI展示性能问题，我们引入一个专门的服务。

1.  **创建 `ThumbnailService`**
    *   **位置**: `lib/services/thumbnail_service.dart`
    *   **职责**: 提供一个方法 `Future<File> getThumbnail(String resourcePath, MediaType type)`。
    *   **内部机制**:
        1.  **缓存优先**: 根据 `resourcePath` 的哈希值计算出缓存路径，并检查缓存是否存在。若存在，立即返回缓存文件。
        2.  **后台生成**: 若缓存不存在，使用 `compute` 将生成任务抛到后台 Isolate。
            *   **图片**: 使用 `image` 库读取文件、缩放尺寸、编码为JPEG。
            *   **视频**: 使用 `video_thumbnail` 插件生成缩略图。
        3.  **持久化缓存**: 生成的缩略图文件被写入应用的缓存目录，供下次直接使用。
    *   **接口**:
        *   `Future<File> getThumbnail(String resourcePath, MediaType type)`
        *   `Future<void> clearCacheFor(String resourcePath)`

---

#### **四、第三层：业务逻辑 (Business Logic - MediaRepository)**

这是功能实现的核心，封装了所有复杂操作和平台差异。

1.  **接口定义 (`MediaRepository`)**
    *   接口方法统一使用 `UnifiedMediaEntity` 作为参数。
        *   `Future<void> moveAssetsToTrash(List<UnifiedMediaEntity> assets)`
        *   `Future<void> restoreAssetsFromTrash(List<UnifiedMediaEntity> assets)`
        *   `Future<void> permanentlyDeleteAssets(List<UnifiedMediaEntity> assets)`

2.  **实现 (`MediaRepositoryImpl`)**

    *   **`moveAssetsToTrash` 逻辑**:
        *   遍历 `assets`，对每一个 `asset`：
            *   **iOS**:
                1.  通过 `asset.localId` 从系统相册**复制**文件到应用的私有 `.trash` 目录，得到 `newTrashPath`。
                2.  **验证复制成功后**，从系统相册删除原资源。
                3.  更新数据库：`lifecycleState`='trashed', `trashPath`=`newTrashPath`, **`localId`=`null` (重要)**, `lifecycleModifiedDate`=`now()`。
            *   **Android**:
                1.  通过 `photo_manager` API 将资源**移动**到应用的 `.trash` 目录 (需含`.nomedia`文件)，得到 `newTrashPath`。
                2.  更新数据库：`lifecycleState`='trashed', `trashPath`=`newTrashPath`, `lifecycleModifiedDate`=`now()`。

    *   **`restoreAssetsFromTrash` 逻辑**:
        *   遍历 `assets`，对每一个 `asset` (必须是 `trashed` 状态)：
            *   **验证**: `asset.trashPath` 必须存在。
            *   **iOS**:
                1.  从 `asset.trashPath` 读取文件数据。
                2.  使用 `photo_manager` 将其**作为新媒体存回**系统相册，得到一个**全新的 `newLocalId`**。
                3.  更新数据库：`lifecycleState`='active', **`localId`=`newLocalId`**, `trashPath`=`null`。
                4.  调用 `thumbnailService.clearCacheFor(asset.trashPath!)` 清理缩略图缓存。
                5.  删除沙盒中的原文件 (`asset.trashPath`)。
            *   **Android**:
                1.  从 `asset.trashPath` 将文件**移回**公共相册。
                2.  更新数据库：`lifecycleState`='active', `trashPath`=`null`。
                3.  调用 `thumbnailService.clearCacheFor(asset.trashPath!)`。

    *   **`permanentlyDeleteAssets` 逻辑**:
        *   遍历 `assets`，对每一个 `asset`：
            1.  调用 `thumbnailService.clearCacheFor(asset.trashPath!)`。
            2.  从 `asset.trashPath` **物理删除文件**。
            3.  从 `media_assets` 表中**彻底删除**该条数据库记录。

---

#### **五、第四层：UI与ViewModel**

将底层能力暴露给用户。

1.  **主相册 (`MediaPage` & `MediaViewModel`)**:
    *   `ViewModel` 查询 `lifecycleState = 'active'` 的媒体资源。
    *   删除操作调用 `mediaRepository.moveAssetsToTrash(...)`，并显示带“撤销”选项的 `SnackBar`。

2.  **回收站 (`TrashPage` & `TrashViewModel`)**:
    *   `ViewModel` 查询 `lifecycleState = 'trashed'` 的媒体资源。
    *   UI 使用 `GridView` 布局，其 `itemBuilder` 中为每个 `UnifiedMediaEntity` 构建一个 `TrashItemWidget`。
    *   `TrashItemWidget` 内部使用 `FutureBuilder`，调用 `thumbnailService.getThumbnail(...)` 来异步加载缩略图，并提供占位符和错误状态。
    *   提供“恢复”和“永久删除”按钮，调用 `ViewModel` 相应方法。

---

#### **六、第五层：后台服务 (Background Service)**

确保回收站不会无限膨胀。

1.  **创建 `TrashCleanupWorker`**:
    *   使用 `workmanager` 注册一个每日运行的后台任务。
    *   任务逻辑：
        1.  查询数据库中所有 `lifecycleState = 'trashed'` 且 `lifecycleModifiedDate` 早于30天前的 `MediaAsset`。
        2.  将查询结果转换为 `List<UnifiedMediaEntity>`。
        3.  调用 `mediaRepository.permanentlyDeleteAssets(...)` 执行清理。

这个完整的方案形成了一个从数据存储、业务逻辑到UI展示的闭环，不仅实现了功能，还充分考虑了平台特性、性能优化和长期可维护性，为您项目的后续开发奠定了坚实的基础。
