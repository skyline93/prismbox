### **方案：圈子相册 (Group Album) 功能实施蓝图**

**核心原则回顾：**
*   **后端先行，接口驱动**：后端完成所有相关 API 的开发、测试和文档化后，前端才开始大规模开发。
*   **架构解耦**：新增的“圈子”功能在数据模型和业务逻辑上与现有的“个人相册”功能保持独立，仅通过媒体 UUID 引用，确保系统清晰、可维护。
*   **分阶段交付**：将庞大的功能集拆分为可管理的、有明确业务价值的阶段，逐步上线，快速验证，降低风险。

---

### **第一阶段：后端开发与接口定稿 (Backend-First Development)**

**目标**: 完成所有“圈子相册”功能的后端逻辑、数据库设计、API 接口开发与测试，并输出一份最终的、可供移动端团队使用的 OpenAPI (Swagger) 文档和 Postman Collection。

#### **Sprint B1: 数据库与核心模型搭建 (预计：3-4天)**

*   **任务 1: 数据库 Schema 设计与迁移**
    *   创建 `groups` 表，包含 `id`, `uuid`, `name`, `description`, `cover_media_uuid`, `owner_id`, `created_at`, `updated_at` 字段。
    *   创建 `group_members` 表，作为多对多关系枢纽，包含 `id`, `group_id`, `user_id`, `role`, `joined_at`。`role` 字段使用 ENUM('owner', 'admin', 'member')。
    *   创建 `group_media` 表，作为媒体引用核心，包含 `id`, `group_id`, `media_uuid`, `uploader_id`, `caption`, `created_at`。
    *   创建 `group_invites` 表，用于管理邀请码，包含 `id`, `group_id`, `created_by_id`, `code`, `expires_at`, `usage_limit`。
    *   创建 `comments` 表，包含 `id`, `group_media_id`, `user_id`, `content`, `created_at`。
    *   **产出**: 可执行的数据库迁移脚本。

*   **任务 2: ORM 模型定义**
    *   在代码中创建与上述数据表对应的 GORM (或你使用的其他 ORM) 模型，并定义好模型之间的关联关系（`belongsTo`, `hasMany`, `many2many`）。
    *   **产出**: 后端代码中的数据模型文件。

#### **Sprint B2: 圈子与成员管理 API (预计：4-5天)**

*   **任务 1: 圈子 (Group) CRUD 接口**
    *   `POST /groups`: 创建圈子。业务逻辑：创建 `groups` 记录，同时在 `group_members` 中为创建者插入一条 `role: 'owner'` 的记录。
    *   `GET /groups`: 获取用户加入的圈子列表。业务逻辑：通过 `group_members` 表查询 `user_id` 关联的所有 `group_id`，再联查 `groups` 表。
    *   `GET /groups/{uuid}`: 获取圈子详情。需要返回圈子基本信息以及聚合信息（如成员数）。
    *   `PUT /groups/{uuid}`: 更新圈子信息。**权限控制**: 必须校验操作者是否为该圈子的 `owner` 或 `admin`。
    *   **产出**: 4个功能完整并通过单元测试的 API 端点。

*   **任务 2: 成员 (Member) 基础接口**
    *   `GET /groups/{uuid}/members`: 获取圈子成员列表。返回用户信息时，**务必过滤掉敏感字段**（如 email, password hash）。返回数据应包含 `user_id`, `username`, `avatar_url`, `role`。
    *   **产出**: 1个功能完整并通过单元测试的 API 端点。

#### **Sprint B3: 邀请与加入机制 API (预计：3-4天)**

*   **任务 1: 邀请码生成与校验**
    *   `POST /groups/{uuid}/members/invite`: 创建邀请码。**权限控制**: `owner` 或 `admin`。业务逻辑：生成唯一的随机字符串作为 `code`，存入 `group_invites` 表并设置过期时间。
    *   `POST /groups/join`: 使用邀请码加入圈子。业务逻辑：
        1.  校验 `code` 是否存在、是否过期、是否达到使用上限。
        2.  校验用户是否已是该圈子成员。
        3.  在 `group_members` 表中插入新记录，`role: 'member'`。
    *   **产出**: 2个功能完整并通过单元测试的 API 端点。

#### **Sprint B4: 核心媒体共享与 Feed 流 API (预计：5-6天)**

*   **任务 1: 分享媒体到圈子**
    *   `POST /groups/{uuid}/media`: 将个人媒体分享到圈子。这是**核心安全接口**，业务逻辑必须严谨：
        1.  权限校验：操作者必须是 `group_members` 的一员。
        2.  **所有权校验**: 对请求体中 `media_uuids` 数组的每一个 `uuid`，都必须在 `media` 表中校验其 `user_id` 是否与当前操作者 ID 匹配。**严防用户分享不属于自己的照片**。
        3.  数据插入：校验通过后，在 `group_media` 表中批量创建引用记录。
    *   **产出**: 1个高度安全、功能完整的 API 端点。

*   **任务 2: 圈子 Feed 流接口**
    *   `GET /groups/{uuid}/media`: 分页获取圈子 Feed。
    *   **性能考量**: 该接口会被高频调用。后端需要使用 `JOIN` 查询，一次性将 `group_media` 表、`media` 表、`users` 表（上传者信息）的数据关联查出，避免 N+1 查询问题。
    *   **响应体设计**: 设计一个 `GroupMediaResponse` 结构体，清晰地聚合所需信息：
        ```json
        {
          "id": 1, // group_media_id
          "caption": "美丽的海滩",
          "shared_at": "2023-10-28T10:00:00Z",
          "uploader": {
            "user_id": 5,
            "username": "Alice",
            "avatar_url": "..."
          },
          "media_details": { ... } // 完整的 Media 对象
        }
        ```
    *   **产出**: 1个高性能、分页功能完善的 API 端点。

#### **Sprint B5: 互动与管理 API (预计：4-5天)**

*   **任务 1: 评论 (Comment) CRUD 接口**
    *   `POST /group-media/{groupMediaId}/comments`
    *   `GET /group-media/{groupMediaId}/comments`
    *   `DELETE /comments/{commentId}`: **权限控制**: 仅评论发布者或圈子 `owner/admin` 可删除。
    *   **产出**: 3个功能完整的 API 端点。

*   **任务 2: 移除与退出机制**
    *   `DELETE /groups/{uuid}/members/{userId}`: 移除成员 (圈主/管理员操作)。
    *   `POST /groups/{uuid}/leave`: 成员主动退出圈子 (本质上是删除自己的 `group_members` 记录)。
    *   `DELETE /group-media/{groupMediaId}`: 从圈子移除照片 (上传者或圈主/管理员操作)。
    *   **产出**: 3个功能完整的 API 端点。

*   **任务 3: API 文档与测试**
    *   **最终交付物**:
        1.  更新 Swagger/OpenAPI 文档，包含所有新增的接口、模型和详尽的注释。
        2.  提供一个 Postman Collection，其中包含所有新接口的示例请求，方便移动端团队调试。
        3.  完成所有新接口的集成测试，确保业务流程闭环。

### **第二阶段：移动端 (Flutter) 开发实施蓝图 (基于现有项目结构)**

**前提**: 后端已完成第一阶段所有任务，API 稳定且 OpenAPI/Swagger 文档已最终确定。

---

#### **Sprint M1: 基础建设 & 数据层对接 (预计：1周)**

**目标**: 在不动任何 UI 页面的情况下，将“圈子”功能所需的数据通路、状态管理和依赖注入全部搭建完毕。这是后续所有 UI 开发的基石。

*   **1.1 在 `lib/models/` 中创建数据模型**
    *   根据最终的 OpenAPI 文档，创建以下 Dart 模型文件：
        *   `group.dart`
        *   `group_member.dart`
        *   `group_media.dart` (用于表示 Feed 流中的聚合响应)
        *   `group_invite.dart`
        *   `comment.dart`
    *   **要求**: 每个模型都必须包含 `fromJson` 命名构造函数，以及推荐实现的 `copyWith` 方法和 `toString` 方法，以方便调试和状态更新。

*   **1.2 在 `lib/api/services/` 中创建 API 服务**
    *   新建 `group_api_service.dart` 文件。
    *   此类将依赖于 `dio_client`。
    *   根据 OpenAPI 文档，实现所有与“圈子”相关的接口方法，例如：
        *   `Future<List<Group>> getMyGroups();`
        *   `Future<Group> createGroup(String name, String description);`
        *   `Future<Group> joinGroup(String inviteCode);`
        *   `Future<List<GroupMedia>> getGroupFeed(String groupUuid, int page, int limit);`
        *   `Future<void> shareMediaToGroup(String groupUuid, List<String> mediaUuids, String caption);`
        *   ...以及其他所有新接口。
    *   **注意**: 这一层只负责原始的 HTTP 请求和 JSON 解析，不包含任何业务逻辑。

*   **1.3 在 `lib/repositories/` 中创建数据仓库**
    *   新建 `group_repository.dart` 文件。
    *   此类将依赖于 `GroupApiService`。
    *   **职责**:
        *   作为业务逻辑与原始 API 请求之间的桥梁。
        *   处理数据转换（如果需要）。
        *   统一处理错误，将 DioError 转换为自定义的业务异常。
    *   方法名将与业务意图对应，如 `Future<List<Group>> fetchMyGroups();`。

*   **1.4 在 `lib/providers/` 中定义状态管理**
    *   新建 `group_providers.dart` 文件。
    *   使用 Riverpod 定义所有需要的 Provider：
        *   `final groupRepositoryProvider = Provider<GroupRepository>(...)`
        *   `final groupListProvider = FutureProvider<List<Group>>((ref) => ...)`: 用于获取圈子列表。
        *   `final groupFeedProvider = StateNotifierProvider.family<GroupFeedNotifier, AsyncValue<List<GroupMedia>>, String>((ref, groupUuid) => ...)`: 用于处理圈子 Feed 的分页加载和状态。
        *   `final groupMembersProvider = FutureProvider.family<List<GroupMember>, String>((ref, groupUuid) => ...)`: 用于获取成员列表。

*   **1.5 在 `lib/app_container.dart` 中注册依赖**
    *   将新创建的 `GroupApiService` 和 `GroupRepository` 在依赖注入容器中进行注册，确保它们在整个 App 中可用。

#### **Sprint M2: 核心 UI & 导航 (预计：2周)**

**目标**: 搭建用户可见的核心页面框架，实现圈子的创建、加入和浏览功能。

*   **2.1 在 `lib/router/` 中配置新路由**
    *   打开 `app_router.dart` (或你的 GoRouter 配置文件)。
    *   添加新的路由规则：
        *   `/groups`: 指向 `GroupListPage`。
        *   `/groups/create`: 指向 `CreateGroupPage`。
        *   `/groups/:uuid`: 指向 `GroupFeedPage`，通过 `uuid` 参数传递圈子 ID。
        *   `/groups/:uuid/members`: 指向 `GroupMembersPage`。

*   **2.2 在 `lib/pages/` 中创建新页面**
    *   新建目录 `lib/pages/group/`。
    *   在该目录下创建以下页面文件：
        *   `group_list_page.dart`:
            *   UI: 使用 `Scaffold`，`AppBar`，和一个 `ListView.builder`。
            *   逻辑: `ref.watch(groupListProvider)` 来构建 UI，并处理 `when(data: ..., loading: ..., error: ...)` 状态。
            *   交互: 提供“创建圈子”和“加入圈子”的入口按钮。
        *   `create_group_page.dart`: 包含表单和提交按钮。
        *   `group_feed_page.dart`:
            *   UI: `GridView.builder` + `FloatingActionButton` (用于上传)。
            *   逻辑: `ref.watch(groupFeedProvider(groupUuid))` 获取数据。实现滚动监听，在列表底部调用 `ref.read(groupFeedProvider(groupUuid).notifier).fetchNextPage()` 来实现无限滚动。
            *   交互: 点击网格项，导航到大图浏览页。

*   **2.3 在 `lib/widgets/` 中创建可复用组件**
    *   新建目录 `lib/widgets/group/`。
    *   创建 `group_list_item.dart`: 用于在 `GroupListPage` 中显示单个圈子的卡片。
    *   创建 `group_media_grid_item.dart`: 用于在 `GroupFeedPage` 中显示单个照片的缩略图。

#### **Sprint M3: 核心交互 - 上传与评论 (预计：2周)**

**目标**: 实现最核心的分享循环和社交互动，让圈子“活”起来。

*   **3.1 在 `GroupFeedPage` 中实现上传流程**
    *   **触发**: 用户点击 `FloatingActionButton`。
    *   **步骤**:
        1.  调用 `image_picker` 让用户选择设备上的照片。
        2.  **复用现有逻辑**: 调用**已有的** `MediaRepository` 来执行哈希预检和文件上传 (`/media/upload`)。这是关键，避免重复造轮子。
        3.  **获取结果**: 上传成功后，从 `MediaRepository` 的方法返回结果中获得 `media_uuid` 列表。
        4.  **调用新逻辑**: 调用 `ref.read(groupRepositoryProvider).shareMediaToGroup(groupUuid, mediaUuids, caption)`。
        5.  **状态更新**: 调用 `ref.refresh(groupFeedProvider(groupUuid))` 来刷新 Feed，或实现更优雅的乐观更新。

*   **3.2 实现评论功能**
    *   **位置**: 在现有的大图浏览页面下方添加评论区。
    *   **在 `lib/widgets/group/` 中创建组件**:
        *   `comment_list.dart`: 用于显示评论列表。
        *   `comment_input_field.dart`: 用于输入和提交评论。
    *   **在 `lib/providers/` 中添加 Provider**:
        *   `final commentsProvider = FutureProvider.family<List<Comment>, int>((ref, groupMediaId) => ...)`: 获取指定照片的评论列表。
    *   **逻辑**: 在大图页 `ref.watch(commentsProvider(groupMediaId))` 来展示评论。提交新评论后，调用 `ref.read(groupRepositoryProvider).addComment(...)`，然后 `ref.refresh` 对应的 `commentsProvider`。

#### **Sprint M4: 管理功能 & 体验优化 (预计：1-2周)**

**目标**: 补全所有管理功能，并对整体体验进行打磨，准备上线。

*   **4.1 在 `lib/pages/group/` 中创建管理页面**
    *   `group_members_page.dart`:
        *   逻辑: `ref.watch(groupMembersProvider(groupUuid))` 来获取和展示成员列表。
        *   UI: 根据 `role` 字段，动态显示操作按钮（如“移除”、“设为管理员”）。
    *   `group_settings_page.dart`: 提供编辑圈子信息、生成邀请码、退出或解散圈子的入口。

*   **4.2 实现权限相关的业务逻辑**
    *   在所有需要权限的操作按钮上，都需要从 `groupMembersProvider` 或类似的状态中获取当前用户的角色，来决定按钮是否可见或可用。

*   **4.3 集成通知**
    *   若后端支持推送，配置 `firebase_messaging`。
    *   在 `main.dart` 或专门的通知服务类中处理后台和前台消息。
    *   当用户点击通知时，使用 `GoRouter` 深度链接到对应的圈子 Feed 页或照片详情页。

*   **4.4 全面测试与优化**
    *   **UI/UX**: 检查所有的加载状态、空状态、错误状态是否都有友好的 UI 反馈。
    *   **性能**: 使用 Flutter DevTools 分析 `GroupFeedPage` 的滚动性能，确保流畅。
    *   **健壮性**: 对所有用户输入和网络请求进行完整的错误处理。
