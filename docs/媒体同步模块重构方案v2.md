### **媒体同步模块架构重构方案**

### 1. 重构背景与核心思想

**1.1. 问题根源**
当前应用的媒体同步架构采用“前台命令式”模型，由 UI 层发起并管理庞大的同步任务。此模式已证实是导致应用内存溢出崩溃、UI 线程冻结、电池消耗过快以及同步任务因应用切换状态而中断的根本原因。

**1.2. 核心思想转变**
本次重构旨在废弃现有模式，采用业内领先的**“后台服务化、事件驱动、增量同步”**模型。这一转变的核心思想是：

1.  **UI 与同步彻底解耦**: UI 层不再负责触发或管理同步，仅作为本地数据库的**只读响应式视图**。本地数据库是唯一的“单一事实来源”(Single Source of Truth)。
2.  **同步任务后台化**: 引入原生后台服务，确保同步任务能在独立于 App 生命周期的环境中可靠执行，实现“离线”和“应用关闭”后的持续同步。
3.  **事件驱动代替全量扫描**:
    *   **本地同步**: 实时监听系统相册的增删事件，实现精准、零延迟的增量更新。
    *   **云端同步**: 结合静默推送和后台定时轮询，高效发现云端变更。
4.  **健壮的持久化任务队列**: 所有同步操作（上传、下载、删除、变更处理）都必须先作为任务存入数据库队列。后台服务作为不知疲倦的“工人”，持续地从队列中消费任务，确保任务的可靠性、可重试性和智能调度（如网络判断）。

**1.3. 关键概念定义**
*   **本地同步**: 指 **App 本地数据库** 与 **手机系统相册** 之间的数据同步。其职责是发现本地媒体变化。
*   **云端同步**: 指 **App 本地数据库** 与 **云端服务器** 之间的数据同步。其职责是执行数据传输和状态同步。

---

### 2. 重构策略：本地与云端同步的依赖关系

**结论：本地同步与云端同步在功能上可以分离，但在架构组件上高度耦合，其重构工作必须作为一个完整的项目协同处理。**

**阐述**:
用户可以选择只使用本地相册功能而不开启云端备份。在这种情况下，**本地同步**可以独立运作，负责发现并记录本地媒体。然而，只要应用提供了**备份/同步**这一核心特性，就必须有一个健壮的**云端同步**机制来执行上传、下载等实际操作。

*   **本地同步**是任务的**生产者**之一：它发现一张新照片，并根据用户设置（如“自动备份”）来决定是否创建一个“上传任务”。
*   **云端同步**是任务的**消费者**：它负责执行队列中所有类型的任务，包括由本地同步产生的上传任务，以及由云端变更产生的下载任务。

因此，这两个模块共享同一个核心枢纽——**`SyncJobs` 任务队列**。若只重构其一，将导致“备份与同步”功能链条断裂，无法上线。故本次重构必须作为一个不可分割的整体来规划与实施，分阶段构建，但需完整交付。

### 4. 分模块重构实施计划

#### **第一阶段：构建核心枢纽 - 任务队列与后台服务**

*   **目标**: 搭建一个功能完备的、持久化的任务队列，并创建一个能在后台独立运行的服务来消费队列中的任务。这是整个新架构的基石。
*   **涉及文件**:
    *   `lib/data/datasources/app_database.dart` `[*]`
    *   `lib/main.dart` `[*]`
    *   `lib/services/background_service_manager.dart` `[+]`
    *   `lib/services/sync_job_processor.dart` `[+]`
*   **实施步骤**:
    1.  **增强数据库 (`app_database.dart`)**:
        *   在 `JobType` 枚举中，扩充任务类型: `UPLOAD`, `DELETE_CLOUD`, `DOWNLOAD_ORIGINAL`, `DOWNLOAD_THUMBNAIL`, `SYNC_CLOUD_CHANGES`, `PROCESS_CLOUD_CREATE`, `PROCESS_CLOUD_DELETE`。
        *   为 `SyncJobs` 表增加 `networkConstraint` (如 `wifiOnly`) 和 `priority` 字段，以支持智能调度。
        *   增强 `SyncJobDao`，提供健壮的任务管理接口: `getNextPendingJob()`, `updateJobStatus()`, `resetStaleJobs()` 等。
    2.  **创建任务处理器 (`sync_job_processor.dart`)**:
        *   实现 `processNextJob()` 方法，作为任务消费的唯一入口。这是后台服务的“大脑”。
        *   该方法内部是一个 `switch (job.jobType)` 逻辑，根据任务类型调用 `RemoteMediaDataSource` (上传/下载)、`MediaAssetDao` (更新数据库)等来执行实际工作。
        *   内置网络、电量等执行条件的检查逻辑。
    3.  **创建后台服务管理器 (`background_service_manager.dart`)**:
        *   引入 `workmanager` 插件。
        *   定义顶层 `callbackDispatcher()` 作为后台任务入口，其内部调用 `SyncJobProcessor.processNextJob()`。
        *   提供 `initialize()` 方法，用于注册和调度周期性任务（例如，每 15 分钟触发一次“检查云端变更”）。
    4.  **初始化 (`main.dart`)**: 在 `main()` 函数中调用 `BackgroundServiceManager.initialize()`，确保后台服务被系统注册。

#### **第二阶段：接入数据源 - 实现任务的自动创建**

*   **目标**: 实现本地和云端变更的自动发现，并将这些变更转化为原子化的任务，填充到任务队列中。
*   **涉及文件**:
    *   `lib/services/local_media_observer.dart` `[+]`
    *   `lib/services/sync_job_manager.dart` `[+]`
    *   `lib/data/datasources/local_media_source.dart` `[*]`
*   **实施步骤**:
    1.  **创建任务生产者 API (`sync_job_manager.dart`)**:
        *   这是一个门面 (Facade) 类，为上层逻辑（如监听器、UI 操作）提供清晰、业务驱动的接口，如 `createUploadJobForNewAsset(AssetEntity asset)`、`createCloudChangesSyncJob()`、`createDownloadJob(UnifiedMediaEntity entity)`。
        *   它负责封装所有创建任务的复杂逻辑（如写入 `MediaAssets` 表、构建 `SyncJobsCompanion`、存入数据库）。
    2.  **实现本地变更监听 (`local_media_observer.dart`)**:
        *   实现 `startObserving()` 方法，内部调用 `PhotoManager.addChangeCallback()`。
        *   在回调中，对每个新增/删除的媒体，调用 `SyncJobManager` 相应的方法创建任务（是否创建上传任务，取决于用户设置）。
        *   在 App 启动逻辑中（例如 `main.dart` 或一个启动 `Provider`）调用 `startObserving()`。
    3.  **实现云端变更发现**:
        *   在 `BackgroundServiceManager` 的周期性任务中，调用 `SyncJobManager.createCloudChangesSyncJob()`。
        *   （进阶）集成 FCM 静默推送，在收到推送时也调用上述方法，实现实时同步。
    4.  **改造 `local_media_source.dart`**:
        *   彻底删除 `scanAndIndexLocalMedia()` 方法。
        *   保留或重构为处理单个 `AssetEntity` 的辅助方法，供 `SyncJobManager` 调用。
        *   可提供一个**一次性**的、**分页式**的 `performInitialScan()` 方法，用于 App 首次安装时填充数据。

#### **第三阶段：解耦上层建筑 - 改造 Repository 和 UI**

*   **目标**: 移除所有旧的、主动式的同步逻辑，使 Repository 和 UI 完全适应新的后台、事件驱动模型，实现 čistá architektura (Clean Architecture)。
*   **涉及文件**:
    *   `lib/domain/repositories/media_repository.dart` `[*]`
    *   `lib/data/repositories/media_repository_impl.dart` `[*]`
    *   `lib/ui/media/viewmodels/media_viewmodel.dart` `[*]`
    *   `lib/ui/media/pages/media_page.dart` `[*]`
    *   `lib/providers.dart` `[*]`
*   **实施步骤**:
    1.  **重构 Repository (`media_repository.dart` & `media_repository_impl.dart`)**:
        *   彻底删除 `syncWithCloud` 和 `loadAndIndexLocalMedia` 方法。
        *   `getUnifiedMediaStream()` 保持不变，它现在是 UI 获取数据的唯一主要途径。
        *   改造 `downloadAndSaveOriginal` 等方法，使其内部实现变为调用 `SyncJobManager` 创建一个下载任务，然后立即返回，不等待结果。
    2.  **重构 ViewModel (`media_viewmodel.dart`)**:
        *   删除所有与同步状态管理相关的 `StateProvider` (`isSyncingWithCloudProvider` 等) 和方法 (`syncWithCloud`, `retry`)。
        *   ViewModel 的核心逻辑简化为：通过 `ref.watch` 订阅 Repository 提供的 `getUnifiedMediaStream()`，并将数据流直接转换为 UI 状态 (`MediaState`)。
    3.  **重构 UI (`media_page.dart`)**:
        *   移除 `RefreshIndicator` 或将其 `onRefresh` 行为改为调用 `SyncJobManager.createCloudChangesSyncJob(priority: high)`。这仅为用户提供一个“请求优先检查”的选项，UI 本身不等待、不阻塞。
        *   移除所有监听全局同步错误的 `SnackBar` 逻辑。错误现在是单个媒体项的状态，应在 `media_item.dart` 中通过 `syncStatus` 字段来可视化（例如显示一个错误图标）。
    4.  **清理 (`providers.dart`)**: 删除所有已废弃的同步状态 `Provider`，并按需添加新 `Service` 层的 Provider。
