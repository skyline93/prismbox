### **核心目标：构建一个可恢复、高效且对系统友好的后台同步引擎**

我们将围绕三个核心理念来重构：

1.  **任务持久化**：所有待办事项（上传、删除）都应作为“作业”（Job）存入数据库。应用崩溃或重启，任务不丢失。
2.  **原生后台执行**：使用操作系统提供的原生后台任务能力（Android的WorkManager, iOS的BGTaskScheduler）来执行这些作业，保证应用即使不在前台也能进行同步。
3.  **职责分离**：让每个模块只做一件事。`LocalMediaObserver`只负责发现变更，`SyncJobManager`只负责创建作业，而一个全新的**后台执行器**则专门负责处理作业。

---

### **第一阶段：强化“作业队列” - 改造数据库和DAO**

这是整个系统的基石。我们需要让 `sync_jobs` 表能够完整地描述一个任务的生命周期。

1.  **增强 `sync_jobs` 表 (`lib/data/datasources/local_db/tables/sync_jobs.dart`)**
    *   当前可能只有一些基础字段，我们需要扩展它，增加以下字段：
        *   `status`: 作业状态 (TEXT)。例如：`pending`（等待处理）、`running`（正在处理）、`completed`（成功）、`failed`（失败）。这是最重要的字段。
        *   `job_type`: 作业类型 (TEXT)。例如：`upload`、`delete`。
        *   `attempts`: 已尝试次数 (INTEGER)。用于实现重试逻辑。
        *   `error_message`: 最后的错误信息 (TEXT)。方便调试和向用户展示。
        *   `created_at`: 创建时间 (DATETIME)。
        *   `updated_at`: 最后更新时间 (DATETIME)。

2.  **扩展 `SyncJobDao` (`lib/data/datasources/local_db/daos/sync_job_dao.dart`)**
    *   DAO需要提供更丰富的原子操作来管理作业队列：
        *   `addJob(SyncJob job)`: 新增一个作业。
        *   `getPendingJobs(int limit)`: 获取一批处于 `pending` 状态的作业。这是后台执行器拉取任务的入口。
        *   `markJobAsRunning(int jobId)`: 将作业状态更新为 `running`。
        *   `markJobAsCompleted(int jobId)`: 将作业状态更新为 `completed`（或者直接删除）。
        *   `markJobAsFailed(int jobId, String error, int newAttempts)`: 记录失败信息并更新尝试次数。
        *   `resetStaleJobs()`: (可选，但推荐) 找出那些处于 `running` 状态很久但没完成的作业（可能是上次运行时应用崩溃了），将它们重置为 `pending`。

### **第二阶段：引入并配置原生后台执行器**

这是将我们的同步逻辑“托管”给操作系统的关键一步。

1.  **引入依赖**
    *   选择一个插件来与原生后台任务框架交互。`flutter_workmanager` 是一个非常成熟且跨平台的选择。将其添加到 `pubspec.yaml`。

2.  **创建后台任务入口点**
    *   `flutter_workmanager` 要求在 `main.dart` 或其他文件的顶层定义一个回调函数，例如 `callbackDispatcher()`。
    *   这个函数是**在独立的 Isolate 中由操作系统直接调用的**，它不能直接访问Flutter的UI状态，但可以执行Dart代码。

3.  **在后台入口点中初始化服务**
    *   `callbackDispatcher` 函数内部，第一件事就是**重新初始化依赖注入容器**：`configureDependencies()`。这样我们才能在后台拿到数据库、网络服务等实例。
    *   然后，从 `flutter_workmanager` 传入的任务信息中，解析出我们需要执行的逻辑。

4.  **改造 `BackgroundServiceManager` (`lib/services/background_service_manager.dart`)**
    *   这个类是配置和调度后台任务的最佳位置。
    *   **职责**：
        *   **初始化 `flutter_workmanager`**：在App启动时调用 `Workmanager().initialize(callbackDispatcher)`。
        *   **注册同步任务**：定义一个唯一的后台任务名称，例如 `"com.yourapp.syncTask"`。
        *   **调度任务**：在合适的时机，向 `Workmanager` 注册一个任务。例如：
            *   注册一个**周期性任务**（如每小时检查一次）。
            *   或者，在每次有新作业被添加到数据库时，注册一个**一次性任务**，并设置网络条件（如 `Constraints(networkType: NetworkType.UNMETERED)`，表示仅在Wi-Fi下执行）。

### **第三阶段：重构现有服务，明确各自职责**

这是将所有部分串联起来的流程改造。

1.  **`LocalMediaObserver` (`lib/services/local_media_observer.dart`) - 职责：变更发现者**
    *   其核心逻辑 `_reconcileAndStartListening` 和 `_handleChanges` 不再自己处理 `_processNewAsset`。
    *   **新流程**：当它发现一个新增的资产ID（`newId`）或删除的资产ID（`deletedId`）时，它只做一件事：**调用 `SyncJobManager` 去创建一个对应的作业**。
    *   它不再关心这个作业何时、如何被执行。它变成了纯粹的“发现者”和“任务派发者”。

2.  **`SyncJobManager` (`lib/services/sync_job_manager.dart`) - 职责：作业创建者**
    *   移除所有处理、上传、删除的逻辑。
    *   提供简单明了的方法，如：
        *   `Future<void> createUploadJob(String assetId)`
        *   `Future<void> createDeletionJob(String assetId)`
    *   这些方法内部，会构建一个 `SyncJob` 对象（状态为 `pending`），然后调用 `SyncJobDao` 将其存入数据库。
    *   （可选）在成功创建作业后，它可以触发 `BackgroundServiceManager` 去调度一次后台任务。

3.  **`SyncJobProcessor` (`lib/services/sync_job_processor.dart`) - 职责：作业执行者**
    *   这个类现在成为后台任务的**核心引擎**。它包含了之前散落在各处的实际业务逻辑（获取文件、上传到服务器、调用API删除等）。
    *   **它将在 `callbackDispatcher` 定义的后台 Isolate 中被调用**。
    *   **核心方法 `processPendingJobs()`**：
        1.  调用 `SyncJobDao.getPendingJobs()` 获取一批待处理作业。
        2.  遍历这批作业：
        3.  对于每个作业，调用 `SyncJobDao.markJobAsRunning()`。
        4.  执行实际操作（上传或删除）。
            *   如果成功，调用 `SyncJobDao.markJobAsCompleted()`。
            *   如果失败，捕获异常，调用 `SyncJobDao.markJobAsFailed()` 记录错误和尝试次数。
        5.  所有作业处理完毕后，向 `flutter_workmanager` 返回 `Future.value(true)` 表示成功。

### **第四阶段：UI反馈与状态展示**

UI需要知道后台发生了什么。

1.  **`MediaViewModel` / `GalleryViewModel` (`lib/ui/.../viewmodels`)**
    *   它们需要一种方式来展示同步状态。最佳方式是**监听数据库的变化**。
    *   通过 `Drift` (您使用的数据库库) 的 `watch` 功能，`MediaAssetDao` 或 `SyncJobDao` 可以提供一个 `Stream`。
    *   例如，`SyncJobDao` 可以提供一个 `watchPendingJobsCount()` 的流，UI层可以监听这个流来显示“N个项目等待同步”。
    *   `MediaAssetDao` 可以为每个 `MediaAsset` 增加一个 `syncStatus` 字段。当 `SyncJobProcessor` 完成一个上传作业时，它会更新对应资产的状态。UI上的角标（如等待图标、同步完成图标）就可以根据这个状态来显示。

---

### **总结：新的工作流**

1.  **启动/变更**：`LocalMediaObserver` 检测到6000个新照片。
2.  **创建作业**：它循环调用 `SyncJobManager.createUploadJob()` 6000次。
3.  **持久化**：`SyncJobManager` 快速地在 `sync_jobs` 表中插入了6000条状态为 `pending` 的记录。**这个过程非常快，UI不会卡顿。**
4.  **调度**：`SyncJobManager` 通知 `BackgroundServiceManager`：“有活了！” `BackgroundServiceManager` 调度一个WorkManager任务（例如，要求有网络连接）。
5.  **执行**：在未来的某个时刻（可能几秒后，也可能几分钟后，由系统决定），操作系统在后台唤醒App的 `callbackDispatcher`。
6.  **处理**：后台Isolate中的 `SyncJobProcessor` 被唤醒，从DAO中拉取一批（比如20个）`pending` 的作业，开始逐个上传，并不断更新数据库中作业的状态。
7.  **反馈**：用户在前台打开App，UI通过监听数据库的 `Stream`，实时看到待同步数量在减少，以及每个照片缩略图的同步状态图标在变化。
8.  **容错**：`SyncJobProcessor` 处理到第10个作业时应用崩溃了。没关系，前9个作业状态已是 `completed`，第10个作业状态还是 `running` (或 `pending`)。下次后台任务再次启动时，会从第10个作业继续处理（或通过 `resetStaleJobs` 机制重置它）。

这个方案将彻底解决您遇到的性能和稳定性问题，并让您的应用拥有与业内顶尖产品同级别的后台同步架构。
