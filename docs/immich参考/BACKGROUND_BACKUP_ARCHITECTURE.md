## 架构概述

Immich 移动端采用**新版后台备份方案（BackgroundWorkerService）**，这是一个基于独立 Flutter Engine 和 Pigeon 类型安全通信的现代化后台任务架构。

### 核心特点

- **独立 Engine 架构**：后台任务运行在完全独立的 Flutter Engine 中，与主应用 UI Engine 隔离
- **类型安全通信**：使用 Pigeon 进行跨平台通信，编译时类型检查
- **平台原生集成**：Android 使用 WorkManager，iOS 使用 BGTaskScheduler
- **智能资源管理**：自动清理机制，防止内存泄漏
- **灵活的任务调度**：支持多种触发条件和约束

## 核心设计理念

### 1. 隔离性（Isolation）

**为什么需要隔离？**

- **内存隔离**：后台任务可能处理大量数据，独立 Engine 避免影响主应用性能
- **生命周期独立**：后台任务可以独立启动和销毁，不受主应用状态影响
- **错误隔离**：后台任务崩溃不会导致主应用崩溃

**实现方式：**

- Android：每个 WorkManager Worker 创建独立的 FlutterEngine 实例
- iOS：每个 BGTask 创建独立的 FlutterEngine 实例
- 使用 Engine Cache 管理 Engine 生命周期

### 2. 类型安全（Type Safety）

**Pigeon 的优势：**

- **编译时检查**：接口定义在编译时验证，减少运行时错误
- **自动代码生成**：为 Dart、Swift、Kotlin 自动生成接口代码
- **IDE 支持**：完整的类型提示和自动补全
- **文档化**：接口定义即文档

**接口层次：**

```
Pigeon 定义文件
    ↓
自动生成代码
    ├─ Dart (Flutter 侧)
    ├─ Swift (iOS 侧)
    └─ Kotlin (Android 侧)
```

### 3. 平台原生集成

**为什么使用原生调度？**

- **系统优化**：系统会根据设备状态智能调度任务
- **电池优化**：系统会考虑电池状态、网络条件等
- **可靠性**：系统保证任务在合适的时机执行

**平台差异：**

| 特性     | Android                    | iOS                                  |
| -------- | -------------------------- | ------------------------------------ |
| 调度系统 | WorkManager                | BGTaskScheduler                      |
| 触发方式 | ContentObserver + 定期任务 | BGAppRefreshTask + BGProcessingTask  |
| 执行时间 | 无硬性限制                 | Refresh: ~20秒, Processing: 系统决定 |
| 约束条件 | 网络、充电、电池等         | 网络、电源等                         |

## 架构组件详解

### 1. 前台服务层（Foreground Service Layer）

**职责：**
- 管理后台任务的启用/禁用
- 配置任务参数（延迟、约束条件等）
- 保存通知配置

**关键类：**
- `BackgroundWorkerFgService`：前台服务接口封装
- `BackgroundWorkerFgHostApi`：Pigeon 生成的前台 API

**主要方法：**
- `enable()`：启用后台任务
- `disable()`：禁用后台任务
- `configure()`：配置任务参数
- `saveNotificationMessage()`：保存通知消息

### 2. 后台服务层（Background Service Layer）

**职责：**
- 执行实际的后台备份任务
- 管理独立 Flutter Engine 的生命周期
- 处理任务完成和清理

**关键类：**
- `BackgroundWorkerBgService`：后台服务实现
- `BackgroundWorkerFlutterApi`：Pigeon 生成的后台 API
- `BackgroundWorkerBgHostApi`：与原生通信的 API

**主要方法：**
- `onAndroidUpload()`：Android 上传任务入口
- `onIosUpload()`：iOS 上传任务入口
- `cancel()`：取消任务
- `init()`：初始化后台服务

### 3. 同步管理层（Sync Management Layer）

**职责：**
- 同步本地资产到数据库
- 同步远程服务器资产
- 计算资产哈希值（用于去重）

**关键类：**
- `BackgroundSyncManager`：同步管理器
- `backgroundSyncProvider`：Riverpod 提供者

**同步流程：**
1. **本地同步**：扫描设备媒体库，更新本地数据库
2. **远程同步**：从服务器获取已上传资产列表
3. **哈希计算**：计算待上传资产的哈希值（可选，有超时限制）

### 4. 上传管理层（Upload Management Layer）

**职责：**
- 管理上传任务队列
- 处理上传进度和状态
- 处理上传错误和重试

**关键类：**
- `UploadService`：上传服务
- `UploadRepository`：上传仓库
- `background_downloader`：底层上传引擎

**上传配置：**
- 最大并发数：6 个任务
- 每个服务器最大并发：6
- 每个组最大并发：3
- 大文件阈值：256MB（Android 上使用前台服务）

## 平台特定实现

### Android 实现

#### 1. 两级 Worker 架构

**MediaObserver Worker：**
- **职责**：监听媒体库变化
- **触发条件**：
  - 内容 URI 变化（图片/视频添加）
  - 延迟触发（可配置，默认 5 秒）
  - 最大延迟（默认 50 秒）
  - 可选：需要充电
- **行为**：检测到变化后，触发 BackgroundWorker

**BackgroundWorker：**
- **职责**：执行实际备份任务
- **触发条件**：
  - 电池电量充足
  - 由 MediaObserver 或系统调度触发
- **行为**：
  - 创建独立 Flutter Engine
  - 执行备份流程
  - 完成后清理资源

#### 2. Engine 管理

**Engine 创建：**
```kotlin
engine = FlutterEngine(ctx)
FlutterEngineCache.getInstance().put(ENGINE_CACHE_KEY, engine)
```

**Engine 销毁：**
```kotlin
engine?.destroy()
FlutterEngineCache.getInstance().remove(ENGINE_CACHE_KEY)
```

**关键点：**
- 使用 Engine Cache 管理 Engine 生命周期
- 任务完成后必须销毁 Engine，避免内存泄漏
- 检查 Engine 是否存在可以判断任务是否运行中

#### 3. 通知管理

**前台服务通知：**
- 如果应用忽略电池优化，使用前台服务（Foreground Service）
- 否则使用普通通知
- 通知内容可配置（标题、内容）

**通知配置：**
- 重要性：LOW（低优先级，不打扰用户）
- 类型：ONGOING（持续通知）
- 图标：应用图标

### iOS 实现

#### 1. 两种任务类型

**BGAppRefreshTask（刷新任务）：**
- **用途**：快速同步和轻量级上传
- **执行时间**：约 20 秒
- **触发频率**：系统决定（通常每 15-30 分钟）
- **限制**：必须快速完成，不能执行长时间操作

**BGProcessingTask（处理任务）：**
- **用途**：长时间上传任务
- **执行时间**：系统决定（通常几分钟）
- **触发条件**：
  - 需要网络连接
  - 可配置需要外部电源
  - 最早执行时间（默认 15 分钟后）
- **限制**：系统可能随时终止

#### 2. 任务调度策略

**刷新任务调度：**
- 每次刷新任务完成后，立即调度下一个
- 最早执行时间：5 分钟后
- 用于保持数据同步

**处理任务调度：**
- 每次处理任务完成后，立即调度下一个
- 最早执行时间：15 分钟后
- 需要网络连接
- 可选：需要外部电源

#### 3. 超时处理

**刷新任务：**
- 硬性超时：20 秒
- 超时后自动取消任务

**处理任务：**
- 软性超时：由系统决定
- 通过 `expirationHandler` 处理系统终止
- 给 Flutter 侧 2 秒时间清理资源

#### 4. 信号量同步

**为什么需要信号量？**
- 防止多个任务同时运行
- iOS 系统可能同时触发多个任务
- 使用 `DispatchSemaphore` 确保互斥

**实现：**
```swift
private static let taskSemaphore = DispatchSemaphore(value: 1)

// 在任务开始时
if taskSemaphore.wait(timeout: .now()) == .success {
    // 执行任务
} else {
    // 另一个任务正在运行，放弃执行
}

// 在任务结束时
defer { taskSemaphore.signal() }
```

## 工作流程

### 完整备份流程

```
1. 任务触发
   ├─ Android: MediaObserver 检测到变化 / 系统调度
   └─ iOS: BGTaskScheduler 触发任务

2. 原生层处理
   ├─ 创建独立 Flutter Engine
   ├─ 注册 Pigeon API
   └─ 启动 Dart 入口点

3. Flutter 侧初始化
   ├─ 初始化数据库连接
   ├─ 加载翻译资源
   ├─ 配置 API 端点
   ├─ 配置文件下载器
   └─ 通知原生层初始化完成

4. 同步阶段
   ├─ 本地同步（syncLocal）
   │   └─ 扫描设备媒体库，更新本地数据库
   ├─ 远程同步（syncRemote）
   │   └─ 从服务器获取已上传资产列表
   └─ 哈希计算（hashAssets，可选）
       └─ 计算待上传资产的哈希值（有超时限制）

5. 备份执行
   ├─ 检查备份是否启用
   ├─ 获取当前用户
   ├─ 构建上传候选列表
   ├─ 过滤已上传资产
   └─ 执行上传
       ├─ 遍历候选资产
       ├─ 读取文件
       ├─ 上传到服务器
       ├─ 更新进度
       └─ 处理错误

6. 清理阶段
   ├─ 取消哈希计算
   ├─ 释放 Worker Manager
   ├─ 关闭日志服务
   ├─ 关闭数据库连接
   ├─ 销毁 Flutter Engine
   └─ 通知原生层任务完成
```

### 关键流程详解

#### 1. 任务触发流程

**Android：**
1. MediaObserver 检测到媒体库变化
2. 满足约束条件（延迟、充电等）
3. 触发 BackgroundWorker
4. WorkManager 执行 Worker

**iOS：**
1. BGTaskScheduler 根据系统策略触发任务
2. 检查信号量（防止并发）
3. 创建 BackgroundWorker 实例
4. 启动 Flutter Engine

#### 2. 初始化流程

**关键步骤：**
1. **数据库初始化**：创建 Isar 和 Drift 连接
2. **Provider 容器**：创建独立的 Riverpod ProviderContainer
3. **依赖注入**：覆盖数据库提供者，使用后台任务的数据库实例
4. **服务初始化**：
   - 加载翻译资源
   - 初始化 Worker Manager
   - 配置 API 端点
   - 配置文件下载器
   - 启用后台文件访问权限
5. **通知原生层**：调用 `onInitialized()` 通知原生层准备就绪

**为什么需要独立 ProviderContainer？**
- 后台任务需要独立的依赖注入上下文
- 避免与主应用的 Provider 冲突
- 可以覆盖特定的提供者（如数据库）

#### 3. 同步流程

**本地同步（syncLocal）：**
- 扫描设备媒体库
- 更新本地数据库（Isar）
- 识别新增、修改、删除的资产

**远程同步（syncRemote）：**
- 从服务器获取已上传资产列表
- 更新本地数据库中的远程资产信息
- 用于后续去重判断

**哈希计算（hashAssets）：**
- 计算待上传资产的哈希值
- 用于去重和完整性校验
- **超时机制**：
  - Android：3-6 分钟（根据备份是否启用）
  - iOS：5 秒（刷新任务）或 3-6 分钟（处理任务）
- 超时后继续执行，不阻塞备份流程

#### 4. 备份执行流程

**候选资产构建：**
1. 根据选中的相册获取资产
2. 根据排除的相册过滤资产
3. 应用时间过滤器（只获取上次备份后的新资产）

**去重处理：**
1. 检查本地重复资产数据库
2. 调用服务器 API 检查已存在资产
3. 过滤掉已上传的资产

**上传执行：**
1. 按类型排序（图片优先于视频）
2. 遍历候选资产
3. 对于每个资产：
   - 检查权限
   - 读取文件（iOS 可能需要从 iCloud 下载）
   - 创建上传请求
   - 上传文件
   - 更新进度
   - 处理错误

**进度通知：**
- 总进度：已上传数量 / 总数量
- 单文件进度：已上传字节数 / 文件总大小
- 当前文件信息：文件名、类型等

## 数据同步机制

### 本地数据库结构

**Isar（NoSQL）：**
- 存储资产元数据
- 存储相册信息
- 快速查询和索引

**Drift（SQL）：**
- 存储备份状态
- 存储上传任务队列
- 关系型数据管理

### 同步策略

**增量同步：**
- 只同步上次备份后的新资产
- 使用 `lastBackup` 时间戳过滤
- 减少网络传输和服务器负载

**去重机制：**
- **本地去重**：检查本地重复资产数据库
- **服务器去重**：调用 `checkExistingAssets` API
- **设备 ID 匹配**：使用 `deviceAssetId` 和 `deviceId` 匹配

**冲突处理：**
- 如果服务器返回 200（已存在），标记为重复
- 如果服务器返回 201（新建），创建新资产
- 记录重复资产 ID，避免重复检查

### 状态管理

**备份状态：**
- `totalCount`：总资产数
- `backupCount`：已备份数量
- `remainderCount`：剩余数量
- `processingCount`：处理中数量

**同步状态：**
- `isRemoteSyncing`：远程同步中
- `isLocalSyncing`：本地同步中
- `isHashing`：哈希计算中

## 资源管理与清理

### 清理时机

**正常完成：**
- 备份任务完成后
- 所有资源必须清理

**异常终止：**
- 系统终止任务
- 用户取消任务
- 超时终止

### 清理步骤

**1. 标记清理状态：**
```dart
_isCleanedUp = true
```
防止重复清理和后续操作

**2. 取消进行中的操作：**
- 取消哈希计算
- 取消同步任务
- 取消上传任务

**3. 关闭数据库连接：**
- 关闭 Drift 连接
- 关闭 DriftLogger
- 关闭 Isar（如果打开）

**4. 释放 Provider 容器：**
```dart
_ref?.dispose()
_ref = null
```

**5. 释放其他资源：**
- Worker Manager
- 日志服务
- Store

**6. 销毁 Flutter Engine（原生层）：**
- Android：`engine.destroy()`
- iOS：`engine.destroyContext()`
- 从 Engine Cache 中移除

### 内存管理最佳实践

**1. 及时清理：**
- 任务完成后立即清理
- 不要等待系统回收

**2. 检查清理状态：**
- 在执行任何操作前检查 `_isCleanedUp`
- 避免在清理后执行操作

**3. 异常安全：**
- 使用 `try-finally` 确保清理执行
- 使用 `runZonedGuarded` 捕获异常

**4. 资源限制：**
- 限制并发任务数
- 限制内存使用
- 大文件使用流式处理

## 错误处理与恢复

### 错误类型

**1. 网络错误：**
- 连接超时
- 服务器错误
- 网络不可用

**处理策略：**
- 记录错误
- 跳过当前资产
- 继续处理下一个资产
- 任务完成后，系统会重新调度

**2. 文件访问错误：**
- 权限不足
- 文件不存在
- 文件被删除

**处理策略：**
- 记录错误资产
- 跳过该资产
- 继续处理其他资产

**3. 服务器错误：**
- 配额超限
- 认证失败
- 服务器维护

**处理策略：**
- 配额超限：停止上传，记录错误
- 认证失败：记录错误，下次重试
- 服务器错误：记录错误，继续尝试

**4. 系统终止：**
- iOS 系统终止任务
- Android 系统回收资源

**处理策略：**
- 快速保存状态
- 清理资源
- 下次任务继续

### 错误恢复机制

**1. 自动重试：**
- WorkManager 自动重试失败的任务
- 使用指数退避策略

**2. 状态持久化：**
- 备份状态保存在数据库
- 下次任务可以继续

**3. 错误通知：**
- 记录错误资产
- 用户可以在 UI 中查看
- 支持手动重试

### 日志记录

**日志级别：**
- `INFO`：正常流程日志
- `WARNING`：警告信息
- `SEVERE`：严重错误

**日志内容：**
- 任务开始/结束时间
- 同步状态
- 上传进度
- 错误信息
- 性能指标

## 性能优化策略

### 1. 并发控制

**上传并发：**
- 最大并发：6 个任务
- 每个服务器最大并发：6
- 每个组最大并发：3

**为什么限制并发？**
- 避免网络拥塞
- 避免服务器过载
- 平衡速度和稳定性

### 2. 任务优先级

**资产排序：**
- 图片优先于视频
- 按创建时间排序
- 小文件优先（可选）

**为什么图片优先？**
- 图片通常更小，上传更快
- 用户可以更快看到备份结果
- 视频可以在后台慢慢上传

### 3. 超时策略

**哈希计算超时：**
- Android：3-6 分钟
- iOS：5 秒（刷新）或 3-6 分钟（处理）

**为什么需要超时？**
- 哈希计算可能很慢
- 不应该阻塞整个备份流程
- 超时后继续执行备份

### 4. 内存优化

**流式处理：**
- 大文件使用流式上传
- 不将整个文件加载到内存

**及时释放：**
- 上传完成后立即释放文件句柄
- iOS 上删除临时文件

### 5. 网络优化

**条件上传：**
- 可配置仅 Wi-Fi 上传
- 可配置需要充电
- 检查网络类型（计量/非计量）

**批量检查：**
- 批量检查已存在资产
- 减少 API 调用次数

## 常见问题与解决方案

### 1. 后台任务不执行

**可能原因：**
- 电池优化未禁用
- 任务未正确调度
- 约束条件不满足

**解决方案：**
- 引导用户禁用电池优化
- 检查任务调度逻辑
- 放宽约束条件（测试时）

### 2. 任务被系统终止

**可能原因：**
- iOS 超时限制
- 系统资源不足
- 用户强制停止

**解决方案：**
- 快速保存状态
- 优化任务执行时间
- 处理终止信号

### 3. 内存泄漏

**可能原因：**
- Engine 未销毁
- 数据库连接未关闭
- Provider 容器未释放

**解决方案：**
- 确保清理流程完整
- 使用工具检查内存
- 定期测试内存使用

### 4. 上传失败

**可能原因：**
- 网络问题
- 服务器错误
- 文件访问错误

**解决方案：**
- 实现重试机制
- 记录错误信息
- 提供手动重试

### 5. 同步不完整

**可能原因：**
- 超时限制
- 数据库锁定
- 权限问题

**解决方案：**
- 增加超时时间（如果可能）
- 优化数据库操作
- 检查权限状态

Immich 的新版后台备份方案是一个**现代化、可靠、高性能**的架构设计。它通过以下关键特性实现了优秀的用户体验：

1. **隔离性**：独立 Engine 确保后台任务不影响主应用
