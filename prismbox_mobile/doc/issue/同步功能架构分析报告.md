## 同步功能架构分析报告

### 优点

1. 职责划分清晰
   - `local_sync` 和 `remote_sync` 分别处理本地和远程同步
   - `SyncCoordinator` 和 `RemoteSyncCoordinator` 负责协调与状态管理
   - 服务层负责具体业务逻辑

2. 目录结构合理
   - `features/local_sync` 和 `features/remote_sync` 按功能模块组织
   - 子目录清晰：`models/`, `services/`, `providers/`, `exceptions/`

3. 依赖注入
   - 使用 Riverpod 进行依赖管理
   - Coordinator 使用 `keepAlive: true` 保证单例

### 存在的问题

#### 1. 代码重复和职责重叠

问题1: 存在多个同步管理器
- `BackgroundSyncManager` (services/sync/)
- `SyncCoordinator` (features/local_sync/)
- `RemoteSyncCoordinator` (features/remote_sync/)

问题2: 远程同步有多个实现
- `RemoteSyncService` 使用流式同步 API
- `BackgroundSyncManager.syncRemote()` 使用分页 API

建议: 统一远程同步的实现方式，只保留一种。

#### 2. 命名不一致

```103:103:prismbox_mobile/lib/features/local_sync/services/sync_coordinator.dart
  Future<void> _checkAndSync({bool force = false}) async {
```

```139:152:prismbox_mobile/lib/features/remote_sync/services/remote_sync_coordinator.dart
  Future<void> _checkAndSync({
    required String userId,
    bool force = false,
  }) async {
```

问题: 两个 Coordinator 都有 `_checkAndSync` 方法，但签名不同，容易混淆。

建议: 为本地同步的 `_checkAndSync` 加上明确的前缀，或统一抽象接口。

#### 3. 耦合问题

问题1: SyncCoordinator 直接依赖 AssetSyncService
```174:175:prismbox_mobile/lib/features/local_sync/services/sync_coordinator.dart
        // 启动后台任务：为没有 checksum 的本地资产计算 checksum 并匹配远程资产
        _startChecksumMatchingTask();
```

```254:254:prismbox_mobile/lib/features/local_sync/services/sync_coordinator.dart
        final assetSyncService = AssetSyncService(database: _database);
```

问题: `SyncCoordinator` 依赖 `AssetSyncService`，职责混杂。

建议: 将 checksum 匹配逻辑提取为独立的服务或策略。

#### 4. 目录结构不一致

问题:
- `local_sync` 位于 `features/`
- `BackgroundSyncManager` 位于 `services/sync/`
- `AssetSyncService` 位于 `services/sync/`

建议: 统一组织方式。如果按功能模块划分，将相关服务移至对应 feature；如果按层次划分，将 `local_sync` 和 `remote_sync` 移至 `services/`。

#### 5. 数据新鲜度阈值不一致

```40:41:prismbox_mobile/lib/features/local_sync/services/sync_coordinator.dart
  /// 数据新鲜度阈值（1小时）
  static const Duration _freshnessThreshold = Duration(hours: 1);
```

```40:41:prismbox_mobile/lib/features/remote_sync/services/remote_sync_coordinator.dart
  /// 数据新鲜度阈值（30分钟）
  static const Duration _dataFreshnessThreshold = Duration(minutes: 1);
```

问题: 注释写的是 30 分钟，实际是 1 分钟；与本地同步的 1 小时不一致。

建议: 统一阈值或说明差异原因，并修正注释。

#### 6. 重复的取消逻辑

问题: `LocalSyncService` 有自定义 `CancelToken`，而 `RemoteSyncService` 使用 `bool _isCancelled`。

```23:23:prismbox_mobile/lib/features/local_sync/services/local_sync_service.dart
  CancelToken? _cancelToken;
```

```28:28:prismbox_mobile/lib/features/remote_sync/services/remote_sync_service.dart
  bool _isCancelled = false;
```

建议: 统一取消机制，使用同一个工具类。

#### 7. 互斥锁实现不一致

问题: `SyncCoordinator` 使用 `AsyncMutex`，`RemoteSyncCoordinator` 使用 `synchronized` 包的 `Lock`。

```32:32:prismbox_mobile/lib/features/local_sync/services/sync_coordinator.dart
  final AsyncMutex _syncMutex = AsyncMutex();
```

```29:29:prismbox_mobile/lib/features/remote_sync/services/remote_sync_coordinator.dart
  final _syncLock = Lock();
```

建议: 统一互斥锁实现，保持一致性。

### 改进建议

#### 1. 统一同步架构

```
services/sync/
├── coordinators/
│   ├── sync_coordinator_interface.dart  # 抽象接口
│   ├── local_sync_coordinator.dart      # 本地同步协调器
│   └── remote_sync_coordinator.dart     # 远程同步协调器
├── services/
│   ├── local_sync_service.dart
│   ├── remote_sync_service.dart
│   └── asset_sync_service.dart
└── models/
```

#### 2. 提取 Checksum 匹配服务

```dart
services/sync/services/checksum_matching_service.dart
```

将 checksum 匹配逻辑从 `SyncCoordinator` 中分离。

#### 3. 统一工具类

- 统一使用 `CancellationToken` 或统一的取消机制
- 统一使用 `AsyncMutex` 或 `Lock`

#### 4. 移除重复实现

确定并移除 `BackgroundSyncManager` 中的远程同步实现，统一使用 `RemoteSyncService` 的流式同步。

#### 5. 配置化阈值

```dart
class SyncConfig {
  static const Duration localFreshnessThreshold = Duration(hours: 1);
  static const Duration remoteFreshnessThreshold = Duration(minutes: 30);
  // ...
}
```

### 总结

评分：
- 架构合理性: 7/10（职责清晰，但存在重复）
- 逻辑清晰度: 8/10（整体流程清楚，命名略有混淆）
- 代码维护性: 6/10（重复代码较多，耦合偏高）
- 目录结构: 7/10（基本合理，但组织不一致）
- 文件命名: 8/10（基本清晰，部分可优化）
- 高内聚低耦合: 6/10（部分耦合较高，存在重复）

主要改进方向：
1. 消除代码重复
2. 统一命名和实现
3. 降低耦合（提取 Checksum 服务）
4. 统一目录组织
5. 统一工具类和配置

整体架构思路正确，但需要在统一性和去重方面加强。
