## 模块概述

### 职责范围

本地媒体同步模块是 PrismBox 移动端的核心功能模块，负责：

1. **本地媒体库同步**：将系统相册的媒体资源同步到本地数据库
2. **数据获取**：提供 BaseAsset 数据列表，支持从数据库或 photo_manager 获取
3. **智能数据源切换**：根据数据可用性自动选择最优数据源（数据库或 photo_manager）
4. **上传状态标识**：清晰标识媒体资源的上传状态（已上传/未上传/上传中）
5. **后台同步协调**：在后台执行同步任务，不阻塞用户浏览体验

### 模块定位

本模块专注于**数据获取和同步**，与**媒体资源展示模块**形成清晰的层次关系：

- **本模块（数据层）**：提供 BaseAsset 数据列表
  - 从数据库或 photo_manager 获取媒体资源数据
  - 同步系统相册到数据库
  - 管理数据源选择和数据一致性
  
- **媒体资源展示模块（展示层）**：接收 BaseAsset，加载和渲染图片
  - 接收本模块提供的 BaseAsset 数据
  - 选择 ImageProvider（本地或远程）
  - 加载图片资源并渲染到 UI

**数据流向**：
```
本地媒体同步模块 → BaseAsset 列表 → 媒体资源展示模块 → ImageProvider → 图片渲染
```

**注意**：本模块负责提供数据（BaseAsset 列表），不负责图片的加载和渲染，
后者由媒体资源展示模块负责。

### 核心目标

1. **即时数据获取**：应用启动后立即提供媒体资源数据，减少用户等待时间
2. **后台同步**：同步在后台执行，不阻塞用户浏览
3. **数据一致性**：同步完成后保持数据一致，支持增量更新
4. **状态可见**：清晰标识上传状态，支持实时更新
5. **性能优化**：优先使用数据库查询，必要时回退到直接扫描

### 设计原则

1. **双路径并行**：UI 线程立即获取数据 + 后台线程同步，互不阻塞
2. **智能数据源切换**：根据数据可用性自动选择最优数据源
3. **渐进式优化**：先实现基础功能，再逐步优化性能
4. **状态驱动**：通过状态管理实现响应式更新
5. **用户体验优先**：确保用户能立即获取数据，后台优化数据

### 与其他模块的关系

```
本地媒体同步模块
    │
    ├─→ 数据库模块：存储本地资产信息（LocalAssetEntity）
    ├─→ 媒体资源展示模块：提供 BaseAsset 数据源，由媒体资源展示模块负责图片加载
    ├─→ 备份上传下载模块：共享同步逻辑，关联上传状态
    ├─→ 页面导航模块：为照片页面提供时间线数据（BaseAsset 列表）
    └─→ API 对接模块：同步远程资产信息，关联本地和远程资产
```

## 架构设计

### 整体架构

本地媒体同步模块采用**双路径并行架构**，通过智能的数据源选择、后台同步协调和状态管理，实现即时数据获取和后台优化的平衡。

```
┌─────────────────────────────────────────────────────────────┐
│                    应用启动流程                               │
│                                                               │
│  1. 应用启动                                                  │
│     ↓                                                         │
│  2. 并行执行（不阻塞）：                                      │
│     ├─→ UI 线程：照片页面立即加载                            │
│     │   ├─→ 检查数据库数据可用性                             │
│     │   ├─→ 数据可用 → 从数据库读取 ✅                        │
│     │   └─→ 数据不可用 → 从 photo_manager 读取 ✅            │
│     │                                                         │
│     └─→ 后台线程：同步服务启动（延迟 2 秒）                  │
│         ├─→ 检查数据库数据新鲜度                             │
│         ├─→ 数据新鲜 → 增量同步                              │
│         └─→ 数据过期/缺失 → 全量同步                         │
│                                                               │
│  3. 同步完成后：                                              │
│     └─→ 刷新时间线数据（可选切换到数据库数据源）            │
└─────────────────────────────────────────────────────────────┘
```

### 核心组件

1. **LocalSyncService（本地同步服务）**：负责扫描系统相册并同步到数据库
2. **TimelineProvider（时间线数据提供者）**：提供时间线数据，支持双数据源
3. **SyncCoordinator（同步协调器）**：协调后台同步任务，不阻塞 UI
4. **数据源选择器**：根据数据可用性自动选择最优数据源
5. **状态管理器**：管理同步状态和上传状态

### 技术选型

#### Flutter 侧
- **photo_manager**：访问系统相册资源
- **Riverpod**：状态管理和依赖注入
- **Drift**：本地数据库存储
- **Isolate**：后台同步执行（可选）

#### 平台原生 API
- **Android**：MediaStore（通过 photo_manager）
- **iOS**：PHPhotoLibrary（通过 photo_manager）

## 核心组件详解

### 1. LocalSyncService（本地同步服务）

#### 1.1 职责

- 扫描系统相册，识别新增/修改/删除的资产
- 更新本地数据库（LocalAssetEntity）
- 计算 checksum（可选，后台执行）
- 关联远程资产（通过 checksum）

#### 1.2 核心方法

**syncLocal()**
- **功能**：同步本地媒体库到数据库
- **参数**：
  - `full`：是否全量同步（false 时尝试增量同步）
  - `onProgress`：进度回调 (current, total)
- **返回值**：SyncResult（包含新增、更新、删除数量）

**同步类型**：

1. **全量同步**
   - 触发时机：首次同步、数据库为空、用户手动触发
   - 执行内容：扫描所有系统相册资产，完整更新数据库
   - 性能考虑：分批处理（每批 100 个），避免内存溢出

2. **增量同步**
   - 触发时机：数据库已有数据，定期同步
   - 执行内容：只处理新增/修改/删除的资产
   - 优化策略：通过修改时间快速判断，避免全量对比

#### 1.3 同步流程

**全量同步流程**：

```
1. 请求相册权限
   ↓
2. 获取所有相册列表
   ↓
3. 获取"所有照片"相册
   ↓
4. 分批获取资产（每批 100 个）
   ├─→ 转换 AssetEntity → LocalAssetEntityData
   ├─→ 批量写入数据库
   └─→ 更新进度回调
   ↓
5. 检测已删除的资产（对比数据库）
   └─→ 批量删除
   ↓
6. 同步完成
   └─→ 返回 SyncResult
```

**增量同步流程**：

```
1. 检查数据库最后同步时间
   ↓
2. 获取系统相册变更（通过修改时间过滤）
   ├─→ 新增：不在数据库中的资产
   ├─→ 修改：修改时间更新的资产
   └─→ 删除：数据库中存在但系统相册中不存在的资产
   ↓
3. 批量更新数据库
   ↓
4. 同步完成
```

### 2. TimelineProvider（时间线数据提供者）

#### 2.1 职责

- 提供时间线数据（BaseAsset 列表）
- 支持双数据源（数据库和 photo_manager）
- 根据数据可用性自动选择最优数据源
- 响应数据源切换

#### 2.2 数据源选择逻辑

**数据源优先级**：

1. **数据库数据源（优先）**
   - 条件：数据库资产数量 > 阈值（建议 100 条）
   - 优势：查询性能好，支持复杂筛选，包含元数据
   - 适用：后续展示、数据已同步的场景

2. **photo_manager 数据源（快速路径）**
   - 条件：数据库为空或数据很少
   - 优势：立即可用，无需等待同步
   - 适用：首次启动、手动刷新、数据库不可用

3. **混合数据源（可选优化）**
   - 策略：以 photo_manager 为准，补充数据库元数据
   - 适用：需要最新系统相册状态 + 数据库元数据

**选择逻辑**：

```
应用启动/页面加载
    ↓
检查数据库资产数量
    ├─→ > 阈值（如 100 条）
    │   └─→ 使用数据库数据源 ✅
    │       └─→ 后台增量同步（保持最新）
    │
    └─→ ≤ 阈值或数据库为空
        └─→ 使用 photo_manager 数据源 ✅
            └─→ 后台全量同步
                └─→ 同步完成后可选切换到数据库
```

#### 2.3 数据转换

**从数据库读取**：
- 读取 LocalAssetEntityData
- 转换为 LocalAsset
- **关键**：需要通过 ID 获取 AssetEntity（延迟获取或批量获取）
- **策略**：
  - 方案A：延迟获取（按需获取，首次加载图片时）
  - 方案B：批量获取（读取数据时一次性获取所有 AssetEntity）

**从 photo_manager 读取**：
- 读取 AssetEntity 列表
- 转换为 LocalAsset
- 关键：直接传递 AssetEntity，支持立即加载图片

### 3. SyncCoordinator（同步协调器）

#### 3.1 职责

- 协调后台同步任务
- 管理同步状态
- 不阻塞 UI 线程
- 支持取消操作

#### 3.2 同步时机

**自动同步时机**：

1. **应用启动时（延迟 2 秒）**
   - 不阻塞 UI 渲染
   - 检查数据新鲜度，决定全量或增量同步

2. **应用恢复时（从后台恢复）**
   - 检查数据新鲜度
   - 如果数据过期（如超过 1 小时），触发增量同步

3. **定期同步（可选）**
   - 后台任务定期执行（如每 30 分钟）
   - 使用 WorkManager（Android）/ BGTaskScheduler（iOS）

**手动同步时机**：

1. **用户手动刷新**
   - 从 photo_manager 重新扫描
   - 立即提供最新数据
   - 后台同步到数据库

2. **设置页面触发**
   - 用户主动触发全量同步
   - 显示同步进度

#### 3.3 执行策略

**后台执行**：
- 同步在独立 Isolate 或后台线程执行
- 不阻塞 UI 线程
- 支持取消操作

**状态管理**：
- 通过 SyncStatusProvider 管理同步状态
- UI 可以监听状态变化
- 显示同步进度和错误信息

### 4. 数据源选择器

#### 4.1 职责

- 检查数据库数据可用性
- 决定使用哪个数据源
- 支持手动切换数据源

#### 4.2 选择策略

**数据可用性判断**：
- 数据库资产数量 > 阈值：认为数据库可用
- 数据库资产数量 ≤ 阈值：认为需要重新同步

**切换策略**：
- 平滑切换：同步完成后，刷新时间线数据，自动切换到数据库
- 用户可控：提供设置选项，允许用户选择数据源
- 自动回退：数据库不可用时，自动回退到 photo_manager

### 5. 状态管理器

#### 5.1 同步状态管理

**SyncStatusProvider**：
- 管理同步状态（syncing/success/error）
- 提供同步进度（current/total）
- 支持错误信息传递

**状态更新时机**：
- 同步开始时：更新为 syncing
- 同步进行中：更新进度
- 同步完成：更新为 success
- 同步失败：更新为 error，包含错误信息

#### 5.2 上传状态管理

**上传状态标识**：
- 通过 LocalAssetEntity.remoteAssetId 标识
- 内存状态管理实时上传状态
- 支持状态查询和更新

## 数据流设计

### 1. 应用启动数据流

```
应用启动
    ↓
并行执行：
    ├─→ UI 线程：照片页面加载
    │   ├─→ TimelineProvider 被访问
    │   ├─→ 检查数据库数据可用性
    │   ├─→ 数据可用 → 从数据库读取
    │   │   └─→ 立即提供 BaseAsset 列表 ✅
    │   └─→ 数据不可用 → 从 photo_manager 读取
    │       └─→ 立即提供 BaseAsset 列表 ✅
    │
    └─→ 后台线程：同步服务启动（延迟 2 秒）
        ├─→ LocalSyncService.syncLocal()
        ├─→ 扫描系统相册
        ├─→ 更新数据库
        └─→ 同步完成
            └─→ 刷新 TimelineProvider（可选切换数据源）
```

### 2. 首次启动数据流

```
首次启动（数据库为空）
    ↓
照片页面立即从 photo_manager 读取
    └─→ 立即提供 BaseAsset 列表 ✅
    ↓
后台同步服务启动（延迟 2 秒）
    └─→ 全量同步
        ├─→ 扫描系统相册
        ├─→ 保存到数据库
        ├─→ 计算 checksum（后台执行）
        └─→ 关联远程资产（如果有）
    ↓
同步完成
    └─→ 可选：切换到数据库数据源
        └─→ 后续数据获取从数据库读取
```

### 3. 后续启动数据流

```
后续启动（数据库已有数据）
    ↓
检查数据库数据新鲜度
    ├─→ 数据新鲜（< 1 小时）
    │   └─→ 从数据库读取 ✅
    │       └─→ 后台增量同步（保持最新）
    │
    └─→ 数据过期（> 1 小时）
        └─→ 从数据库读取（立即提供数据）✅
            └─→ 后台增量同步（更新数据）
```

### 4. 手动刷新数据流

```
用户点击刷新
    ↓
从 photo_manager 重新扫描
    └─→ 立即提供最新 BaseAsset 列表 ✅
    ↓
后台同步到数据库
    └─→ 更新数据库
        └─→ 后续数据获取从数据库读取
```

### 5. 上传状态更新数据流

```
上传任务创建
    ↓
标记为 "pending"（内存状态）
    ↓
开始上传
    ↓
标记为 "uploading"（内存状态）
    ↓
上传成功
    ├─→ 更新 LocalAssetEntity.remoteAssetId ✅
    ├─→ 标记为 "success"（内存状态）
    └─→ 刷新 UI 显示
    ↓
上传失败
    └─→ 标记为 "failed"（内存状态）
        └─→ 支持重试
```

## 同步策略设计

### 1. 同步类型

#### 1.1 全量同步

**触发条件**：
- 首次同步（数据库为空）
- 用户手动触发全量同步
- 数据库数据严重过期（如超过 24 小时）

**执行内容**：
- 扫描所有系统相册资产
- 完整更新数据库
- 检测并删除已不存在的资产

**性能优化**：
- 分批处理（每批 100 个资产）
- 批量写入数据库
- 后台执行，不阻塞 UI

#### 1.2 增量同步

**触发条件**：
- 数据库已有数据
- 定期同步（如每 30 分钟）
- 应用恢复时检查数据新鲜度

**执行内容**：
- 只处理新增/修改/删除的资产
- 通过修改时间快速判断
- 避免全量对比

**优化策略**：
- 快速路径：比较资产数量、最后修改时间等元数据
- 如果元数据未变化，跳过全量对比
- 只对比有变化的资产

### 2. 同步时机

#### 2.1 自动同步

**应用启动时**：
- 延迟 2 秒执行，不阻塞 UI
- 检查数据新鲜度
- 决定全量或增量同步

**应用恢复时**：
- 检查数据新鲜度
- 如果过期，触发增量同步

**定期同步**：
- 后台任务定期执行
- 使用 WorkManager（Android）/ BGTaskScheduler（iOS）
- 默认间隔：30 分钟

#### 2.2 手动同步

**用户手动刷新**：
- 从 photo_manager 重新扫描
- 立即提供最新数据
- 后台同步到数据库

**设置页面触发**：
- 用户主动触发全量同步
- 显示同步进度
- 支持取消操作

### 3. 性能优化策略

#### 3.1 分批处理

- 每批处理 100 个资产，避免内存溢出
- 批量写入数据库，减少事务次数
- 支持进度回调，更新 UI

#### 3.2 快速路径优化

- 增量同步时，先比较元数据（资产数量、最后修改时间）
- 如果元数据未变化，跳过全量对比
- 只对比有变化的资产

#### 3.3 后台执行

- 同步在独立 Isolate 或后台线程执行
- 不阻塞 UI 线程
- 支持取消操作

## 数据源选择策略

### 1. 数据源类型

#### 1.1 数据库数据源

**优势**：
- 查询性能好（索引优化）
- 支持复杂筛选和排序
- 包含完整元数据（checksum、remoteAssetId 等）
- 支持分页查询

**适用场景**：
- 数据库已有完整数据
- 需要复杂查询和筛选
- 后续数据获取优化

#### 1.2 photo_manager 数据源

**优势**：
- 立即可用，无需等待同步
- 始终反映最新系统相册状态
- 直接访问 AssetEntity，支持立即加载图片

**适用场景**：
- 首次启动（数据库为空）
- 手动刷新（需要最新数据）
- 数据库不可用

#### 1.3 混合数据源（可选）

**策略**：
- 以 photo_manager 数据为准（最新系统相册状态）
- 补充数据库的元数据（checksum、remoteAssetId 等）

**适用场景**：
- 需要最新系统相册状态
- 同时需要数据库元数据
- 数据合并展示

### 2. 选择逻辑

#### 2.1 自动选择

**判断条件**：
- 数据库资产数量 > 阈值（建议 100 条）：使用数据库
- 数据库资产数量 ≤ 阈值：使用 photo_manager

**切换时机**：
- 同步完成后，如果数据库数据充足，自动切换到数据库
- 数据库不可用时，自动回退到 photo_manager

#### 2.2 手动切换

**用户控制**：
- 提供设置选项，允许用户选择数据源
- 支持手动刷新（强制使用 photo_manager）
- 支持强制使用数据库（如果可用）

### 3. 数据源切换流程

```
同步完成
    ↓
检查数据库数据充足性
    ├─→ 数据充足（> 阈值）
    │   └─→ 切换到数据库数据源
    │       └─→ 刷新 TimelineProvider
    │
    └─→ 数据不足（≤ 阈值）
        └─→ 保持 photo_manager 数据源
            └─→ 继续后台同步
```

## 上传状态标识方案

### 1. 标识机制

#### 1.1 双重标识策略

**显式关联标识（快速查询）**：
- 字段：`LocalAssetEntity.remoteAssetId`（可为空）
- 更新时机：上传成功后立即更新
- 优势：查询快速，无需计算 checksum
- 用途：快速判断是否已上传

**checksum 关联标识（兜底验证）**：
- 机制：通过 `checksum` 关联 `LocalAssetEntity` 和 `RemoteAssetEntity`
- 更新时机：后台定期验证和修复
- 优势：即使显式关联丢失，仍能通过 checksum 恢复
- 用途：数据一致性保障

#### 1.2 状态标识流程

```
上传任务创建
    ↓
标记为 "pending"（内存状态）
    ↓
开始上传
    ↓
标记为 "uploading"（内存状态 + 可选持久化）
    ↓
上传成功
    ├─→ 更新 LocalAssetEntity.remoteAssetId ✅
    ├─→ 标记为 "success"（内存状态）
    └─→ 刷新 UI 显示
    ↓
上传失败
    └─→ 标记为 "failed"（内存状态）
        └─→ 支持重试
```

### 2. 状态管理

#### 2.1 状态存储

**内存状态（实时状态）**：
- 使用 Riverpod StateNotifier 管理
- 实时更新 UI
- 应用重启后丢失

**持久化状态**：
- 通过 `LocalAssetEntity.remoteAssetId` 字段推断状态
- 上传任务表（可选实现）
- 应用重启后恢复状态

#### 2.2 状态查询

**已上传**：
- 判断：`LocalAssetEntity.remoteAssetId != null`
- 查询：通过 remoteAssetId 关联 RemoteAssetEntity

**未上传**：
- 判断：`LocalAssetEntity.remoteAssetId == null`
- 查询：检查上传任务状态（内存状态）

**上传中**：
- 判断：内存状态中查询
- 查询：上传任务状态表（可选）

### 3. 状态展示时机

#### 3.1 立即展示

**上传任务创建时**：
- 立即显示"上传中"状态
- 更新内存状态
- UI 自动响应

**上传成功时**：
- 立即更新为"已上传"状态
- 更新 `remoteAssetId` 字段
- 刷新 UI 显示

**上传失败时**：
- 立即显示"上传失败"状态
- 支持重试操作
- 显示错误信息

#### 3.2 状态同步

**状态更新机制**：
- 通过 Provider 监听状态变化
- UI 自动响应状态更新
- 支持手动刷新状态

**状态恢复**：
- 应用重启后，从数据库恢复状态
- 通过 `remoteAssetId` 推断上传状态
- 清理过期的内存状态

## 立即数据获取策略

### 1. 首次启动数据获取

#### 1.1 设计思路

- 应用启动后，照片页面立即从 photo_manager 读取
- 不等待数据库同步
- 后台同步在独立线程执行

#### 1.2 执行流程

```
应用启动
    ↓
照片页面加载
    ↓
检查数据库数据可用性
    ├─→ 数据库有数据（> 阈值）
    │   └─→ 从数据库读取 ✅（立即提供数据）
    │
    └─→ 数据库无数据或数据很少
        └─→ 从 photo_manager 读取 ✅（立即提供数据）
            └─→ 后台同步到数据库（不阻塞）
```

### 2. 数据源切换策略

#### 2.1 切换时机

**同步完成后（可选）**：
- 数据库已有完整数据
- 切换到数据库数据源
- 提升后续查询性能

**手动刷新**：
- 用户主动刷新
- 从 photo_manager 重新读取
- 立即提供最新数据

**数据过期检测**：
- 检查数据库最后同步时间
- 如果过期（如超过 1 小时），触发增量同步
- 同步期间仍使用数据库数据源

#### 2.2 切换策略

**平滑切换**：
- 同步完成后，刷新时间线数据，自动切换到数据库
- 用户无感知
- 提升后续性能

**用户可控**：
- 提供设置选项，允许用户选择数据源
- 支持手动刷新（强制使用 photo_manager）
- 支持强制使用数据库（如果可用）

**自动回退**：
- 数据库不可用时，自动回退到 photo_manager
- 确保功能可用性
- 后台修复数据库

### 3. 数据合并策略（可选）

#### 3.1 设计思路

- 以 photo_manager 数据为准（最新系统相册状态）
- 补充数据库的元数据（checksum、remoteAssetId 等）

#### 3.2 合并逻辑

```
1. 从 photo_manager 获取资产列表（最新状态）
   ↓
2. 从数据库获取元数据（checksum、remoteAssetId 等）
   ↓
3. 通过 ID 关联合并
   ├─→ photo_manager 资产 + 数据库元数据
   └─→ 创建完整的 LocalAsset 对象
   ↓
4. 提供合并后的数据
```

## 性能优化

### 1. 同步性能优化

#### 1.1 分批处理

- 每批处理 100 个资产，避免内存溢出
- 批量写入数据库，减少事务次数
- 支持进度回调，更新 UI

#### 1.2 快速路径优化

- 增量同步时，先比较元数据（资产数量、最后修改时间）
- 如果元数据未变化，跳过全量对比
- 只对比有变化的资产

#### 1.3 后台执行

- 同步在独立 Isolate 或后台线程执行
- 不阻塞 UI 线程
- 支持取消操作

### 2. 查询性能优化

#### 2.1 数据库查询优化

- 使用索引优化查询
- 支持分页查询，避免一次性加载大量数据
- 缓存查询结果（可选）

#### 2.2 数据源选择优化

- 优先使用数据库（性能更好）
- 数据库不可用时回退到 photo_manager
- 避免重复查询

### 3. 内存优化

#### 3.1 分批加载

- 时间线数据分批加载
- 使用分页查询
- 避免一次性加载所有数据

#### 3.2 资源释放

- 及时释放不需要的 AssetEntity
- 取消不需要的加载任务
- 清理过期的缓存

## 错误处理

### 1. 同步错误处理

#### 1.1 权限错误

**错误类型**：相册访问权限被拒绝

**处理策略**：
- 显示权限请求对话框
- 引导用户到设置页面授予权限
- 权限授予后自动重试同步

#### 1.2 数据库错误

**错误类型**：数据库写入失败、事务冲突等

**处理策略**：
- 记录错误信息
- 重试写入操作
- 如果持续失败，回退到 photo_manager 数据源

#### 1.3 系统相册错误

**错误类型**：photo_manager 访问失败、资产不存在等

**处理策略**：
- 记录错误信息
- 跳过错误的资产，继续处理其他资产
- 返回部分成功的结果

### 2. 数据源错误处理

#### 2.1 数据库不可用

**错误类型**：数据库连接失败、数据损坏等

**处理策略**：
- 自动回退到 photo_manager 数据源
- 记录错误信息
- 后台修复数据库

#### 2.2 photo_manager 不可用

**错误类型**：权限被拒绝、系统相册不可访问等

**处理策略**：
- 显示错误提示
- 引导用户授予权限
- 如果数据库有数据，使用数据库数据源

### 3. 状态同步错误

#### 3.1 状态不一致

**错误类型**：内存状态与数据库状态不一致

**处理策略**：
- 定期验证状态一致性
- 修复不一致的状态
- 通过 checksum 关联验证

#### 3.2 状态丢失

**错误类型**：应用重启后内存状态丢失

**处理策略**：
- 从数据库恢复状态
- 通过 `remoteAssetId` 推断上传状态
- 清理过期的内存状态

## 总结

本地媒体同步模块通过**双路径并行架构**和**智能数据源切换**，实现了即时数据获取和后台优化的平衡。核心特点包括：

1. **即时数据获取**：应用启动后立即提供媒体资源数据，无需等待同步
2. **后台同步**：同步在后台执行，不阻塞用户浏览
3. **智能切换**：根据数据可用性自动选择最优数据源
4. **状态可见**：清晰标识上传状态，支持实时更新
5. **性能优化**：优先使用数据库，必要时回退到直接扫描

该方案在用户体验和性能之间取得了良好的平衡，为后续功能扩展奠定了坚实基础。
