## 方案概述

### 设计目标

本备份方案旨在提供灵活、高效的媒体资源备份机制，支持两种备份模式：

1. **手动备份**：用户主动选择媒体资源，立即在后台执行，不受网络条件限制
2. **自动备份**：系统根据配置自动触发，支持多种筛选策略和条件检查

### 核心特性

- **双模式支持**：手动备份和自动备份完全独立，互不干扰
- **灵活筛选**：支持按相册、时间段、未备份资源等多种筛选策略
- **多用户支持**：每个用户拥有独立的备份配置和状态
- **增量同步**：基于时间戳的增量备份，减少网络传输
- **条件控制**：自动备份支持网络条件（WiFi）检查

### 与其他模块的关系

```
备份方案
    │
    ├─→ 数据库模块：存储备份配置和状态（backup_status 表）
    ├─→ 本地媒体同步模块：获取本地资产数据
    ├─→ 上传服务模块：执行实际上传任务
    └─→ 配置管理模块：读取全局备份配置（Store）
```

## 备份类型与触发机制

### 1. 手动备份

#### 1.1 触发方式

- **用户主动选择**：用户在 UI 中选择媒体资源（单个/批量/相册/时间段）
- **立即触发**：选择完成后立即在后台发起备份任务

#### 1.2 执行特点

- **不检查网络条件**：无论当前网络环境如何，都立即执行
- **高优先级**：手动备份任务优先级高于自动备份任务
- **不更新 lastBackupTime**：手动备份不影响增量同步的时间基准
- **独立执行**：不受自动备份配置影响

#### 1.3 使用场景

- 用户想要立即备份某些照片/视频
- 用户想要备份特定相册
- 用户想要备份某个时间段的媒体资源
- 用户想要强制备份（即使网络条件不满足自动备份要求）

### 2. 自动备份

#### 2.1 触发方式

- **系统定时触发**：通过 WorkManager（Android）或 BGTaskScheduler（iOS）定时触发
- **媒体库变化触发**：Android MediaObserver 检测到媒体库变化时触发
- **应用恢复触发**：应用从后台恢复时检查并触发

#### 2.2 执行条件

- **全局开关**：`autoBackup` 配置必须为 `true`
- **用户开关**：`backup_status.enabled` 必须为 `true`
- **网络条件**：如果 `backupRequireWifi = true`，则必须连接 WiFi
- **充电条件**（可选）：如果 `backupRequireCharging = true`，则必须正在充电

#### 2.3 筛选策略

自动备份支持三种筛选模式，通过 `backup_status.autoBackupMode` 配置：

**模式 A：`all_unbacked`（所有未备份）**
- 备份所有未备份的媒体资源
- 基于 `lastBackupTime` 进行增量筛选
- 排除 `backupSelection = excluded` 的相册中的资产

**模式 B：`selected_albums`（选中相册）**
- 仅备份 `backupSelection = selected` 的相册中的资产
- 可结合时间范围进一步筛选（如果配置了 `timeRangeStart` 和 `timeRangeEnd`）

**模式 C：`time_range`（时间段）**
- 仅备份指定时间范围内的媒体资源
- 基于 `timeRangeStart` 和 `timeRangeEnd` 筛选
- 排除 `backupSelection = excluded` 的相册中的资产

#### 2.4 触发频率控制

**频率限制**：
- **最小间隔**：两次自动备份之间至少间隔 5 分钟
- **节流机制**：使用节流（throttle）避免媒体库频繁变化导致的重复触发
- **去重检查**：同一批次的任务不重复创建

**实现方式**：
- 记录上次自动备份触发时间（`lastAutoBackupTriggerTime`）
- 触发前检查：`DateTime.now().difference(lastAutoBackupTriggerTime) >= Duration(minutes: 5)`
- 媒体库变化触发时，合并短时间内的多次变化（如 30 秒内的变化合并为一次触发）

## 备份配置设计

### 1. 全局备份配置（Store）

存储在 `Store` 中的全局配置，所有用户共享：

| 配置项 | 类型 | 说明 |
|--------|------|------|
| `autoBackup` | `bool` | 全局自动备份开关 |
| `backupRequireWifi` | `bool` | 自动备份是否仅 WiFi |
| `backupRequireCharging` | `bool` | 自动备份是否需充电（可选） |

**存储位置**：`lib/core/storage/store_key.dart`

### 2. 用户级备份状态（backup_status 表）

每个用户拥有独立的备份配置和状态：

| 字段 | 类型 | 说明 |
|------|------|------|
| `userId` | `String` | 用户 ID（主键） |
| `lastBackupTime` | `DateTime?` | 最后自动备份时间（用于增量同步） |
| `enabled` | `bool` | 该用户的自动备份是否启用 |
| `autoBackupMode` | `AutoBackupMode` | 自动备份模式枚举 |
| `timeRangeStart` | `DateTime?` | 时间段起始（time_range 模式） |
| `timeRangeEnd` | `DateTime?` | 时间段结束（time_range 模式） |

**AutoBackupMode 枚举值**：
- `all_unbacked`：备份所有未备份资源
- `selected_albums`：仅备份选中的相册
- `time_range`：仅备份指定时间段的资源

### 3. 相册级备份选择（LocalAlbumEntity）

每个相册的备份选择状态：

| 字段 | 类型 | 说明 |
|------|------|------|
| `backupSelection` | `BackupSelection` | 备份选择枚举 |

**BackupSelection 枚举值**：
- `none`：不参与自动备份（默认）
- `selected`：参与自动备份（selected_albums 模式）
- `excluded`：排除（手动备份仍可包含）

**存储位置**：`lib/data/database/tables/local_album_entity.dart`

### 4. 配置层级关系

```
全局配置（Store）
    │
    ├─→ 控制全局自动备份开关
    └─→ 控制网络/充电条件
         │
         └─→ 用户配置（backup_status 表）
              │
              ├─→ 控制该用户的自动备份开关
              ├─→ 控制该用户的备份模式
              └─→ 存储该用户的备份状态
                   │
                   └─→ 相册配置（LocalAlbumEntity）
                        │
                        └─→ 控制每个相册是否参与自动备份
```

## 备份候选资源筛选逻辑

### 1. 手动备份筛选

**流程**：
```
用户选择的资源
    ↓
可选去重检查（默认启用）
    ├─→ 批量检查服务器 checksum
    └─→ 过滤已存在的资产（可选）
    ↓
直接创建上传任务
    ├─→ 记录任务类型：manual
    ├─→ 记录 userId
    └─→ 设置优先级：high (priority = 1)
    ↓
不进行网络条件检查（立即执行）
    ↓
立即加入上传队列（高优先级）
```

**特点**：
- 用户明确指定资源，无需额外筛选
- **可选去重检查**：默认启用，避免重复上传（可通过配置关闭）
- 不检查网络条件、时间范围等
- 不检查相册的 `backupSelection` 状态
- 所有任务必须包含 `userId` 和 `taskType = manual`

### 2. 自动备份筛选

#### 2.1 模式 A：`all_unbacked`（所有未备份）

**筛选逻辑**：
```
1. 获取当前用户的 lastBackupTime
   - 如果为 null，则从 1970-01-01 开始
   
2. 查询 LocalAssetEntity
   - 条件：createdAt > lastBackupTime
   - 排除：属于 backupSelection = excluded 相册的资产
   
3. 去重检查
   - 批量调用服务器 API 检查 checksum
   - 过滤掉已存在的资产
   
4. 生成上传任务
```

**适用场景**：
- 首次备份后，定期备份新增资源
- 适合大多数用户的使用习惯

#### 2.2 模式 B：`selected_albums`（选中相册）

**筛选逻辑**：
```
1. 查询 LocalAlbumEntity
   - 条件：backupSelection = selected
   
2. 获取这些相册中的所有资产
   - 通过 AlbumAssetEntity 关联查询
   
3. 应用时间过滤（可选）
   - 如果配置了 timeRangeStart 和 timeRangeEnd
   - 筛选：createdAt >= timeRangeStart AND createdAt <= timeRangeEnd
   
4. 去重检查
   - 批量调用服务器 API 检查 checksum
   - 过滤掉已存在的资产
   
5. 生成上传任务
```

**适用场景**：
- 用户只想备份特定相册（如"相机"、"截图"等）
- 可以精确控制哪些相册参与自动备份

#### 2.3 模式 C：`time_range`（时间段）

**筛选逻辑**：
```
1. 获取配置的时间范围
   - timeRangeStart：起始时间（包含）
   - timeRangeEnd：结束时间（不包含，左闭右开区间）
   
2. 查询 LocalAssetEntity
   - 条件：createdAt >= timeRangeStart AND createdAt < timeRangeEnd
   - 排除：属于 backupSelection = excluded 相册的资产
   
3. 去重检查
   - 批量调用服务器 API 检查 checksum
   - 过滤掉已存在的资产
   
4. 生成上传任务
```

**边界处理规则**：
- 使用左闭右开区间：`[timeRangeStart, timeRangeEnd)`
- `timeRangeStart` 包含，`timeRangeEnd` 不包含
- 例如：`[2024-01-01 00:00:00, 2024-01-02 00:00:00)` 包含 1 月 1 日的所有资产，但不包含 1 月 2 日的资产

**适用场景**：
- 用户只想备份某个时间段的资源（如"最近一周"、"上个月"等）
- 适合定期清理和归档场景

### 3. 去重检查机制

所有自动备份模式都需要进行去重检查：

**检查流程**：
```
1. 收集候选资产的 checksum
   
2. 批量调用服务器 API
   - POST /api/v1/media/check_hashes
   - 传入 checksum 列表
   
3. 服务器返回已存在的 checksum 列表
   
4. 过滤掉已存在的资产
   
5. 剩余资产创建上传任务
```

**优化**：
- **分批检查**：每批最多 100 个 checksum，避免单次请求过大
- **本地缓存优先**：优先检查本地数据库（RemoteAssetEntity），减少服务器请求
- **降级策略**：批量检查失败时，回退到逐个检查或跳过去重（仅自动备份）
- **缓存有效期**：本地缓存有效期 24 小时，过期后重新检查服务器
- **超时控制**：批量检查超时时间 30 秒，超时后降级处理

## 备份执行流程

### 1. 手动备份流程

```
用户操作（选择资源）
    ↓
创建手动备份任务
    ├─→ 记录任务类型：manual
    ├─→ 记录用户选择的资源列表
    └─→ 设置优先级：high
    ↓
立即加入上传队列（高优先级）
    ↓
后台执行上传
    ├─→ 不检查网络条件
    ├─→ 不检查充电条件
    └─→ 直接执行上传
    ↓
更新任务状态
    ├─→ 成功：标记任务完成
    ├─→ 失败：记录错误信息，支持重试
    └─→ 不更新 lastBackupTime
```

**关键点**：
- 手动备份任务优先级高于自动备份任务
- 不更新 `lastBackupTime`，不影响增量同步
- 失败后可以手动重试

### 2. 自动备份流程

```
系统触发（定时/媒体变化/应用恢复）
    ↓
检查全局开关
    ├─→ autoBackup = false：结束
    └─→ autoBackup = true：继续
    ↓
检查用户开关
    ├─→ backup_status.enabled = false：结束
    └─→ backup_status.enabled = true：继续
    ↓
检查网络条件
    ├─→ backupRequireWifi = true 且非 WiFi：等待或跳过
    └─→ 条件满足：继续
    ↓
根据 autoBackupMode 筛选候选资源
    ├─→ all_unbacked：基于 lastBackupTime 筛选
    ├─→ selected_albums：基于相册选择筛选
    └─→ time_range：基于时间范围筛选
    ↓
去重检查（checksum）
    ├─→ 批量检查服务器
    └─→ 过滤已存在的资产
    ↓
创建上传任务（正常优先级）
    ↓
后台执行上传
    ↓
更新备份状态
    ├─→ 全部成功：更新 lastBackupTime = DateTime.now()
    ├─→ 全部失败：不更新 lastBackupTime，保留失败任务
    └─→ 部分成功：根据成功比例决定
        ├─→ 成功比例 ≥ 80%：更新 lastBackupTime，失败任务保留
        └─→ 成功比例 < 80%：不更新 lastBackupTime，失败任务保留
```

**关键点**：
- 自动备份需要满足所有条件才能执行
- **lastBackupTime 更新策略**（优化版）：
  - **全部成功**：立即更新 `lastBackupTime = DateTime.now()`
  - **部分成功**：
    - 成功比例 ≥ 80%：更新 `lastBackupTime`（避免少量失败阻塞增量同步）
    - 成功比例 < 80%：不更新 `lastBackupTime`（避免跳过大量失败任务）
  - **全部失败**：不更新 `lastBackupTime`
  - **边界情况处理**：
    - 考虑失败原因：网络错误等临时错误不影响更新决策，文件错误等永久错误需要更严格判断
    - 考虑任务重要性：关键资产（如用户手动选择的）失败时，降低成功比例阈值（如 ≥ 90%）
    - 用户可配置：提供成功比例阈值配置（默认 80%）
- 失败的任务保留在队列中，支持自动重试（最多 3 次，指数退避）
- 达到最大重试次数后标记为永久失败，不再自动重试

### 3. 任务优先级管理

**优先级规则**：
- **手动备份任务**：优先级 = 高（priority = 1）
- **自动备份任务**：优先级 = 正常（priority = 5）

**调度策略**：
- 上传队列按优先级排序
- 高优先级任务优先执行
- 同优先级任务按创建时间排序

## 关键设计要点

### 1. 手动备份与自动备份的区分

**核心原则**：
- **手动备份**：用户主导，立即执行，不更新 `lastBackupTime`
- **自动备份**：系统主导，条件执行，更新 `lastBackupTime`

**实现方式**：
- 上传任务记录任务类型（`taskType: manual | auto`）
- 手动备份任务不更新 `lastBackupTime`
- 自动备份任务成功后才更新 `lastBackupTime`

### 2. 多用户支持

**设计要点**：
- `backup_status` 表按 `userId` 隔离，每个用户独立的备份状态
- 用户切换时，读取对应用户的 `backup_status` 配置
- 全局配置（Store）所有用户共享，用户配置（backup_status）独立

**实现方式**：
- 查询 `backup_status` 时始终带上 `userId` 条件
- 更新 `lastBackupTime` 时使用 `userId` 作为主键

### 3. 增量同步机制

**设计要点**：
- `lastBackupTime` 仅由自动备份更新，手动备份不影响
- **三种自动备份模式的 lastBackupTime 使用**：
  - `all_unbacked` 模式：依赖 `lastBackupTime` 进行增量筛选（`createdAt > lastBackupTime`）
  - `selected_albums` 模式：不依赖 `lastBackupTime`，但更新它（用于模式切换）
  - `time_range` 模式：不依赖 `lastBackupTime`，但更新它（用于模式切换）
- **三种模式共享同一个 `lastBackupTime`**：
  - 设计考虑：共享同一个 `lastBackupTime` 便于模式切换时的数据一致性
  - 模式切换规则：
    - 从 `all_unbacked` 切换到其他模式：保留 `lastBackupTime`，新模式不依赖它
    - 从其他模式切换到 `all_unbacked`：使用当前 `lastBackupTime` 作为增量基准
    - 模式切换时，如果 `lastBackupTime` 为 null，则从 1970-01-01 开始

**实现方式**：
- 自动备份成功执行后，根据成功比例更新 `backup_status.lastBackupTime`
- `all_unbacked` 模式查询时使用 `createdAt > lastBackupTime` 条件
- `selected_albums` 和 `time_range` 模式不依赖 `lastBackupTime`，但成功后会更新它
- 手动备份任务不涉及 `lastBackupTime` 的更新

### 4. 优先级管理

**设计要点**：
- 手动备份任务优先级始终高于自动备份任务
- 确保用户主动操作能够及时执行
- 避免自动备份任务阻塞手动备份

**实现方式**：
- 上传任务表包含 `priority` 和 `taskType` 字段
- **优先级排序规则**（按顺序）：
  1. **任务类型优先**：`taskType = manual` 优先于 `taskType = auto`
  2. **优先级字段**：数字越小优先级越高（manual: 1, auto: 5）
  3. **文件类型**：图片优先于视频
  4. **文件大小**：小文件优先（可选配置）
  5. **创建时间**：早创建的任务优先
- 上传队列按上述规则排序执行

### 5. 网络条件检查

**设计要点**：
- 手动备份不检查网络条件，立即执行
- 自动备份根据 `backupRequireWifi` 配置检查网络条件
- 条件不满足时，自动备份等待或跳过本次执行

**实现方式**：
- 手动备份：跳过网络检查，直接执行
- 自动备份：检查 `backupRequireWifi` 配置
  - 如果 `backupRequireWifi = true` 且当前非 WiFi，等待或跳过
  - 如果 `backupRequireWifi = false`，不检查网络条件

### 6. 相册选择机制

**设计要点**：
- `backupSelection = selected` 的相册参与 `selected_albums` 模式的自动备份
- `backupSelection = excluded` 的相册不参与任何自动备份
- 手动备份不受相册选择限制

**实现方式**：
- `selected_albums` 模式：查询 `backupSelection = selected` 的相册
- `all_unbacked` 和 `time_range` 模式：排除 `backupSelection = excluded` 的相册
- 手动备份：不检查 `backupSelection`，直接包含用户选择的资源

### 7. 错误恢复机制

**设计要点**：
- 失败任务支持自动重试，避免临时错误导致永久失败
- 区分临时失败和永久失败，永久失败不再自动重试
- 提供用户友好的错误提示和手动重试选项

**实现方式**：
- **重试策略**：
  - 最大重试次数：3 次
  - 重试间隔：指数退避（1秒、2秒、4秒）
  - 可重试错误：网络错误、超时错误、5xx 服务器错误
  - 不可重试错误：认证错误、4xx 客户端错误、本地文件错误
- **任务状态管理**：
  - `pending`：待上传
  - `uploading`：上传中
  - `completed`：已完成
  - `failed`：失败（可重试）
  - `permanentlyFailed`：永久失败（达到最大重试次数）
  - `cancelled`：已取消
- **状态转换规则**：
  ```
  pending
    ├─→ uploading（开始上传）
    └─→ cancelled（用户取消）

  uploading
    ├─→ completed（上传成功）
    ├─→ failed（上传失败，可重试）
    ├─→ permanentlyFailed（达到最大重试次数）
    └─→ cancelled（用户取消）

  failed
    ├─→ uploading（重试）
    ├─→ permanentlyFailed（达到最大重试次数）
    └─→ cancelled（用户取消）

  permanentlyFailed
    └─→ uploading（用户手动重试）

  cancelled（终态）
  completed（终态）
  ```
- **状态转换验证**：
  - 状态转换前验证转换是否合法
  - 非法转换记录错误日志，不执行转换
  - 终态（`completed`、`cancelled`）不允许转换到其他状态
- **永久失败处理**：
  - 达到最大重试次数后标记为 `permanentlyFailed`
  - 不再自动重试，但支持用户手动重试
  - 记录详细错误信息，便于用户排查问题

### 8. 配置同步机制

**设计要点**：
- 全局配置（Store）和用户配置（backup_status 表）需要保持一致性
- 用户切换时及时加载对应用户的配置
- 配置变更时通知相关服务更新

**实现方式**：
- **配置加载时机**：
  - 应用启动时：加载全局配置和当前用户的备份配置
  - 用户切换时：卸载旧用户配置，加载新用户配置
  - 配置变更时：立即更新内存中的配置，持久化到存储
- **配置验证规则**：
  - **时间范围验证**（`time_range` 模式）：
    - `timeRangeStart` 和 `timeRangeEnd` 必须同时存在
    - `timeRangeStart` 不能晚于 `timeRangeEnd`
    - 时间范围不能超过 365 天
  - **相册选择验证**（`selected_albums` 模式）：
    - 至少需要选择一个相册（`backupSelection = selected`）
    - 验证选中的相册是否存在且有效
  - **模式切换验证**：
    - 切换模式时，验证新模式的配置是否完整
    - 配置不完整时，保留旧配置或使用默认配置
- **配置验证实现**：
  - 配置更新前进行验证
  - 验证失败时，返回错误信息，不更新配置
  - 加载配置时，如果配置无效，使用默认值或上次有效配置
- **配置迁移**：
  - 版本升级时自动迁移旧配置到新格式
  - 保持向后兼容，避免配置丢失

### 9. 相册删除场景处理

**设计要点**：
- 相册被删除后，相关的备份选择状态需要妥善处理
- 避免因相册删除导致的备份配置不一致

**处理策略**：
- **相册删除时**：
  - 检查该相册的 `backupSelection` 状态
  - 如果 `backupSelection = selected`，记录到日志（用于审计）
  - 相册删除后，`backupSelection` 状态自动失效
- **相册重新创建时**：
  - 如果用户重新创建同名相册，`backupSelection` 恢复为 `none`（默认值）
  - 不自动恢复之前的 `selected` 状态（避免误操作）
  - 用户需要重新选择相册参与备份
- **备份执行时**：
  - 查询 `backupSelection = selected` 的相册时，验证相册是否存在
  - 如果相册不存在，跳过该相册，记录警告日志
  - 不影响其他相册的备份执行

### 10. 备份状态通知策略

**设计要点**：
- 及时通知用户备份状态，提供良好的用户体验
- 避免通知过于频繁，打扰用户

**通知触发条件**：
- **手动备份**：
  - 全部完成：显示成功通知（可选，用户可配置）
  - 部分失败：显示失败通知，包含失败数量和原因
  - 全部失败：显示失败通知，包含详细错误信息
- **自动备份**：
  - 仅在失败时通知（成功时不通知，避免打扰）
  - 失败通知包含失败数量和原因
  - 达到最大重试次数后，显示永久失败通知

**通知聚合策略**：
- **单条通知**：手动备份任务，每条任务单独通知
- **汇总通知**：自动备份任务，同一批次的任务汇总为一条通知
- **通知内容**：
  - 成功：显示备份数量和耗时
  - 失败：显示失败数量和主要错误原因
  - 进度：显示当前进度百分比（可选，用户可配置）

**用户配置**：
- 提供通知偏好设置：
  - 手动备份成功通知：开启/关闭
  - 自动备份成功通知：开启/关闭（默认关闭）
  - 进度通知：开启/关闭（默认关闭）
  - 失败通知：始终显示（不可关闭）

## 用户认证与生命周期管理策略

### 1. 后台任务中的 Token 管理

#### 1.1 Token 获取与刷新策略

**设计原则**：
- 后台任务启动时预验证 Token 有效性
- Token 刷新失败时采用渐进式降级策略
- 使用分布式锁避免并发刷新导致的重复请求

**Token 获取流程**：
```
后台任务启动
    ↓
检查内存缓存中的 Token（有效期检查）
    ├─→ 有效：直接使用
    └─→ 无效/不存在：从 SecureStorage 读取
            ├─→ 存在且有效：更新缓存，使用
            └─→ 不存在/过期：触发刷新
                    ├─→ 刷新成功：更新缓存和存储，使用
                    └─→ 刷新失败：标记任务失败，记录错误
```

**Token 刷新策略**：
- **刷新时机**：Token 过期前 5 分钟或检测到过期
- **并发控制**：使用 `AsyncMutex` 确保同一 userId 的 Token 刷新操作互斥
- **失败处理**：
  - 刷新失败但任务未开始：标记任务为 `pending`，等待用户重新登录
  - 刷新失败且任务执行中：标记当前批次任务失败，停止后续任务
- **降级策略**：刷新失败后，记录错误日志，不立即中断所有任务，允许已完成的任务正常完成

#### 1.2 认证失败处理

**401 错误处理流程**：
```
检测到 401 错误
    ↓
尝试刷新 Token
    ├─→ 刷新成功：重试原请求（最多 1 次）
    │       ├─→ 重试成功：继续执行
    │       └─→ 重试失败：标记任务失败
    └─→ 刷新失败：标记认证失败
            ├─→ 自动备份任务：标记为 pending，等待用户重新登录
            └─→ 手动备份任务：立即失败，通知用户
```

**实现要点**：
- 在 `ApiService` 的拦截器中统一处理 401 错误
- 区分刷新 Token 接口的 401 错误（避免循环刷新）
- 认证失败时，记录到任务错误信息中，便于用户查看

### 2. 多用户场景下的生命周期管理

#### 2.1 用户切换时的任务处理

**处理策略**：
- **正在执行的任务**：
  - 手动备份任务：继续执行完成（用户已明确操作）
  - 自动备份任务：完成当前批次后停止，标记为暂停
- **待执行的任务**：
  - 立即切换任务队列到新用户
  - 旧用户的任务保留在数据库中，但不执行

**实现方式**：
- `BackupService` 维护当前活跃用户 ID
- 任务创建时检查当前用户是否匹配
- 用户切换时，`UploadService` 暂停旧用户的任务队列

#### 2.2 用户登出时的任务处理

**处理策略**：
- **手动备份任务**：
  - 执行中的任务：继续执行完成
  - 待执行的任务：标记为 `cancelled`，不自动恢复
  - 失败的任务：保留，允许用户重新登录后手动重试
- **自动备份任务**：
  - 所有任务标记为 `paused`
  - 用户重新登录后，根据备份配置决定是否恢复

**数据清理**：
- **不清理**：任务记录、备份状态、备份配置（保留用户数据）
- **清理**：Token、会话信息（安全考虑）

#### 2.3 用户删除场景

**处理策略**：
- 触发 `backup_status` 表的 CASCADE DELETE
- 该用户的所有备份任务标记为 `cancelled`
- 不立即删除任务记录，保留 30 天后自动清理（用于审计）

### 3. 应用生命周期管理

#### 3.1 应用启动时的状态恢复

**恢复流程**：
```
应用启动
    ↓
加载当前用户的备份配置
    ↓
检查是否有未完成的任务
    ├─→ 有：根据任务状态决定是否恢复
    │       ├─→ pending/failed（可重试）：自动恢复
    │       ├─→ uploading：标记为 failed，允许重试
    │       └─→ cancelled：不恢复
    └─→ 无：正常启动
```

**恢复策略**：
- 自动备份任务：根据 `backup_status.enabled` 决定是否自动恢复
- 手动备份任务：提示用户是否继续之前的备份

#### 3.2 应用被系统杀死时的状态保存

**状态保存机制**：
- **任务状态**：实时写入数据库，不需要额外保存
- **执行进度**：记录到任务表的 `progress` 字段
- **断点信息**：使用 `background_downloader` 的内置断点续传机制

**恢复机制**：
- 应用重启后，检查 `uploading` 状态的任务
- 标记为 `failed`，允许用户或系统重试
- 利用断点续传机制，从上次中断处继续

## 平台限制与适配策略

### 1. Android 后台限制处理

#### 1.1 电池优化检测与引导

**检测策略**：
- 应用启动时检测电池优化状态
- 自动备份启用时，检测是否忽略电池优化
- 未忽略时，引导用户手动关闭电池优化

**引导流程**：
```
检测到未忽略电池优化
    ↓
显示引导对话框
    ├─→ 用户选择"去设置"：跳转到电池优化设置页
    └─→ 用户选择"稍后"：记录状态，下次启动时再次提示
```

**实现方式**：
- 使用 `ignoreBatteryOptimizations` 权限
- 通过 `Settings.ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 跳转

#### 1.2 前台服务与通知策略

**策略选择**：
- **电池优化已忽略**：使用普通通知（Notification）
- **电池优化未忽略**：使用前台服务（Foreground Service）

**前台服务配置**：
- **服务类型**：`FOREGROUND_SERVICE_TYPE_DATA_SYNC`
- **通知重要性**：`IMPORTANCE_LOW`（不打扰用户）
- **通知内容**：显示当前备份进度和状态
- **启动条件**：仅在自动备份且电池优化未忽略时启动

#### 1.3 Doze 模式适配

**影响**：
- Doze 模式下，WorkManager 任务可能延迟执行
- 网络访问可能受限

**适配策略**：
- 使用 `setRequiredNetworkType(NetworkType.UNMETERED)` 确保 WiFi 连接
- 使用 `setRequiresBatteryNotLow(true)` 确保电量充足
- 任务执行时检查网络状态，必要时等待网络恢复

### 2. iOS 后台执行策略

#### 2.1 两种任务类型的分配策略

**BGAppRefreshTask（刷新任务）**：
- **用途**：快速同步和轻量级上传
- **执行时间**：约 20 秒
- **触发场景**：
  - 定期同步（每 15-30 分钟）
  - 媒体库变化通知后快速同步
- **执行内容**：
  - 同步本地媒体库（增量）
  - 同步远程资产列表
  - 上传少量小文件（< 5MB）

**BGProcessingTask（处理任务）**：
- **用途**：长时间上传任务
- **执行时间**：系统决定（通常几分钟）
- **触发场景**：
  - 有大量待上传任务
  - 上次刷新任务检测到待上传资产
- **执行内容**：
  - 执行完整的上传流程
  - 处理大文件上传
  - 批量上传任务

**分配逻辑**：
```
检查待上传任务
    ↓
判断任务数量和大小
    ├─→ 任务数 < 10 且总大小 < 50MB：使用 BGAppRefreshTask
    └─→ 任务数 ≥ 10 或总大小 ≥ 50MB：使用 BGProcessingTask
```

#### 2.2 expirationHandler 状态保存

**保存策略**：
- **保存粒度**：任务级（记录当前执行的任务 ID 和进度）
- **保存内容**：
  - 当前执行的任务 ID 列表
  - 每个任务的进度百分比
  - 任务状态快照
- **保存时机**：expirationHandler 触发时（系统终止前约 2 秒）

**恢复机制**：
- 下次任务启动时，检查是否有未完成的任务
- 从保存的进度继续执行（利用断点续传）

**实现要点**：
- 使用 `UserDefaults` 或数据库保存状态
- expirationHandler 中只做快速保存，不做耗时操作
- 保存操作使用同步 API，确保完成

#### 2.3 信号量同步机制

**问题**：iOS 系统可能同时触发多个后台任务

**解决方案**：
- 使用 `DispatchSemaphore` 确保同一时间只有一个任务执行
- 信号量值为 1（互斥锁）
- 任务开始时等待信号量，结束时释放

**实现要点**：
- 在任务入口处统一管理信号量
- 使用 `wait(timeout:)` 避免无限等待
- 任务异常退出时也要释放信号量（使用 defer 或 finally）

### 3. 网络状态管理

#### 3.1 网络状态监听

**监听机制**：
- **Android**：使用 `ConnectivityManager` 监听网络变化
- **iOS**：使用 `NWPathMonitor` 监听网络状态
- **Flutter**：使用 `connectivity_plus` 插件统一处理

**监听内容**：
- 网络类型（WiFi、移动数据、无网络）
- 网络是否计费（isExpensive）
- 网络是否可用

#### 3.2 网络状态变化时的任务处理

**WiFi 断开**：
- **自动备份任务**：
  - 如果 `backupRequireWifi = true`：立即暂停任务，等待 WiFi 恢复
  - 如果 `backupRequireWifi = false`：继续执行（使用移动数据）
- **手动备份任务**：继续执行（用户明确操作）

**移动数据切换为 WiFi**：
- 自动恢复暂停的任务（如果因 WiFi 要求而暂停）

**无网络**：
- 所有任务暂停，等待网络恢复
- 网络恢复后，自动恢复暂停的任务

#### 3.3 流量限制处理

**检测机制**：
- 检测网络是否计费（isExpensive）
- 检测当前使用的网络类型

**处理策略**：
- **自动备份**：
  - 如果 `backupRequireWifi = true` 且当前为计费网络：暂停任务
  - 如果 `backupRequireWifi = false`：允许使用移动数据（但可配置上限）
- **手动备份**：允许使用移动数据，但提示用户

**流量上限配置**（可选）：
- 允许用户配置移动数据上传的上限（如每月 1GB）
- 达到上限后，仅允许 WiFi 上传

## 数据一致性保证机制

### 1. 事务边界设计

#### 1.1 lastBackupTime 更新的事务边界

**更新时机**：
- 仅在自动备份任务全部完成或成功比例 ≥ 80% 时更新
- 使用数据库事务确保原子性

**事务边界**：
```dart
// 伪代码示例
await database.transaction(() async {
  // 1. 更新所有成功的任务状态为 completed
  await updateTaskStatuses(successTaskIds, TaskStatus.completed);
  
  // 2. 计算成功比例
  final successRatio = successCount / totalCount;
  
  // 3. 如果满足条件，更新 lastBackupTime
  if (successRatio >= 0.8 || successCount == totalCount) {
    await updateLastBackupTime(userId, DateTime.now());
  }
  
  // 4. 更新失败任务状态
  await updateTaskStatuses(failedTaskIds, TaskStatus.failed);
});
```

**关键点**：
- 整个更新过程在一个事务中完成
- 如果任何步骤失败，整个事务回滚
- 确保任务状态和 lastBackupTime 的一致性

#### 1.2 任务状态更新的原子性

**更新场景**：
- 任务创建：创建任务记录
- 任务开始：更新状态为 `uploading`，记录开始时间
- 任务完成：更新状态为 `completed`，记录完成时间
- 任务失败：更新状态为 `failed`，记录错误信息

**原子性保证**：
- 每次状态更新都在事务中完成
- 使用数据库的 `UPDATE ... WHERE` 确保条件更新
- 状态转换验证：确保状态转换合法（如不能从 `completed` 转为 `uploading`）

### 2. 并发冲突检测与处理

#### 2.1 冲突检测机制

**检测时机**：
- **任务创建时**：检查是否已存在相同资产的任务
- **任务执行前**：二次验证任务是否仍然有效

**冲突判定标准**：
- **主要标准**：`assetId`（资产 ID）
- **辅助标准**：`checksum`（文件哈希值）
- **优先级**：`assetId` 优先，`checksum` 用于辅助判断

**检测流程**：
```
创建新任务
    ↓
查询数据库中是否存在相同 assetId 的任务
    ├─→ 存在且状态为 pending/uploading：冲突
    │       ├─→ 相同 taskType：跳过新任务（避免重复）
    │       └─→ 不同 taskType：根据优先级处理
    │               ├─→ manual > auto：取消旧任务，创建新任务
    │               └─→ auto > manual：跳过新任务（手动任务优先级高）
    └─→ 不存在或状态为 completed/failed/cancelled：无冲突，创建任务
```

#### 2.2 冲突解决策略

**策略选择**：
- **优先级覆盖**：高优先级任务覆盖低优先级任务
  - `manual` 任务覆盖 `auto` 任务
  - `priority` 值小的任务覆盖 `priority` 值大的任务
  - 覆盖时，取消旧任务（状态改为 `cancelled`），创建新任务
- **跳过策略**：如果已存在相同资产的任务且任务类型相同，跳过新任务
- **边界情况处理**：
  - **文件被移动或重命名**：通过 `checksum` 辅助判断，如果 `checksum` 相同，视为同一资产
  - **文件被删除**：任务执行时检测到文件不存在，标记为 `permanentlyFailed`
  - **资产 ID 变化**：如果 `assetId` 变化但 `checksum` 相同，视为冲突，按优先级处理

**实现要点**：
- 冲突检测在 `UploadOrchestrator` 的任务创建阶段完成
- 使用数据库的唯一索引或查询确保检测的准确性
- 冲突解决后，记录日志便于追踪
- 冲突解决时，使用数据库事务确保原子性

### 3. 去重检查的一致性保证

#### 3.1 去重检查结果的有效期

**有效期策略**：
- **本地缓存**：24 小时有效
- **服务器检查结果**：立即使用，不缓存（服务器状态实时变化）

**时间窗口问题**：
- **问题**：去重检查完成后到任务创建之间，服务器状态可能已变化
- **解决方案**：
  - 上传前二次验证（可选，用于手动备份）
  - 上传失败时，如果是"文件已存在"错误，更新本地缓存

#### 3.2 去重检查与任务创建的原子性

**当前设计**：
- 去重检查是独立阶段，与任务创建分离
- 不要求严格的原子性（允许时间窗口）

**优化方案**（可选）：
- 对于手动备份，支持上传前二次验证
- 二次验证失败时，标记任务为"已存在"，不实际上传
- 减少不必要的网络传输

#### 3.3 去重缓存的更新时机

**更新时机**：
- **检查时**：批量检查结果更新到本地缓存
- **上传成功后**：将新上传的资产添加到本地缓存
- **上传失败（已存在）**：更新本地缓存（服务器返回文件已存在）

**缓存失效**：
- 时间过期：24 小时后失效
- 用户手动清除：提供清除缓存的功能
- 用户登出：清除对应用户的缓存

### 1. 数据库表设计

**创建 backup_status 表**：

- 在 `lib/data/database/tables/` 目录下创建 `backup_status_entity.dart`
- 定义表结构和字段
- 在 `app_database.dart` 中注册表
- 创建数据库迁移脚本

**关键字段**：
- `userId`：主键，外键关联 `UserEntity`
- `lastBackupTime`：最后自动备份时间
- `enabled`：用户自动备份开关
- `autoBackupMode`：自动备份模式枚举

### 2. 服务层设计

**职责划分**：

**BackupService（备份服务）**：
- **职责**：备份功能的入口和协调
- **方法**：
  - `startManualBackup(String userId, List<String> assetIds, {bool skipDeduplication = false})`：启动手动备份
  - `startAutoBackup(String userId)`：启动自动备份（需要 userId）
  - `getBackupStatus(String userId)`：获取用户备份状态
  - `updateBackupConfig(String userId, BackupConfig config)`：更新备份配置
  - `retryFailedTask(String userId, String taskId)`：手动重试失败任务
- **依赖**：BackupCandidateSelector、UploadOrchestrator

**BackupCandidateSelector（候选资源筛选器）**：
- **职责**：根据备份模式筛选候选资源（不涉及去重和任务创建）
- **方法**：
  - `selectAllUnbacked(String userId)`：筛选所有未备份资源
  - `selectSelectedAlbums(String userId, DateTime? start, DateTime? end)`：筛选选中相册资源
  - `selectTimeRange(String userId, DateTime start, DateTime end)`：筛选时间段资源
- **返回**：候选资源列表（`List<LocalAssetEntity>`）
- **不负责**：去重检查、任务创建、上传执行

**UploadOrchestrator（上传编排器）**：
- **职责**：上传任务的编排和执行协调（去重、优先级、并发控制）
- **方法**：
  - `orchestrateManualUpload(String userId, List<String> assetIds, {bool skipDeduplication = false})`：编排手动上传
  - `orchestrateAutoUpload(String userId, List<LocalAssetEntity> candidates)`：编排自动上传（需要 userId）
  - `filterUploadedAssets(String userId, List<LocalAssetEntity> assets)`：去重过滤（批量检查 checksum）
- **负责**：去重检查、任务创建、优先级管理、并发控制、冲突检测
- **不负责**：候选资源筛选（由 BackupCandidateSelector 负责）

**职责边界**：
- BackupCandidateSelector：负责筛选逻辑，返回候选资源
- UploadOrchestrator：负责去重和任务编排，接收候选资源
- BackupService：负责协调两者，提供统一接口

### 3. 配置管理

**全局配置（Store）**：
- 复用现有的 `StoreKey.autoBackup`
- 复用现有的 `StoreKey.backupRequireWifi`
- 添加 `StoreKey.backupRequireCharging`（可选）

**用户配置（backup_status 表）**：
- 创建 `BackupStatusDao` 提供数据访问接口
- 提供配置读取和更新方法
- 支持用户切换时的配置加载

**相册配置（LocalAlbumEntity）**：
- 复用现有的 `backupSelection` 字段
- 提供相册选择状态的更新接口

### 4. 触发机制实现

**手动备份触发**：
- UI 层：用户选择资源后调用 `BackupService.startManualBackup()`
- 立即创建上传任务，加入队列

**自动备份触发**：
- 系统定时：通过 WorkManager/BGTaskScheduler 定时触发
- 媒体变化：Android MediaObserver 检测到变化时触发
- 应用恢复：应用从后台恢复时检查并触发

### 5. 优先级实现

**上传任务表设计**：
- `upload_tasks` 表必须包含以下字段：
  - `id`：任务 ID（主键）
  - `userId`：用户 ID（外键，用于多用户隔离）
  - `assetId`：资产 ID
  - `taskType`：任务类型（`manual` 或 `auto`）
  - `priority`：优先级（数字越小优先级越高）
  - `status`：任务状态
  - `retryCount`：重试次数
  - `maxRetries`：最大重试次数（默认 3）
  - `createdAt`：创建时间
  - 其他字段...
- 手动备份任务：`taskType = manual`，`priority = 1`
- 自动备份任务：`taskType = auto`，`priority = 5`

**队列调度**：
- 上传队列按以下规则排序：
  1. 任务类型：`manual` 优先于 `auto`
  2. 优先级字段：升序排序
  3. 文件类型：图片优先于视频
  4. 创建时间：升序排序
- 查询任务时始终带上 `userId` 条件，确保多用户隔离

## 总结

### 方案特点

本备份方案提供了灵活、高效的媒体资源备份机制，具有以下特点：

1. **双模式支持**：手动备份和自动备份完全独立，满足不同使用场景
2. **灵活筛选**：支持三种自动备份模式，满足不同用户需求
3. **多用户支持**：每个用户拥有独立的备份配置和状态
4. **增量同步**：基于时间戳的增量备份，减少网络传输
5. **条件控制**：自动备份支持网络条件检查，节省流量

### 核心原则

- **手动备份**：用户主导，立即执行，不检查条件
- **自动备份**：系统主导，条件执行，更新状态
- **配置分离**：全局配置 + 用户配置 + 相册配置
- **状态隔离**：每个用户独立的备份状态

### 实施优先级

1. **第一阶段**：实现基础架构（数据库表、服务接口）
2. **第二阶段**：实现手动备份功能
3. **第三阶段**：实现自动备份功能（`all_unbacked` 模式）
4. **第四阶段**：实现其他自动备份模式（`selected_albums`、`time_range`）
