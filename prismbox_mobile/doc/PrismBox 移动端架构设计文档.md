## 架构概述

### 1.1 项目背景与目标

PrismBox 是一个全新的高性能相册应用，旨在提供卓越的用户体验和高效的资源管理。核心目标包括：

1. **高性能、高效率且体验良好的备份上传和下载**
   - 支持后台自动备份，不影响用户正常使用
   - 智能上传队列管理，支持断点续传
   - 高效的网络资源利用
   - 优雅的错误处理和重试机制

2. **高性能的媒体资源展示**
   - 流畅的图片/视频浏览体验
   - 快速加载，减少用户等待时间
   - 智能缓存策略，优化内存和存储使用
   - 渐进式加载，提供即时视觉反馈

### 1.3 核心特点

- **分层架构**：清晰的层次划分（UI 层、服务层、数据层、网络层）
- **模块化设计**：功能模块独立，低耦合高内聚
- **渐进式加载**：占位符 → 缩略图 → 预览图 → 原图
- **智能资源选择**：根据本地/远程资源可用性和用户偏好自动选择
- **多级缓存体系**：内存缓存 + 磁盘缓存，大图小图分离管理
- **隔离性**：后台任务运行在独立 Engine 中，不影响主应用
- **类型安全**：使用 Pigeon 进行跨平台通信，编译时类型检查

### 1.4 技术选型

#### Flutter 侧
- **框架**：Flutter 3.x+
- **状态管理**：Riverpod 2.x
- **路由**：AutoRoute
- **数据库**：Drift (SQLite)
- **网络**：http、background_downloader、cancellation_token_http
- **本地资源**：photo_manager
- **缓存**：flutter_cache_manager
- **跨平台通信**：Pigeon

#### Android 侧
- **后台任务**：WorkManager
- **网络**：HttpsURLConnection、SSLContext
- **存储**：Keystore（Token 存储）

#### iOS 侧
- **后台任务**：BGTaskScheduler
- **网络**：URLSession、Security Framework
- **存储**：Keychain（Token 存储）

## 分层架构设计

### 2.1 UI 层（Presentation Layer）

#### 2.1.1 职责
- 用户界面展示和交互
- 状态管理和 UI 状态更新
- 用户输入处理和事件响应

#### 2.1.2 设计要点

**页面结构**：
- **TabShell 容器**：单导航容器架构，管理四个核心标签页
  - 照片页面（时间线视图）
  - 搜索页面（多维度智能搜索）
  - 相册页面（管理远程相册集合）
  - 资料库页面（快速访问收藏和集合）
- **查看器页面**：全屏查看照片和视频，支持左右滑动和双指缩放
- **功能页面**：设置、备份管理、相册详情等

**状态管理**：
- 使用 Riverpod 进行状态管理
- Provider 分层：
  - **基础设施 Provider**：数据库、API、服务注入
  - **业务 Provider**：认证、媒体、相册、备份等
  - **UI Provider**：页面级状态管理

**响应式设计**：
- 自动适配竖屏/横屏
- 底部导航栏（竖屏）/ 侧边导航栏（横屏）
- 流畅的过渡动画（600ms 淡入淡出）

### 2.2 服务层（Service Layer）

#### 2.2.1 职责
- 业务逻辑封装和编排
- 跨模块协调
- 复杂业务流程管理

#### 2.2.2 核心服务

**BackupService（备份服务）**：
- 自动备份调度和管理
- 上传队列管理
- 任务状态跟踪
- 错误处理和重试

**MediaLoadService（媒体加载服务）**：
- 资源选择策略
- 分级加载管理
- 缓存协调
- 加载任务取消

**SyncService（同步服务）**：
- 本地媒体库同步
- 远程数据同步
- 增量同步策略
- 冲突处理

**ApiService（API 服务）**：
- 统一 API 客户端管理
- 认证头注入
- 端点发现和配置
- 错误处理和重试

#### 2.2.3 设计模式

- **门面模式**：Service 作为业务功能的统一入口
- **策略模式**：资源选择、加载策略可配置
- **观察者模式**：任务进度、状态变更通知

### 2.3 仓库层（Repository Layer）

#### 2.3.1 职责
- 数据访问抽象
- 本地和远程数据源统一接口
- 数据转换和映射

#### 2.3.2 设计要点

**接口定义**：
```dart
// 示例：媒体仓库接口
abstract class MediaRepository {
  Future<List<MediaEntity>> getLocalMedia();
  Future<List<MediaEntity>> getRemoteMedia();
  Future<MediaEntity?> getMediaById(String id);
  Future<void> syncMedia();
}
```

**实现分离**：
- **本地数据源**：通过 Drift 访问 SQLite
- **远程数据源**：通过 ApiService 访问服务器
- **缓存数据源**：通过 CacheManager 访问缓存

**数据转换**：
- Entity ↔ Model ↔ DTO 转换
- 本地数据 ↔ 远程数据关联

### 2.4 数据层（Data Layer）

#### 2.4.1 数据库设计

**数据库选择**：Drift (SQLite)

**表设计原则**：
- 所有表使用业务主键（String），不使用自增 ID
- 启用 STRICT 模式，确保类型安全
- 使用 WITHOUT ROWID，提升查询性能
- 本地与远程数据分离存储

**核心表结构**：
- `local_asset_entity`：本地资产表
- `remote_asset_entity`：远程资产表
- `local_album_entity`：本地相册表
- `remote_album_entity`：远程相册表
- `album_asset_entity`：相册-资产关联表

**关系设计**：
- 完整的外键约束
- 合理的删除策略（CASCADE/SET NULL）
- 使用复合主键表示多对多关系

**索引策略**：
- 为常用查询字段创建索引
- 使用复合索引优化多字段查询
- 使用条件索引优化特定场景

#### 2.4.2 缓存设计

**内存缓存**：
- **三级缓存池**：
  - ThumbHash 缓存（临时存储）
  - 小图缓存（缩略图，数量大）
  - 大图缓存（完整图，最多 5 张）
- **LRU 淘汰策略**：超出容量时淘汰最久未使用的

**磁盘缓存**：
- **缩略图缓存**：5000 个对象，30 天过期
- **远程图片缓存**：500 个对象，30 天过期
- **缓存分离**：大图小图使用不同缓存池

### 2.5 网络层（Network Layer）

#### 2.5.1 职责
- HTTP/HTTPS 请求处理
- SSL/TLS 证书管理
- 连接池和连接复用
- 请求重试和错误处理

#### 2.5.2 设计要点

**统一认证机制**：
- Token 认证，自动注入请求头
- Token 存储在平台安全存储（Keychain/Keystore）
- 401 错误自动跳转登录

**灵活协议支持**：
- 支持 HTTP/HTTPS
- 支持自签名证书（开发/内网场景）
- 支持客户端证书（双向 TLS）

**智能端点发现**：
- 优先尝试 `/.well-known/immich` 发现端点
- 使用 `pingServer()` 验证端点可用性
- 支持端点切换（本地/远程）

### 3.1 备份上传下载模块

#### 3.1.1 架构设计

**后台任务架构**：
- 使用独立 Flutter Engine 运行后台任务
- Android 使用 WorkManager，iOS 使用 BGTaskScheduler

- 任务完成后必须清理资源，防止内存泄漏

#### 3.1.2 上传队列管理

**并发控制**：
- 最大并发：6 个任务
- 每个服务器最大并发：6
- 每个组最大并发：3

**任务优先级**：
- 图片优先于视频
- 小文件优先（可选）
- 按创建时间排序

**断点续传**：
- 使用 background_downloader 管理上传任务
- 支持任务暂停和恢复
- 大文件（>256MB）在 Android 上使用前台服务

#### 3.1.3 网络优化

**连接管理**：
- 连接复用，减少连接建立开销
- 最大 16 个并发 HTTP 连接
- 使用连接池复用连接

**智能重试机制**：
- 指数退避策略
- 网络失败自动重试（默认 3 次）
- 网络状态检测，WiFi 优先上传

**自定义请求头**：
- 支持自定义请求头（适配企业环境）
- 自动注入认证头

#### 3.1.4 数据同步机制

**增量同步**：
- 只同步上次备份后的新资产
- 使用文件哈希（checksum）进行去重
- 批量检查已存在资产，减少 API 调用

**本地同步**：
- 扫描设备媒体库，更新本地数据库
- 识别新增、修改、删除的资产
- 使用 photo_manager 访问本地资源

**远程同步**：
- 从服务器获取已上传资产列表
- 更新本地数据库中的远程资产信息
- 支持多用户场景

#### 3.1.5 错误处理与恢复

**统一错误类型**：
- 网络错误
- 认证错误
- 服务器错误
- 本地错误

**自动恢复机制**：
- 任务状态持久化，支持恢复
- 网络失败自动重试
- 友好的错误提示和手动重试机制

#### 3.2.2 智能资源选择

**选择策略**：
1. 检查本地资源可用性
2. 尊重用户偏好（本地优先或远程优先）
3. 自动选择最优资源提供者

**实现要点**：
- 优先使用本地资源（速度快、不耗流量）
- 本地资源不可用时回退到远程资源
- 支持用户手动切换

#### 3.2.3 多级缓存体系

**内存缓存**：
- **三级缓存池**：
  - ThumbHash 缓存：临时存储，不长期保留
  - 小图缓存：缩略图，数量大但占内存小
  - 大图缓存：完整图，最多 5 张，避免内存溢出
- **LRU 淘汰策略**：超出容量时淘汰最久未使用的

**磁盘缓存**：
- **缩略图缓存**：5000 个对象，30 天过期
- **远程图片缓存**：500 个对象，30 天过期
- **缓存分离**：大图小图使用不同缓存池，防止大图驱逐小图

#### 3.2.4 占位符优化

**ThumbHash 优先**：
- 体积小（通常 < 100 字节）
- 解码快（毫秒级）
- 视觉效果好（保留原图色彩和结构）

**渐变占位符**：
- 无 ThumbHash 时使用渐变占位符
- 基于图片主色调生成
- 100ms 淡入动画，平滑过渡

#### 3.2.5 加载优化策略

**可取消加载**：
- 支持加载任务取消
- 组件销毁时自动取消相关加载
- 避免加载已不需要的资源

**预加载策略**：
- 预加载相邻图片
- 可见性检测，仅加载可见区域
- 离开视口时取消加载

**流式加载**：
- 边下载边解码，提升感知速度
- 支持进度事件，UI 可显示加载进度

### 3.3 API 对接模块

#### 3.3.1 统一认证机制

**自定义请求头**：

#### 3.3.2 灵活协议支持

**HTTP/HTTPS 支持**：
- 支持 HTTP/HTTPS
- 支持自签名证书（开发/内网场景）
- 支持客户端证书（双向 TLS）

**SSL 配置管理**：
- HttpSSLOptions 管理 SSL 配置
- 支持证书链验证
- 支持证书固定（Certificate Pinning）

#### 3.3.3 智能端点发现

**端点配置**：
- 支持多个服务器配置

#### 3.3.4 完善错误处理

**统一异常处理**：
- ApiException 统一异常类型

**重试机制**：
- 自动重试拦截器（网络错误和 5xx 错误）

## 性能优化方案

### 4.1 上传下载性能优化

#### 4.1.1 并发控制

**并发策略**：
- 最大并发：6 个任务
- 每个服务器最大并发：6
- 每个组最大并发：3

**优先级管理**：
- 图片优先于视频
- 小文件优先（可选）
- 按创建时间排序

#### 4.1.2 内存优化

**流式上传**：
- 大文件使用流式上传
- 不将整个文件加载到内存
- 上传完成后立即释放文件句柄

**资源管理**：
- 任务完成后立即清理资源
- 使用弱引用避免内存泄漏
- 定期检查资源使用情况

#### 4.1.3 网络优化

**连接复用**：
- 使用连接池复用连接
- 减少连接建立开销
- 最大 16 个并发 HTTP 连接

**智能重试**：
- 指数退避策略
- 网络状态检测
- WiFi 优先上传

### 4.2 媒体展示性能优化

#### 4.2.1 加载优化

**并发控制**：
- 最大 16 个并发 HTTP 连接
- 使用连接池复用连接
- 优先使用缓存

**预加载策略**：
- 预加载相邻图片
- 可见性检测，仅加载可见区域
- 离开视口时取消加载

#### 4.2.2 内存优化

**缓存限制**：
- 大图缓存限制严格（最多 5 张）
- 小图缓存更宽松
- 及时清理不再使用的图片

**图片解码**：
- 异步解码，不阻塞 UI 线程
- 加载适配设备分辨率的图片
- 使用硬件加速动画

#### 4.2.3 渲染优化

**异步处理**：
- 异步解码图片
- 不阻塞 UI 线程
- 使用 Isolate 处理复杂计算

**硬件加速**：
- 使用硬件加速动画
- 优化图片渲染流程
- 减少不必要的重绘

### 4.3 数据库性能优化

#### 4.3.1 查询优化

**索引策略**：
- 为常用查询字段创建索引
- 使用复合索引优化多字段查询
- 使用条件索引优化特定场景

**查询优化**：
- 避免全表扫描
- 使用 LIMIT 限制结果集
- 使用 JOIN 优化关联查询

#### 4.3.2 写入优化

**批量操作**：
- 使用事务批量写入
- 减少数据库锁定时间
- 优化写入顺序

**WAL 模式**：
- 使用 WAL 模式提升并发性能
- 减少写入冲突
- 提升查询性能

## 关键技术决策

### 6.1 状态管理：Riverpod vs Provider

**决策**：选择 Riverpod 2.x

**理由**：
- **编译时安全**：Riverpod 提供编译时类型检查，减少运行时错误
- **更好的性能**：自动优化重建范围，减少不必要的重建
- **依赖注入**：内置依赖注入机制，简化依赖管理
- **代码生成**：支持代码生成，减少样板代码
- **测试友好**：易于测试和模拟

**权衡**：
- 学习曲线相对较陡
- 需要配置代码生成

### 6.2 数据库：Drift vs Isar

**决策**：选择 Drift (SQLite)

**理由**：
- **成熟稳定**：基于 SQLite，成熟稳定
- **类型安全**：编译时类型检查，减少错误
- **迁移支持**：完善的迁移机制
- **跨平台**：支持所有 Flutter 平台
- **性能优秀**：SQLite 性能优秀，支持复杂查询

**权衡**：
- 需要编写 SQL 查询（但 Drift 提供了类型安全的 API）
- 相比 NoSQL 数据库，灵活性稍低

### 6.3 后台任务：独立 Engine vs Isolate

**决策**：选择独立 Flutter Engine

**理由**：
- **完全隔离**：独立 Engine 提供完全的内存和生命周期隔离
- **平台集成**：更好地与平台原生后台任务系统集成
- **资源管理**：更精确的资源管理和清理
- **类型安全**：使用 Pigeon 提供类型安全的跨平台通信

**权衡**：
- 实现复杂度较高
- 需要管理多个 Engine 实例
- 内存占用相对较大

### 6.4 图片缓存：自定义 vs 第三方库

**决策**：自定义 CustomImageCache + flutter_cache_manager

**理由**：
- **精细控制**：可以精确控制缓存策略和行为
- **性能优化**：可以针对特定场景优化
- **大图小图分离**：实现大图小图分离缓存，避免相互干扰
- **灵活扩展**：易于扩展和定制

**权衡**：
- 需要自己实现和维护
- 开发工作量较大

### 6.5 网络库：Dio vs http

**决策**：Dio + background_downloader

**理由**：
- **功能丰富**：Dio 提供拦截器、请求取消、文件上传等功能
- **后台下载**：background_downloader 专门处理后台下载任务
- **SSL 支持**：完善的 SSL/TLS 支持
- **错误处理**：完善的错误处理和重试机制

**权衡**：
- 需要学习两个库的 API
- 配置相对复杂

### 6.6 路由：AutoRoute vs GoRouter

**决策**：选择 AutoRoute

**理由**：
- **代码生成**：自动生成路由代码，减少错误
- **类型安全**：编译时类型检查
- **嵌套路由**：支持复杂的嵌套路由结构
- **守卫支持**：完善的路由守卫机制
- **深度链接**：支持深度链接

**权衡**：
- 需要配置代码生成
- 学习曲线相对较陡

### 6.7 跨平台通信：Pigeon vs MethodChannel

**决策**：选择 Pigeon

**理由**：
- **类型安全**：编译时类型检查，减少运行时错误
- **代码生成**：自动生成 Dart、Swift、Kotlin 代码
- **IDE 支持**：完整的类型提示和自动补全
- **文档化**：接口定义即文档

**权衡**：
- 需要定义 Pigeon 接口文件
- 需要配置代码生成

### 核心设计理念

PrismBox 移动端架构遵循以下核心设计理念：

1. **性能优先**：所有设计决策优先考虑性能影响，确保流畅的用户体验
2. **渐进式加载**：占位符 → 缩略图 → 预览图 → 原图，提供即时视觉反馈
3. **智能资源选择**：根据本地/远程资源可用性和用户偏好自动选择最优资源
4. **隔离性**：后台任务运行在独立 Engine 中，不影响主应用性能
5. **类型安全**：使用 Pigeon、Drift、Riverpod 等工具提供编译时类型检查
6. **可扩展性**：模块化设计，支持功能扩展和性能优化

### 技术亮点

- **独立 Engine 架构**：后台任务完全隔离，不影响主应用
- **三级内存缓存**：ThumbHash、小图、大图分离缓存，避免相互干扰

**目录结构说明：**

1. **core/**：核心基础设施，包括依赖注入、缓存管理、存储服务等
2. **data/**：数据层，包含数据库定义和数据源实现
3. **domain/**：领域层，定义业务实体和仓库接口
4. **infrastructure/**：基础设施层，实现仓库、API客户端、网络层
5. **services/**：服务层，封装业务逻辑，按功能模块组织
6. **features/**：功能模块，独立的功能单元，包含完整的实现
7. **providers/**：Riverpod Providers，按层次组织
8. **presentation/**：展示层，包含路由、页面和组件
9. **utils/**：工具类和扩展方法
10. **config/**：应用配置

**设计原则：**

- **清晰分层**：严格遵循分层架构，各层职责明确
- **模块化**：功能模块独立，低耦合高内聚
- **可扩展性**：易于添加新功能和模块
- **类型安全**：充分利用 Dart 的类型系统

### D. 性能指标目标

#### 上传下载性能
- **上传速度**：WiFi 环境下 > 10MB/s
- **下载速度**：WiFi 环境下 > 15MB/s
- **并发任务**：最多 6 个并发上传任务
- **断点续传**：支持大文件断点续传

#### 媒体展示性能
- **缩略图加载**：< 100ms（缓存命中）
- **预览图加载**：< 500ms（WiFi 环境）
- **原图加载**：< 2s（WiFi 环境）
- **内存占用**：< 200MB（正常使用）

#### 数据库性能
- **查询响应**：< 50ms（简单查询）
- **批量写入**：> 1000 条/秒
- **数据库大小**：< 100MB（10万条记录）

### E. 安全考虑

1. **Token 存储**：使用平台安全存储（Keychain/Keystore）
2. **HTTPS 优先**：默认使用 HTTPS，支持自签名证书（开发环境）
3. **证书验证**：支持证书固定（Certificate Pinning）
4. **数据加密**：敏感数据加密存储
5. **权限管理**：最小权限原则，仅请求必要权限
