## 概述

### 设计目标

设备唯一ID用于在多设备场景下区分不同的设备，确保每个设备有独立的同步状态（checkpoint）。核心要求：

1. **持久性**：应用卸载重装后ID保持不变
2. **唯一性**：每个设备有唯一的标识符
3. **稳定性**：ID在设备生命周期内保持稳定
4. **跨平台一致性**：Android 和 iOS 使用统一的实现方式

### 核心价值

- **多设备隔离**：同一用户在不同设备上的同步进度互不干扰
- **断点续传**：应用卸载重装后可以继续之前的同步进度
- **问题排查**：通过设备ID可以精确定位问题设备

## 实现原理

### 技术选型：flutter_udid

采用 `flutter_udid` 包的 `consistentUdid` 特性，该特性基于系统级设备标识符生成。

### 底层机制

#### Android 平台

`consistentUdid` 基于 **Android ID**（`Settings.Secure.ANDROID_ID`）生成：

- **Android ID** 是系统为每个应用分配的64位随机数
- 在应用首次安装时生成，应用卸载重装后保持不变
- 恢复出厂设置后会重新生成
- 不同应用在同一设备上的 Android ID 不同

**特点**：
- ✅ 应用卸载重装后保持不变
- ✅ 不同应用隔离（同一设备不同应用ID不同）
- ❌ 恢复出厂设置后会变化
- ❌ 系统更新可能影响（极少数情况）

#### iOS 平台

`consistentUdid` 基于 **IdentifierForVendor (IDFV)** 生成：

- **IDFV** 是 iOS 系统为同一开发者的应用分配的标识符
- 同一开发者的所有应用在同一设备上共享相同的 IDFV
- 应用卸载重装后保持不变
- 如果设备上所有该开发者的应用都被卸载，IDFV 会重置

**特点**：
- ✅ 应用卸载重装后保持不变
- ✅ 同一开发者应用共享（便于多应用场景）
- ❌ 卸载所有该开发者应用后会变化
- ❌ 恢复出厂设置后会变化

### 工作原理

```
应用首次启动
    ↓
调用 FlutterUdid.consistentUdid
    ↓
平台原生代码获取系统标识符
    ├─ Android: 获取 Android ID
    └─ iOS: 获取 IdentifierForVendor
    ↓
flutter_udid 对系统标识符进行处理
    ├─ 可能进行哈希处理
    └─ 格式化为统一格式
    ↓
返回一致的设备ID
    ↓
应用将ID存储到本地存储
    ↓
后续使用直接从存储读取
```

## 实现方案

### 1. 设备ID生成策略

#### 1.1 生成时机

**首次生成**：
- 应用首次启动时
- 本地存储中没有设备ID时

**读取策略**：
- 优先从本地存储读取已保存的设备ID
- 如果存储中没有，调用 `FlutterUdid.consistentUdid` 生成新的ID
- 生成后立即保存到本地存储

#### 1.2 存储策略

**存储位置**：
- 使用应用的本地存储（Store）持久化保存
- 存储键名：`deviceId`

**存储时机**：
- 首次生成后立即保存
- 登录成功后保存（确保ID已生成）

**存储格式**：
- 字符串格式
- 由 `flutter_udid` 生成的格式（通常是十六进制字符串）

### 2. 设备ID获取流程

```
应用启动/需要设备ID
    ↓
检查本地存储中是否有 deviceId
    ├─ 有 → 直接返回存储的ID
    └─ 没有 → 继续
    ↓
调用 FlutterUdid.consistentUdid
    ↓
获取系统级设备标识符
    ├─ Android: Android ID
    └─ iOS: IdentifierForVendor
    ↓
生成设备ID（由 flutter_udid 处理）
    ↓
保存到本地存储
    ↓
返回设备ID
```

### 3. 设备ID注入机制

#### 3.1 请求头注入

设备ID通过 HTTP 请求头 `x-device-id` 发送到服务器：

- **请求头名称**：`x-device-id`
- **注入位置**：所有需要设备隔离的API请求
- **注入方式**：在 API 拦截器中自动注入

#### 3.2 注入时机

- 应用启动时获取设备ID
- 每次API请求时自动添加到请求头
- 无需手动管理，由 API 服务统一处理

### 4. 容错处理

#### 4.1 存储读取失败

如果从本地存储读取失败：
- 重新调用 `FlutterUdid.consistentUdid` 生成新的ID
- 尝试保存到存储（如果保存失败，记录日志但继续使用）
- 返回生成的ID

#### 4.2 系统标识符获取失败

如果系统标识符获取失败（极少数情况）：
- 记录错误日志
- 可以考虑使用备用方案（但当前方案不涉及）
- 返回错误或抛出异常

## 平台差异说明

### Android 平台

#### 特性

1. **基于 Android ID**
   - 系统为每个应用分配独立的 Android ID
   - 应用卸载重装后保持不变
   - 不同应用在同一设备上的 Android ID 不同

2. **持久性保证**
   - ✅ 应用卸载重装：保持不变
   - ✅ 应用更新：保持不变
   - ❌ 恢复出厂设置：会变化
   - ❌ 系统重置：会变化

3. **隐私特性**
   - Android ID 是应用级别的标识符
   - 不同应用无法访问彼此的 Android ID
   - 符合 Android 隐私保护要求

#### 注意事项

- **恢复出厂设置**：设备ID会变化，需要重新同步
- **系统更新**：通常不影响，但极少数情况下可能变化
- **多用户场景**：每个用户账户有独立的 Android ID

### iOS 平台

#### 特性

1. **基于 IdentifierForVendor (IDFV)**
   - 系统为同一开发者的应用分配相同的 IDFV
   - 应用卸载重装后保持不变
   - 同一开发者的所有应用共享相同的 IDFV

2. **持久性保证**
   - ✅ 应用卸载重装：保持不变
   - ✅ 应用更新：保持不变
   - ❌ 卸载所有该开发者应用：会变化
   - ❌ 恢复出厂设置：会变化

3. **开发者隔离**
   - 同一开发者的应用共享 IDFV
   - 不同开发者的应用有不同的 IDFV
   - 便于多应用场景下的设备识别

#### 注意事项

- **卸载所有应用**：如果设备上所有该开发者的应用都被卸载，IDFV 会重置
- **恢复出厂设置**：设备ID会变化，需要重新同步
- **多应用场景**：同一开发者的多个应用会共享相同的设备ID（这是特性，不是问题）

### 平台对比

| 特性 | Android | iOS |
|------|---------|-----|
| **基础标识符** | Android ID | IdentifierForVendor |
| **应用级别** | 每个应用独立 | 同一开发者应用共享 |
| **卸载重装** | ✅ 保持不变 | ✅ 保持不变 |
| **恢复出厂设置** | ❌ 会变化 | ❌ 会变化 |
| **系统更新** | ✅ 通常不变 | ✅ 通常不变 |
| **多应用共享** | ❌ 不共享 | ✅ 同一开发者共享 |

### 跨平台一致性

虽然底层实现不同，但通过 `flutter_udid` 封装，上层应用使用统一的接口：

- **统一接口**：`FlutterUdid.consistentUdid`
- **统一格式**：返回的ID格式一致
- **统一行为**：应用卸载重装后都保持不变

## 使用场景

### 1. 同步状态隔离

每个设备有独立的同步 checkpoint，确保：
- 设备A的同步进度不影响设备B
- 设备B可以独立进行全量或增量同步
- 多设备同时同步不会产生冲突

### 2. 断点续传

应用卸载重装后：
- 设备ID保持不变
- 可以从之前的 checkpoint 继续同步
- 避免重复同步已同步的数据

### 3. 问题排查

通过设备ID可以：
- 精确定位问题设备
- 查看特定设备的同步历史
- 分析设备特定的同步问题

### 4. 数据统计

可以统计：
- 每个设备的同步状态
- 设备活跃度
- 多设备使用情况

## 总结

### 核心优势

1. **持久性**：应用卸载重装后ID保持不变，适合同步场景
2. **系统级支持**：基于系统标识符，稳定可靠
3. **跨平台统一**：通过 `flutter_udid` 实现统一的接口和行为
4. **隐私友好**：符合平台隐私保护要求

### 适用场景

- ✅ 需要卸载重装后保持状态的场景
- ✅ 多设备同步场景
- ✅ 需要设备隔离的场景

### 限制说明

- ❌ 恢复出厂设置后ID会变化（系统限制，无法避免）
- ❌ iOS 上卸载所有该开发者应用后ID会变化（系统限制）
- ⚠️ 需要依赖第三方包 `flutter_udid`
