# 远程视频播放方案（长期版）

## 一、设计原则

1. **播放引擎与「播放源」解耦**：由「源」（本地文件 / 远程 URL+headers）决定用哪种引擎，View 层不关心具体是 native 还是 video_player。
2. **统一控制接口**：进度、播放/暂停、音量、seek 等通过一个抽象接口暴露，控制栏只依赖该接口，便于以后换/加播放器。
3. **源与引擎选择集中在一处**：在单一工厂/策略里根据「是否有本地文件 / 是否仅远程」选择引擎，避免在 ViewerVideoPage 里散落 if/else。
4. **便于扩展**：后续若增加「签名 URL」「新播放器」或「仅远程用某插件」，只需新增源类型或新的控制器实现，不改 ViewerVideoPage 和控制栏的公共逻辑。

## 二、整体架构（分层）

```
┌─────────────────────────────────────────────────────────────────┐
│  MediaViewerPage                                                 │
│    └─ ViewerVideoPage (只依赖「播放控制器接口」+ 统一控制栏)          │
└─────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────┐
│  播放控制器抽象 (ViewerPlaybackController)                          │
│  - position / duration / isPlaying / setVolume / play / pause   │
│  - seek / 监听进度与状态变化 / 提供「视频画面」Widget                │
└─────────────────────────────────────────────────────────────────┘
        │                                    │
        ▼                                    ▼
┌───────────────────────┐        ┌───────────────────────────────────┐
│ NativePlaybackController │        │ NetworkPlaybackController        │
│ (包装 NativeVideoPlayer  │        │ (包装 video_player 的           │
│  Controller)             │        │  VideoPlayerController)         │
│ 用于：本地文件、本地 Live  │        │ 用于：仅远程（URL + headers）     │
└───────────────────────┘        └───────────────────────────────────┘
        │                                    │
        ▼                                    ▼
  native_video_player                    video_player
  (file / 未来可支持 signed URL)         (network + httpHeaders)
```

- **ViewerVideoPage**：只持有「播放控制器」抽象，根据控制器类型渲染对应「画面」Widget，控制栏统一用同一套。
- **ViewerPlaybackController**：抽象接口；Native / Network 各一个实现，便于以后加更多实现（如签名 URL、其他插件）。

## 三、目录与职责建议

在 `lib/` 下集中放「播放抽象 + 多引擎实现」，便于后续扩展和维护：

```
lib/
  presentation/widgets/viewer/
    viewer_video_page.dart         # 仅依赖 ViewerPlaybackController 接口
    viewer_video_manager.dart     # 通过「工厂」获取控制器，缓存 Future<Controller?>
    viewer_video_controller.dart  # VideoPlayerControls：参数改为接口
    viewer_video_state_provider.dart

  features/video_playback/        # 新建：播放抽象与多引擎
    viewer_playback_controller.dart   # 抽象接口
    native_playback_controller.dart   # 封装 native_video_player
    network_playback_controller.dart  # 封装 video_player + httpHeaders
    playback_backend_factory.dart     # 根据 asset + 环境 选引擎并创建控制器
```

- **兼容性**：现有 native 逻辑收进 `native_playback_controller`，对外仍是同一接口。
- **扩展性**：新增引擎 = 新文件实现 `ViewerPlaybackController`，在工厂里多一个分支。
- **易维护**：所有「用谁播、怎么播」的决策都在 `playback_backend_factory` 和 `video_playback/` 内，View 层保持薄。

## 四、核心类型设计（可落地）

### 1. 播放源（可选但推荐）

用于区分「本地文件」和「远程需带 header」，工厂根据源类型选引擎，后续加「签名 URL」只需新变体。

```dart
// 放在 features/video_playback/playback_source.dart（或 video_provider 同目录）

/// 播放源：不依赖具体播放器，仅描述「从哪里播」
sealed class VideoPlaybackSource {
  const VideoPlaybackSource();
}

class LocalFileSource extends VideoPlaybackSource {
  final String filePath;
  const LocalFileSource(this.filePath);
}

class RemoteNetworkSource extends VideoPlaybackSource {
  final String url;
  final Map<String, String> headers;
  const RemoteNetworkSource({required this.url, required this.headers});
}
```

- 现有 `VideoProvider` 中「本地路径」和「远程 URL+headers」的构建逻辑可以保留，但改为返回 `VideoPlaybackSource`（或同时保留原有 `VideoSource` 仅给 native 用，由工厂内部决定用哪种）。
- 长远看建议：**源只到「URL/路径 + headers」这一层**，不再在业务层直接构造 native 的 `VideoSource`，由 `NativePlaybackController` 内部用 `VideoSource.init`。

### 2. 播放控制器抽象接口

控制栏和 ViewerVideoPage 只依赖该接口，便于以后换/加引擎。

```dart
// features/video_playback/viewer_playback_controller.dart

abstract class ViewerPlaybackController {
  /// 当前播放位置
  Duration get position;

  /// 总时长（未就绪可为 Duration.zero）
  Duration get duration;

  /// 是否正在播放
  bool get isPlaying;

  /// 是否已就绪（可 seek、可拿 duration）
  bool get isReady;

  /// 播放
  Future<void> play();

  /// 暂停
  Future<void> pause();

  /// 跳转
  Future<void> seekTo(Duration position);

  /// 设置音量 0.0 ~ 1.0
  Future<void> setVolume(double volume);

  /// 设置是否循环（如 Live Photo 不循环）
  Future<void> setLoop(bool loop);

  /// 进度/状态变化时通知（避免各引擎 listener 形态不一致）
  void addPositionListener(VoidCallback listener);
  void removePositionListener(VoidCallback listener);
  void addStatusListener(VoidCallback listener);
  void removeStatusListener(VoidCallback listener);

  /// 用于构建「视频画面」的 Widget（由各实现返回自己的 View）
  Widget buildVideoView();

  /// 释放资源
  Future<void> dispose();
}
```

- **兼容性**：现有 `NativeVideoPlayerController` 的 play/pause/position/duration/volume 都可在 `NativePlaybackController` 里映射到上述方法。
- **扩展性**：以后新播放器只要实现该接口即可接入同一套 UI 与生命周期。

### 3. 两个实现类（概要）

- **NativePlaybackController**  
  - 持有 `NativeVideoPlayerController`，在 `buildVideoView()` 里返回 `NativeVideoPlayerView(onViewReady: ...)`，在 onViewReady 里 `loadVideoSource`（仅接受**本地** `VideoSource` 或未来 signed URL）。  
  - 所有 `ViewerPlaybackController` 的方法委托给 `NativeVideoPlayerController`，监听其 `onPlaybackStatusChanged` / `onPlaybackPositionChanged`，转成 `addPositionListener` / `addStatusListener` 的回调。

- **NetworkPlaybackController**  
  - 持有 `VideoPlayerController`（`video_player`），用 `VideoPlayerController.network(url, httpHeaders: headers)` 初始化。  
  - `buildVideoView()` 返回 `VideoPlayer(controller)`。  
  - position/duration/isPlaying 从 `controller.value` 取，play/pause/seek/setVolume 委托给 controller，用 `controller.addListener` 转成上述 Listener。

这样「控制栏」只依赖 `ViewerPlaybackController`，不再直接依赖 native 或 video_player 的类型。

### 4. 工厂：根据资产与源选择引擎

```dart
// features/video_playback/playback_backend_factory.dart

class PlaybackBackendFactory {
  /// 根据 asset、serverUrl、assetEntityLoader、videoIdOverride 决定用哪种引擎并创建控制器
  Future<ViewerPlaybackController?> create({
    required BaseAsset asset,
    required String assetId,
    String? serverUrl,
    AssetEntityLoader? assetEntityLoader,
    String? videoIdOverride,
  }) async {
    // 1) 解析源：先尝试「本地文件」（本地视频 / 本地 Live Photo motion）
    final localPath = await _tryResolveLocalPath(asset, assetEntityLoader, videoIdOverride);
    if (localPath != null) {
      return NativePlaybackController.fromFile(localPath);
    }

    // 2) 仅远程：URL + headers，用 video_player 以保证带认证头
    final remote = await _resolveRemoteUrlAndHeaders(asset, serverUrl, videoIdOverride);
    if (remote != null) {
      return NetworkPlaybackController.fromNetwork(
        url: remote.url,
        headers: remote.headers,
      );
    }

    return null;
  }

  Future<String?> _tryResolveLocalPath(...) { ... }  // 复用现有 VideoProvider 本地逻辑
  Future<({String url, Map<String, String> headers})?> _resolveRemoteUrlAndHeaders(...) { ... }
}
```

- **长远**：若后端支持「签名 URL」，可在 `_resolveRemoteUrlAndHeaders` 里改为返回「带签名的 URL + 空 headers」，并新增一个 `SignedUrlPlaybackController`（仍可实现 `ViewerPlaybackController`，内部用 native 或 video_player 均可），工厂里多一个分支即可，View 不变。
- **扩展性**：新引擎 = 新 Controller 实现 + 工厂里多一种源/条件的分支。

## 五、与现有组件的衔接（具体改法）

### 1. VideoProvider / 源解析

- **方案 A（最小改动）**：保持 `VideoProvider.getVideoSource` 现有签名，但仅用于「本地 + native」路径。  
  - 新增例如 `VideoProvider.getPlaybackSource(asset, serverUrl, ...)`，返回 `VideoPlaybackSource?`（LocalFileSource 或 RemoteNetworkSource），由工厂或 VideoProvider 内部根据 asset 类型和本地是否可解析决定。  
- **方案 B（更统一）**：逐步让 `VideoProvider` 只产出「源」（LocalFileSource / RemoteNetworkSource），不再直接返回 native 的 `VideoSource`；`NativePlaybackController` 内部根据 `LocalFileSource` 自己调用 `VideoSource.init(path: ..., type: VideoSourceType.file)`。  
- 远程 URL + headers 的拼接逻辑可以留在 `VideoProvider` 或迁到 `PlaybackBackendFactory._resolveRemoteUrlAndHeaders`（调用 `ApiService.getRequestHeaders()` 与现有 `_getRemoteVideoSource` 的 URL 构建），二选一即可，避免重复。

### 2. ViewerVideoManager

- 当前：缓存 `Future<VideoSource?>`，再在 ViewerVideoPage 里用 native 的 `loadVideoSource`。  
- 改为：缓存 `Future<ViewerPlaybackController?>`，由 `PlaybackBackendFactory.create(...)` 得到。  
- `getVideoSource` 可重命名为 `getPlaybackController`，参数保持不变（asset, assetId, serverUrl, assetEntityLoader, videoIdOverride），便于 MediaViewerPage 调用处只改方法名（或保留旧名做转发）。

### 3. ViewerVideoPage

- 当前：持有 `NativeVideoPlayerController? _controller`，build 里写死 `NativeVideoPlayerView` + `VideoPlayerControls(controller: controller)`。  
- 改为：  
  - 持有 `ViewerPlaybackController? _controller`。  
  - 通过 `widget.videoManager.getPlaybackController(...)` 得到控制器（内部即工厂创建的 Native 或 Network 实现）。  
  - 画面区域：`_controller!.buildVideoView()`（由 Native 或 Network 实现各自返回自己的 View）。  
  - 控制栏：`VideoPlayerControls(playbackController: _controller!, ...)`。  
- 加载中 / 错误 / 生命周期（dispose、前后台、切换当前页）逻辑不变，只是把对 native controller 的 pause/dispose 换成对 `ViewerPlaybackController` 的 `pause()`/`dispose()`。

### 4. VideoPlayerControls（viewer_video_controller.dart）

- 当前：参数为 `NativeVideoPlayerController controller`，内部用 `controller.playbackInfo`、`controller.videoInfo`、`controller.onPlaybackStatusChanged` 等。  
- 改为：参数为 `ViewerPlaybackController playbackController`，所有读写通过接口：  
  - `playbackController.position` / `duration` / `isPlaying`；  
  - `playbackController.addPositionListener` / `addStatusListener`（在 initState/didUpdateWidget/dispose 里对称 add/remove）；  
  - 播放/暂停/seek/音量 调用 `playbackController.play()` / `pause()` / `seekTo()` / `setVolume()`。  
- 这样控制栏与具体播放器完全解耦，后续换引擎或加新引擎都不必再改控制栏。

## 六、实施顺序建议（易维护、可分批上线）

1. **新建 `features/video_playback/`**  
   - 定义 `ViewerPlaybackController` 接口。  
   - 实现 `NativePlaybackController`（包装现有 native 逻辑，内部仍用 `VideoSource.init` + `NativeVideoPlayerView`）。  
   - 在 ViewerVideoPage 里先**仅**用 `NativePlaybackController` 替换对 `NativeVideoPlayerController` 的直接使用，控制栏改为依赖 `ViewerPlaybackController`。验证本地视频、本地 Live Photo 行为不变。

2. **实现 `NetworkPlaybackController`**  
   - 使用 `VideoPlayerController.network(url, httpHeaders: headers)`，实现接口的 play/pause/seek/volume 与 `buildVideoView()`。  
   - 在工厂里增加「仅远程 → NetworkPlaybackController」分支，URL 与 headers 从现有 `VideoProvider` 或新 `_resolveRemoteUrlAndHeaders` 来。  
   - ViewerVideoManager 改为通过工厂返回 `ViewerPlaybackController?`，ViewerVideoPage 用 `_controller!.buildVideoView()` 渲染画面。  
   - 验证仅远程视频能正常播放（带认证头）。

3. **可选：引入 `VideoPlaybackSource`**  
   - 将「本地路径 / 远程 URL+headers」抽象为 `VideoPlaybackSource`，工厂或 VideoProvider 先产出 Source，再由工厂根据 Source 类型创建对应 Controller。  
   - 为后续「签名 URL」或更多源类型留扩展点。

4. **后续扩展（兼容性/扩展性）**  
   - 签名 URL：新增 `SignedUrlSource`（或仅在 `_resolveRemoteUrlAndHeaders` 返回带签名的 URL），新增 `SignedUrlPlaybackController` 或复用现有某一实现，工厂多一个分支。  
   - 新播放器：新文件实现 `ViewerPlaybackController`，工厂按条件选择即可，View 与控制栏无需改。

## 七、小结

| 目标         | 做法 |
|--------------|------|
| 长期兼容     | 抽象出 `ViewerPlaybackController`，现有 native 行为收进 `NativePlaybackController`，UI 与生命周期只依赖接口。 |
| 扩展性       | 新引擎 = 新 Controller 实现 + 工厂分支；新源类型 = 新 Source 变体 + 工厂分支。 |
| 易维护       | 播放相关集中到 `video_playback/` 和工厂；ViewerVideoPage / VideoPlayerControls 只依赖接口，不依赖具体播放器。 |
| 解决远程头   | 仅远程使用 `video_player` 的 `NetworkPlaybackController`，通过 `httpHeaders` 传认证，避免 native_video_player 不传 header 的问题。 |

按上述步骤实现，即可在**不破坏现有本地播放体验**的前提下，让远程视频用 `video_player` 稳定播放，并为签名 URL、新播放器预留清晰扩展路径。若你希望，我可以再针对某一步（例如工厂与 VideoProvider 的职责边界、或 `ViewerPlaybackController` 的完整方法列表）按你当前仓库的文件名和类名写一版更贴代码的伪代码/补全版。
