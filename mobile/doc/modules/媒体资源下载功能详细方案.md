# 媒体资源下载功能详细方案

本文档描述 PrismBox 移动端**媒体资源统一后台下载**的详细设计与实现方案。下载能力与现有**上传**架构对齐：在后台执行、任务持久化、状态可观测，并统一支持「照片页时间线资产」与「圈子帖子媒体」两种来源；对 Live Photo 下载后仍以一条 Live Photo 写回相册。

## 一、目标与约束

### 1.1 功能目标

- **后台执行**：与上传一致，使用 `background_downloader` 在后台执行下载，应用退到后台或锁屏仍可继续。
- **统一入口**：照片页（时间线/相册）与圈子帖子共用同一套下载管道，仅「请求来源」不同（BaseAsset vs PostMedia）。
- **下载内容**：仅下载**原始资源**（`/api/v1/media/:uuid/download/original`）。
- **Live Photo**：下载后仍以**一条 Live Photo** 写回相册（图+视频一起），不拆成两张独立文件。
- **可观测**：任务持久化、状态/进度可查，便于列表/通知/重试。

### 1.2 设计约束

- 下载与上传使用同一底层库（`background_downloader`），但通过**独立 task group** 区分，避免回调与上传混在一起。
- 下载完成后的「写相册」逻辑（saveImage / saveVideo / saveLivePhoto）在**任务完成回调**中执行，作为后处理步骤。
- 所有下载任务状态变更通过**状态机**驱动，与上传侧一致，便于维护与扩展。

## 二、与上传架构的对应关系

上传侧已有分层可直接复刻到下载侧：

| 上传侧 | 下载侧（本方案） |
|--------|------------------|
| `UploadTaskEntity`（DB 表） | `DownloadTaskEntity`（新表） |
| `UploadTaskStatus` | `DownloadTaskStatus`（新枚举，或复用语义相近的） |
| `UploadTaskManager`（创建 UploadTask、enqueue、注册回调） | `DownloadTaskManager`（创建 DownloadTask、enqueue、注册回调，**独立 group**） |
| `UploadTaskStateMachine` | `DownloadTaskStateMachine` |
| `UploadService`（addTask、addTasks、startUpload、队列状态） | `DownloadService`（addDownload、startDownload、队列状态） |
| `UploadOrchestrator`（取 pending → 并发执行 → 单任务 _executeUpload） | `DownloadOrchestrator`（取 pending → 并发执行 → 单任务 _executeDownload + 完成后**后处理**） |
| `TaskFactory`（从 LocalAsset 建 UploadTaskEntityData） | `DownloadTaskFactory` 或入参抽象（从「下载请求」建 DownloadTaskEntityData + 1/2 个 DownloadTask） |
| `BackupService`（手动/自动备份入口） | 预览页「下载」按钮 → `DownloadService.addDownload(request)` |

差异点：

1. **网络方向**：上传是 `UploadTask.fromFile`，下载是 `DownloadTask`（GET URL → 写入本地路径）。
2. **完成后逻辑**：下载需要在**任务完成回调**里做「后处理」：根据类型调用 `PhotoManager.editor.saveImage` / `saveVideo` / `saveLivePhoto`，再删临时文件、更新状态。
3. **任务组**：使用**独立 group**（如 `prismbox_download`），与 `UploadTaskGroup.manual` / `auto` 分开。

## 三、数据模型与存储

### 3.1 下载任务表 `DownloadTaskEntity`

与上传表平级，表示「用户可见的一条下载」：普通媒体 1 个文件，Live Photo 1 条记录对应 2 个文件。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | TEXT PK | 主键，如 `download_<sourceId>_<timestamp>` 或 UUID |
| `userId` | TEXT FK | 用户 ID |
| `sourceType` | INT (enum) | 来源：`timeline_asset` \| `post_media` |
| `sourceId` | TEXT | 时间线为 assetId，帖子为 media.uuid（或稳定唯一标识） |
| `mediaUuid` | TEXT | 主资源 media UUID（原图/主图） |
| `livePhotoVideoUuid` | TEXT nullable | Live Photo 时视频的 media UUID，非 Live 为 null |
| `filename` | TEXT | 展示用文件名（如 originalFilename） |
| `itemType` | TEXT | `IMAGE` \| `VIDEO`（主资源类型） |
| `status` | INT (enum) | 见 3.2 |
| `progress` | INT | 0–100，Live Photo 可为两文件综合进度 |
| `errorMessage` | TEXT nullable | 失败原因 |
| `imageTempPath` | TEXT nullable | 主图下载完成后的临时路径（后处理写相册后删除） |
| `videoTempPath` | TEXT nullable | Live 视频临时路径（仅 Live Photo） |
| `createdAt` | DATETIME | 创建时间 |
| `updatedAt` | DATETIME | 更新时间 |

**索引建议**：`userId`、`status`、`sourceType`、`sourceId`（便于去重/冲突检测）。

### 3.2 下载任务状态 `DownloadTaskStatus`

与上传状态机类似：

- `pending` → `queued` → `downloading` → `processing`（写相册中）→ `completed`
- 任意阶段可 → `failed` / `permanentlyFailed` / `cancelled`
- `failed` 可重试 → `queued` 或 `downloading`

其中 `processing` 表示 background_downloader 已下载完成，正在执行「写相册 + 删临时文件」的后处理。

### 3.3 与 background_downloader 的对应关系

- **普通媒体**：1 条 `DownloadTaskEntity` = 1 个 `DownloadTask`（taskId 建议用 `downloadTaskEntity.id` 或带后缀如 `"${entity.id}_image"`）。
- **Live Photo**：1 条 `DownloadTaskEntity` = 2 个 `DownloadTask`：
  - 主图：`mediaUuid` → original URL，taskId 如 `"${entity.id}_image"`，保存到 `imageTempPath`；
  - 视频：`livePhotoVideoUuid` → original URL，taskId 如 `"${entity.id}_video"`，保存到 `videoTempPath`。

两个 DownloadTask 都带同一 `group: 'prismbox_download'`，在回调里用 taskId 反查 entity（去掉 `_image`/`_video` 得到 entity.id），更新对应字段；当两个都完成时再触发后处理（saveLivePhoto）。

## 四、统一下载请求抽象

两处入口统一成同一种「下载请求」，再交给同一套服务建任务、入队。

### 4.1 请求模型

```dart
/// 统一下载请求（照片页时间线资产 或 帖子媒体）
class MediaDownloadRequest {
  final String userId;
  final MediaDownloadSourceType sourceType;  // timeline_asset | post_media
  final String sourceId;                     // assetId 或 media.uuid
  final String mediaUuid;                    // 主图/主资源的 media UUID
  final String? livePhotoVideoUuid;           // Live Photo 时视频 UUID
  final String itemType;                     // 'IMAGE' | 'VIDEO'
  final String filename;                     // 展示/保存用文件名
}

enum MediaDownloadSourceType { timeline_asset, post_media }
```

### 4.2 从两处构造请求

- **照片页（MediaViewerPage）**  
  - 当前项：`_currentAssetId` → `BaseAsset`。  
  - 仅当 `asset.remoteId != null` 时允许下载（仅远程有原图）。  
  - 构造：`mediaUuid = asset.remoteId!`，`livePhotoVideoUuid = asset.livePhotoVideoId`，`itemType`、`filename` 从 asset 取。

- **帖子页（PhotoViewerPage）**  
  - 当前项：`widget.media[_currentIndex]`（PostMedia）。  
  - 构造：`mediaUuid = media.uuid`，`livePhotoVideoUuid = media.livePhotoVideoId`（需后端与 PostMedia 支持），`itemType = media.itemType`，`filename = media.originalFilename ?? media.filename ?? media.uuid`。

**DownloadService** 只接收 `MediaDownloadRequest`，不关心来自时间线还是帖子，实现统一。

## 五、后台下载流程

### 5.1 总体流程

1. 用户点击预览页「下载」 → 构造 `MediaDownloadRequest` → `DownloadService.addDownload(request)`。
2. **DownloadService**：  
   - 冲突/去重（同 userId + sourceType + sourceId 且状态为 pending/queued/downloading 可跳过或替换）。  
   - 插入 `DownloadTaskEntity`（status = pending）。  
   - 乐观更新为 queued（可选）。  
   - 调用 `DownloadOrchestrator.startDownload(userId, …)`（不阻塞 UI）。
3. **DownloadOrchestrator**：  
   - 从 DB 取该用户 pending/queued 的下载任务（可按优先级排序）。  
   - 对每条 entity 执行 `_executeDownload(entity)`：  
     - 解析 URL（baseUrl + `/api/v1/media/${uuid}/download/original`），headers 用 `ApiService.getRequestHeaders()`。  
     - 确定保存路径：例如 `BaseDirectory.temporary` 下子目录 `prismbox_download`，文件名 `"${entity.id}_image"` / `"${entity.id}_video"`（扩展名可从 Content-Type 或默认 .jpg/.mov）。  
     - 创建 1 个或 2 个 `DownloadTask`（taskId 与 entity 约定一致），group = `prismbox_download`，然后 `FileDownloader().enqueue(task)`。  
   - 不等待完成即返回（后台执行）。
4. **DownloadTaskManager**：  
   - 仅负责「创建 DownloadTask、enqueue、注册 group 回调」。  
   - 在 `prismbox_download` 的 status 回调中：  
     - 根据 taskId 找到对应 `DownloadTaskEntity` 和 image/video 槽位。  
     - 更新 progress、status（如 downloading、completed）、失败时 errorMessage；  
     - 若为 Live Photo 且两个文件都 completed，则把 entity 状态改为 `processing` 并触发**后处理**（见下）。  
   - 进度回调中可更新 entity.progress（或综合两个子任务进度）。
5. **后处理（必须在回调/主 isolate 中执行）**：  
   - 根据 entity 的 `itemType` 和是否含 `livePhotoVideoUuid`：  
     - 普通图片：`PhotoManager.editor.saveImage(bytes, title: filename, …)`，删除 imageTempPath。  
     - 普通视频：`PhotoManager.editor.saveVideo(File(videoTempPath), …)`，删除 videoTempPath。  
     - Live Photo：`PhotoManager.editor.darwin.saveLivePhoto(File(imageTempPath), File(videoTempPath), title)`（iOS）；Android 可降级为仅保存图片。  
   - 删除临时文件，entity 状态 → `completed`；失败则 → `failed`，保留 errorMessage。

### 5.2 DownloadTaskManager 与 FileDownloader 配置

- 单独为下载配置一组并发（如 `(Config.holdingQueue, (4, 4, 2))`），或复用全局但用 group 区分。  
- `FileDownloader().registerCallbacks(group: 'prismbox_download', taskStatusCallback: ..., taskProgressCallback: ...)`，与 upload 的 group 分开。  
- 若希望下载任务在应用被杀死后仍可恢复，可调用 `trackTasks()` 并保证 taskId 稳定、保存路径固定。

### 5.3 状态机

- 单独实现 `DownloadTaskStateMachine`，规则与上传类似：  
  - pending → queued → downloading → processing → completed；  
  - 任意 → failed / permanentlyFailed / cancelled；  
  - failed 可重试 → queued。  
- 所有 DB 状态变更都经状态机，保证与上传一致的可维护性。

## 六、Live Photo 完整链路

1. **建任务**：`livePhotoVideoUuid != null` 时，一条 `DownloadTaskEntity`，`imageTempPath`/`videoTempPath` 初始为 null。  
2. **创建两个 DownloadTask**：  
   - 主图 URL(mediaUuid)，保存到 `.../prismbox_download/${entity.id}_image.*`；  
   - 视频 URL(livePhotoVideoUuid)，保存到 `.../prismbox_download/${entity.id}_video.*`。  
3. **回调**：每个 DownloadTask 完成时更新 entity 的 imageTempPath 或 videoTempPath，并更新进度；当两个都完成时，将 status 设为 `processing`，执行后处理。  
4. **后处理**：读入两个临时文件，调用 `PhotoManager.editor.darwin.saveLivePhoto(imageFile, videoFile, title)`，成功后删临时文件，entity → completed。  
5. **失败**：任一下载失败或 saveLivePhoto 失败，entity → failed/permanentlyFailed，并清理已存在的临时文件。

这样**下载后仍是 Live Photo**，不会变成两张独立文件。

## 七、后端与前端模型

### 7.1 后端

- **帖子媒体 API**：在返回媒体列表的 DTO 中增加 `live_photo_video_id`（与 sync 一致），并在 group 服务构建 `MediaInfo` 时从 `media.LivePhotoVideoUUID` 赋值。  
- 参考：`backend/internal/service/group/service.go` 中构建 `MediaInfo` 的循环内增加对 `media.LivePhotoVideoUUID` 的赋值；DTO 结构需包含 `LivePhotoVideoID` 字段。

### 7.2 前端

- **PostMedia**：增加 `livePhotoVideoId` 字段，在 `fromJson` 中解析 `live_photo_video_id`。  
- 这样帖子预览页的「下载」也能构造出带 `livePhotoVideoUuid` 的 `MediaDownloadRequest`，走同一套后台下载与 Live Photo 后处理。

## 八、UI 与入口

### 8.1 MediaViewerPage（照片页）

- 在 `ViewerControlsBar` 的 AppBar actions 中增加「下载」按钮（如 `Icons.download`）。  
- 仅当当前 asset 有 `remoteId` 时显示或可用（仅远程资源可下载）。  
- 点击 → 构造 `MediaDownloadRequest`（从当前 `BaseAsset`）→ `DownloadService.addDownload(request)`，并 SnackBar 提示「已加入下载队列」。

### 8.2 PhotoViewerPage（帖子预览）

- 在 AppBar 的 actions 中增加「下载」按钮。  
- 点击 → 从当前 `PostMedia` 构造 `MediaDownloadRequest` → `DownloadService.addDownload(request)`，同样提示已加入队列。

### 8.3 可选：下载队列入口

- 在设置或任务中心增加「下载队列」入口，展示 `DownloadTaskEntity` 列表（状态、进度、错误），与上传队列并列，便于用户查看与重试。

## 九、实现清单

建议按以下顺序实现，便于分步验证。

### 9.1 数据层

- [ ] 新增 `DownloadTaskEntity` 表、`DownloadTaskStatus` 枚举、`DownloadTaskDao`。  
- [ ] 在 AppDatabase 中注册表与 DAO。

### 9.2 下载任务管理层

- [ ] `DownloadTaskManager`：配置 FileDownloader（下载用 group）、创建 `DownloadTask`、enqueue、注册 `prismbox_download` 的 status/progress 回调；在回调中更新 DB 并触发「双文件都完成」时的后处理。  
- [ ] `DownloadTaskStateMachine`：状态转换规则与 DB 更新。

### 9.3 请求与任务创建

- [ ] 定义 `MediaDownloadRequest`、`MediaDownloadSourceType`。  
- [ ] `DownloadTaskFactory`（或 DownloadService 内方法）：由 `MediaDownloadRequest` 生成一条 `DownloadTaskEntity` 及 1/2 个 `DownloadTask`（含 URL、headers、保存路径、taskId 约定）。

### 9.4 编排与后处理

- [ ] `DownloadOrchestrator`：取 pending 任务、调用 DownloadTaskManager 执行 `_executeDownload`（只负责创建并 enqueue DownloadTask），不阻塞。  
- [ ] 在 DownloadTaskManager 的完成回调中：检测 Live Photo 双文件是否都完成，若是则执行写相册（saveImage/saveVideo/saveLivePhoto）、删临时文件、状态 → completed/failed。

### 9.5 服务层

- [ ] `DownloadService`：`addDownload(MediaDownloadRequest)`（冲突检测、插入 entity、乐观更新、触发 startDownload）、`getQueueStatus(userId)`、可选 `cancelDownload`/`retry`。  
- [ ] 依赖注入：在现有 DI 中注册 DownloadService、DownloadOrchestrator、DownloadTaskManager、DownloadTaskStateMachine。

### 9.6 后端

- [ ] 帖子媒体 API 返回 `live_photo_video_id`；PostMedia 模型与 fromJson 支持该字段。

### 9.7 UI

- [ ] MediaViewerPage、PhotoViewerPage 右上角下载按钮，构造 `MediaDownloadRequest` 并调用 `DownloadService.addDownload`。

### 9.8 权限与错误

- [ ] 写相册前请求相册权限；网络/权限/后端错误在 status 回调中写入 `errorMessage`，并可通过 SnackBar 或下载队列页展示。

## 十、与上传的对照小结

| 维度 | 上传 | 下载（本方案） |
|------|------|----------------|
| 任务存储 | UploadTaskEntity | DownloadTaskEntity |
| 执行引擎 | background_downloader UploadTask | background_downloader DownloadTask |
| 任务组 | prismbox_upload_manual / auto | prismbox_download |
| 请求抽象 | LocalAsset + TaskFactory | MediaDownloadRequest + DownloadTaskFactory |
| 完成后逻辑 | 更新 DB、同步状态、可能派生 Live 图片任务 | 后处理：写相册（saveImage/saveVideo/saveLivePhoto）、删临时文件 |
| 入口 | BackupService 手动/自动 | 预览页「下载」+ 可选下载队列页 |
