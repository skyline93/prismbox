## 问题概述

### 问题描述

应用中媒体资源的文件路径获取存在严重问题：使用了 `asset.file` 获取处理后的临时文件路径，而不是 `asset.originFile` 获取原始文件的永久路径。这导致：

1. **数据库存储的路径不正确**：存储的是临时文件路径（可能包含 `_exif.jpg` 后缀）
2. **上传任务文件路径失效**：临时文件被系统清理后，上传任务无法找到文件
3. **文件读取失败**：路径指向已被清理的临时文件，导致各种文件操作失败

### 问题表现

#### 错误日志示例

```
W/TaskWorker(15658): File at /data/user/0/com.u163.glf9832.prismbox/app_flutter/f7fd744b85ec51124a24f76317ee503b_exif.jpg does not exist
```

路径包含 `_exif.jpg` 后缀，这是典型的临时处理文件路径。

#### 问题场景

1. **同步时**：使用 `asset.file` 获取路径并存储到数据库
2. **上传时**：从数据库读取路径，发现文件不存在
3. **修复逻辑**：尝试使用 `asset.file` 重新获取，但仍然是临时路径

### 问题根源

#### photo_manager API 差异

- **`asset.file`**：
  - 返回可能经过处理的文件（如应用 EXIF 旋转的临时文件）
  - 在 Android 上可能生成临时文件，路径包含 `_exif.jpg` 后缀
  - 临时文件可能很快被系统清理
  - 不适用于长期存储和上传操作

- **`asset.originFile`**：
  - 返回原始文件的永久路径
  - 是实际存储在设备上的文件
  - 路径稳定，不会因临时文件清理而失效
  - 适用于所有文件操作场景

#### 代码中的错误使用

在以下位置错误使用了 `asset.file` / `assetEntity.file`：

1. **本地同步服务**（根源）：`local_sync_service.dart:375`
   - 存储到数据库的路径来源
   - 这是最关键的修复点

2. **备份服务**（修复逻辑）：`backup_service.dart:137`
   - 文件不存在时重新获取路径的逻辑

3. **上传编排器**（修复逻辑）：`upload_orchestrator.dart:557`
   - 上传时文件路径失效的修复逻辑

## 问题影响分析

### 1. 数据一致性问题

- **数据库存储错误路径**：所有同步的资产都存储了临时文件路径
- **路径失效风险高**：临时文件被清理后，数据库中的路径全部失效
- **数据完整性受损**：路径字段实际上不可用

### 2. 功能失效问题

- **上传功能失败**：无法找到文件，导致上传任务反复重试后失败
- **文件读取失败**：所有依赖路径的文件操作都可能失败
- **用户体验差**：上传失败，用户无法完成备份操作

### 3. 性能问题

- **不必要的重试**：文件不存在导致任务反复重试
- **资源浪费**：重复尝试访问不存在的文件
- **日志噪音**：大量的文件不存在警告日志

## 整改方案

### 修复优先级

**高优先级**（必须立即修复）：
1. ✅ **本地同步服务**：修复存储到数据库的路径获取逻辑
2. ✅ **备份服务**：修复文件路径重新获取逻辑
3. ✅ **上传编排器**：修复上传时文件路径重新获取逻辑

### 详细修改方案

#### 修改 1: 本地同步服务（最关键）

**文件**: `lib/features/local_sync/services/local_sync_service.dart`

**位置**: `_convertToEntity` 方法，第 373-376 行

**修改前**:
```dart
/// 转换 AssetEntity 为 LocalAssetEntityData
Future<LocalAssetEntityData> _convertToEntity(pm.AssetEntity asset) async {
  // 获取文件路径
  final file = await asset.file;  // ❌ 错误：获取处理后的临时文件
  final path = file?.path ?? '';
```

**修改后**:
```dart
/// 转换 AssetEntity 为 LocalAssetEntityData
Future<LocalAssetEntityData> _convertToEntity(pm.AssetEntity asset) async {
  // 获取文件路径 - 使用 originFile 获取原始文件路径
  // 注意：originFile 返回原始文件的永久路径，不会被系统清理
  // file 可能返回处理后的临时文件（如应用 EXIF 旋转），路径可能包含 _exif.jpg 后缀
  final file = await asset.originFile;  // ✅ 正确：获取原始文件路径
  final path = file?.path ?? '';
```

**影响范围**:
- 修复后，所有新同步的资产将存储正确的原始文件路径
- 这是最关键的修复，因为它决定了存储到数据库的路径质量

#### 修改 2: 备份服务

**文件**: `lib/services/backup/backup_service.dart`

**位置**: `startManualBackup` 方法，第 135-140 行

**修改前**:
```dart
            final assetEntity = await pm.AssetEntity.fromId(asset.id);
            if (assetEntity != null) {
              final fileFromAsset = await assetEntity.file;  // ❌ 错误
              if (fileFromAsset != null && await fileFromAsset.exists()) {
                actualPath = fileFromAsset.path;
```

**修改后**:
```dart
            final assetEntity = await pm.AssetEntity.fromId(asset.id);
            if (assetEntity != null) {
              // 使用 originFile 获取原始文件路径，确保获取的是永久文件
              final fileFromAsset = await assetEntity.originFile;  // ✅ 正确
              if (fileFromAsset != null && await fileFromAsset.exists()) {
                actualPath = fileFromAsset.path;
```

**影响范围**:
- 当数据库中的路径失效时，重新获取的路径将是正确的原始路径
- 同时会更新数据库中的路径（如果修复逻辑包含路径更新）

#### 修改 3: 上传编排器

**文件**: `lib/services/backup/upload_orchestrator.dart`

**位置**: `_executeUpload` 方法，第 555-560 行

**修改前**:
```dart
          final assetEntity = await pm.AssetEntity.fromId(task.assetId);
          if (assetEntity != null) {
            final fileFromAsset = await assetEntity.file;  // ❌ 错误
            if (fileFromAsset != null && await fileFromAsset.exists()) {
              actualPath = fileFromAsset.path;
```

**修改后**:
```dart
          final assetEntity = await pm.AssetEntity.fromId(task.assetId);
          if (assetEntity != null) {
            // 使用 originFile 获取原始文件路径，确保获取的是永久文件
            final fileFromAsset = await assetEntity.originFile;  // ✅ 正确
            if (fileFromAsset != null && await fileFromAsset.exists()) {
              actualPath = fileFromAsset.path;
              
              // 更新任务中的文件路径（确保后续使用正确的路径）
              await _database.uploadTaskDao.updateTaskLocalPath(
                task.id,
                actualPath,
              );
```

**影响范围**:
- 上传时如果路径失效，将获取正确的原始路径
- 同时更新任务记录，确保后续使用正确的路径

## 后续工作建议

### 1. 数据迁移（可选）

如果数据库中已存在错误路径（包含 `_exif` 后缀），可以考虑：

**方案A：自动修复（推荐）**
- 在上传和读取文件时，如果发现路径包含 `_exif` 后缀，自动使用 `originFile` 重新获取并更新
- 优点：无需额外操作，自动修复
- 缺点：修复是渐进式的，需要时间

**方案B：批量修复脚本**
- 编写脚本扫描所有包含 `_exif` 后缀的路径，批量修复
- 优点：一次性修复所有问题
- 缺点：需要额外开发工作，可能影响现有数据

**推荐方案**：使用方案A，因为修复逻辑已经在上传流程中实现，会逐步修复所有问题路径。

### 2. 测试验证

修复后需要验证：

1. **同步功能测试**
   - 执行全量同步，检查数据库中的路径是否为原始路径
   - 执行增量同步，验证新同步的资产路径正确
   - 验证路径格式：不应包含 `_exif` 后缀

2. **上传功能测试**
   - 创建上传任务，验证能正确找到文件
   - 验证上传任务能正常执行完成
   - 验证不再出现文件不存在错误

3. **文件读取测试**
   - 验证从数据库路径读取文件成功
   - 验证各种文件操作（读取、计算 checksum 等）正常

4. **长期稳定性测试**
   - 验证路径不会因时间推移而失效
   - 验证临时文件清理不影响路径有效性
