### 第一部分：重构总结

本次重构旨在解决 `media_sync` 模块内部职责不清、命名混淆、通用能力与业务逻辑耦合以及未来扩展性不足的问题。我们通过三个核心阶段，将一个专有、复杂的业务模块，重构为一个清晰、分层且高度可扩展的后台任务处理中心。

#### 阶段一：模块职责分离 (宏观分层)

*   **问题**: 原 `sync` 模块名称过于具体，但其内部已包含一个通用的后台任务分发框架 (`task_dispatcher`)，导致模块职责不纯粹。
*   **重构动作**:
    1.  将原 `lib/features/sync` 模块重命名为 `lib/features/background_jobs`，使其名称能够准确反映其作为应用“后台任务中心”的定位。
    2.  在该模块下创建了两个顶级目录：
        *   `core/`: 用于存放所有通用的、与具体业务无关的基础设施代码。
        *   `impl/`: 用于存放所有具体的业务实现代码。
    3.  将通用的 `BackgroundTask` 合约、`task_dispatcher` 等文件迁移至 `core/` 目录。
    4.  将所有与媒体同步相关的业务代码整体迁移至 `impl/media_sync/` 目录下。
*   **成果**: 实现了**通用框架**与**具体业务**在物理层面的完全隔离，奠定了清晰的架构基础。

#### 阶段二：业务逻辑梳理 (`media_sync` 内部重构)

*   **问题**: `media_sync` 内部代码虽然按类型（`coordinator`, `handlers`）存放，但目录结构未能反映真实的业务流程，且核心类命名（`MediaSyncService` vs `MediaSyncServiceCore`）存在歧义，增加了理解成本。
*   **重构动作**:
    1.  **引入领域驱动设计 (DDD) 思想**，创建 `domain/` 目录，用于聚合所有核心业务逻辑。
    2.  **核心类重命名**，使其名称能准确反映其职责：
        *   `MediaSyncServiceCore` -> `MediaSyncOrchestrator` (编排器)：清晰表明其在后台 Isolate 中负责**编排和指挥**同步流程。
        *   `AssetActionHandler` -> `AssetChangeExecutor` (执行器)：清晰表明其负责**执行**对数据库的具体变更操作。
    3.  **调整目录结构**，使之与业务流程匹配：
        *   `Orchestrator` 和 `Executor` 移入 `domain/`。
        *   `synchronizers` 目录作为数据源，也移入 `domain/`。
        *   `periodic_sync_task` 被识别为连接外部框架的“适配器”，因此为其创建 `background/` 目录并重命名为 `PeriodicSyncAdapter`。
*   **成果**: `media_sync` 内部结构变得极度清晰。开发者可以轻易地通过目录和文件名理解**数据从哪里来 (`synchronizers`)**、**流程如何控制 (`Orchestrator`)** 以及**变更如何执行 (`Executor`)**。

#### 阶段三：Isolate 管理抽象化 (构建通用服务)

*   **问题**: 原 `SyncIsolate` 和 `SyncIsolateManager` 是为 `media_sync` 业务专用的，未来若有其他复杂任务需要 Isolate，将导致代码重复和维护困难。
*   **重构动作**:
    1.  **创建通用 Isolate 服务**: 在 `core/isolate/` 目录下，创建了一套完全通用的 Isolate 管理框架。
    2.  **定义通用协议**: 设计了通用的通信模型 `IsolateJob` (作业请求) 和 `IsolateJobResult` (作业结果)，解除了通信与具体业务的耦合。
    3.  **实现通用管理器**: `IsolateJobManager` 作为单例，负责管理通用 Isolate 的生命周期，并提供 `submitJob` 和 `executeJob` 等通用接口。
    4.  **定义任务处理器合约**: 创建 `IsolateTaskHandler` 抽象接口，要求所有需要在 Isolate 中运行的业务逻辑都必须实现该接口。
    5.  **改造 `media_sync`**:
        *   删除了专有的 `SyncIsolateManager` 和 `sync_isolate.dart`。
        *   创建了 `MediaSyncIsolateHandler`，它实现了 `IsolateTaskHandler` 接口，作为 `media_sync` 业务逻辑在 Isolate 中的入口。
        *   改造 `MediaSyncService` (门面) 和 `PeriodicSyncAdapter` (适配器)，使其依赖通用的 `IsolateJobManager` 来提交作业。
*   **成果**: 彻底将 Isolate 的管理能力从具体业务中剥离，形成了一个**可复用的、平台级的“计算服务”**。未来任何需要长时间运行的复杂任务，都可以轻松地通过实现 `IsolateTaskHandler` 接口来利用这个服务，而无需关心 Isolate 的底层细节。

### 第二部分：重构后的模块架构说明

欢迎来到 `background_jobs` 模块！这是我们应用中所有后台任务的“指挥中心”。本说明将帮助您快速理解其设计理念、结构和工作流程。

#### 核心设计理念

1.  **关注点分离 (Separation of Concerns)**: 模块严格区分“通用能力”和“具体实现”。
    *   `core/` 目录是我们的**引擎室**，提供稳定、可复用的后台任务运行框架和 Isolate 计算服务。
    *   `impl/` 目录是我们的**业务车间**，每一个子目录都代表一个独立的后台业务功能（如媒体同步）。

2.  **Isolate 即服务 (Isolate as a Service)**: 我们视后台 Isolate 为一个共享的、强大的计算资源。任何需要避免阻塞主线程的复杂、耗时任务（如文件处理、大量数据计算），都应该被封装成一个“作业 (Job)”并提交给这个服务，而不是自己去创建一个 Isolate。

3.  **命令与事件驱动**: 各层之间的交互是松耦合的。上层（如 Service）不直接调用下层（如 Orchestrator）的方法，而是通过 `IsolateJobManager` 发送一个**命令式**的 `IsolateJob`，然后通过监听返回的**事件式**的 `IsolateJobResult` 或 `SyncProgressUpdate` 来获取结果和进度。

#### 模块结构概览

```shell
lib/features/background_jobs
├── core/                  # 引擎室：提供通用框架
│   ├── contracts/         # - 定义了通用接口 (BackgroundTask, IsolateTaskHandler)
│   ├── isolate/           # - 提供了通用的 Isolate 管理服务
│   └── task_dispatcher.dart # - Workmanager 的唯一入口点，负责分发简单后台任务
│
└── impl/                  # 业务车间：存放具体实现
    └── media_sync/        # [示例] 媒体同步业务
        ├── background/    # - 适配器：将本业务连接到外部框架 (如 Workmanager)
        ├── domain/        # - 核心领域：包含所有纯粹的业务逻辑
        ├── models/        # - 数据模型：定义本业务中使用的数据结构
        └── service/       # - 门面：为应用的其它部分 (如UI) 提供统一、简洁的接口
```

#### 工作流程详解 (以媒体同步为例)

##### 场景A: 用户在UI上点击“立即同步”

1.  **UI 层**: 调用 `MediaSyncService.triggerFullSync()`。
2.  **Service (门面)**: `MediaSyncService` 接收到请求，它并不知道如何执行同步，它的唯一职责是调用 `IsolateJobManager.submitJob('mediaSync', payload: 'triggerFullSync')`，将一个“媒体同步”作业提交给通用 Isolate 服务。
3.  **Isolate Manager (核心)**: `IsolateJobManager` 将这个作业打包成 `IsolateJob` 对象，通过 `SendPort` 发送给正在运行的 `GenericIsolate`。
4.  **Generic Isolate (核心)**: Isolate 的入口点 `genericIsolateEntrypoint` 收到作业后，根据作业名 `'mediaSync'` 在其内部的处理器注册表中查找到 `MediaSyncIsolateHandler`。
5.  **Isolate Handler (业务入口)**: `MediaSyncIsolateHandler` 的 `handle` 方法被调用。它解析 `payload` ('triggerFullSync')，并调用 `MediaSyncOrchestrator.handleCommand()`。
6.  **Domain (业务核心)**: `MediaSyncOrchestrator` 开始执行真正的业务流程——调用 `LocalMediaSynchronizer` 对账，然后调用 `AssetChangeExecutor` 将变更应用到数据库。在关键步骤，它会通过 `SendPort` 发送 `SyncProgressUpdate` 消息（如 `SyncStatus.syncingLocal`）回到主 Isolate。
7.  **状态返回与UI更新**: `MediaSyncService` 一直在监听 `IsolateJobManager.jobResultStream`。当它监听到 `SyncProgressUpdate` 类型的消息时，就将其推送到自己的 `syncStateStream` 中，UI 层监听到状态变化后即可刷新界面（例如显示“正在同步本地文件…”）。

##### 场景B: Workmanager 触发的周期性后台同步

1.  **Workmanager**: 在预定时间唤醒 App，并执行 `callbackDispatcher`。
2.  **Task Dispatcher (核心)**: `callbackDispatcher` 查找到 `PeriodicSyncAdapter` 并执行其 `execute` 方法。
3.  **Adapter (适配器)**: `PeriodicSyncAdapter` 的职责与 `MediaSyncService` 类似，它同样调用 `IsolateJobManager.submitJob()` 来提交一个同步作业。
4.  **后续流程**: **接下来的步骤 3 到 6 与场景 A 完全相同**，这完美地体现了核心业务逻辑的复用。
5.  **任务结束**: `PeriodicSyncAdapter` 会监听 `jobResultStream`，直到收到 `SyncStatus.idle` 或 `SyncStatus.error` 的 `SyncProgressUpdate` 消息，然后向 `Workmanager` 返回 `true` (成功) 或 `false` (失败)，完成本次后台任务。

#### 如何添加一个新的后台任务？

##### 方案1：简单的后台任务 (无需 Isolate)

如果你的任务很简单（比如一次网络请求或清理缓存），不涉及大量计算或I/O：

1.  在 `impl/` 下创建一个新业务目录，例如 `data_cleanup`。
2.  在 `data_cleanup/` 下创建一个 `CleanupTask` 类，并实现 `BackgroundTask` 接口。
3.  在 `core/task_dispatcher.dart` 的 `taskHandlers` 映射表中注册你的新任务。
4.  使用 `Workmanager` 调度这个新任务即可。

##### 方案2：复杂的后台任务 (需要 Isolate)

如果你的任务很复杂（如视频转码、图片压缩）：

1.  在 `impl/` 下创建一个新业务目录，例如 `video_processing`。
2.  在 `video_processing/` 内部，参考 `media_sync` 的结构，设计你的 `Orchestrator` (核心流程) 和 `Executor` (具体执行)。
3.  创建一个 `VideoProcessingIsolateHandler` 类，实现 `IsolateTaskHandler` 接口。它的 `handle` 方法将是你的业务在 Isolate 中的入口，负责调用你的 `Orchestrator`。
4.  在 `core/isolate/generic_isolate.dart` 的 `handlers` 映射表中，注册你的 `VideoProcessingIsolateHandler`。
5.  创建一个 `VideoProcessingService` (如果需要从UI触发) 或 `VideoProcessingAdapter` (如果需要从 Workmanager 触发)，让它们通过 `IsolateJobManager` 来提交你的新作业。

遵循以上模式，您可以轻松、规范地为应用添加任意复杂的后台功能，同时保持整体架构的清晰和健壮。
