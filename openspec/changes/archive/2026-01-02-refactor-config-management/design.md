# Design: 配置管理架构重构

## Context

PrismBox 移动端应用当前存在配置管理混乱的问题。配置分散在多个位置，类型边界不清，硬编码值遍布代码库，缺乏统一的管理和访问机制。这影响了代码的可维护性和可扩展性。

## Goals / Non-Goals

### Goals
- 建立清晰的三层配置架构（编译时、运行时系统、用户设置）
- 提供统一的配置访问接口
- 提取并集中管理所有硬编码配置值
- 消除配置冲突，确保单一配置源
- 提供类型安全的配置访问
- 支持配置验证和文档化

### Non-Goals
- 不改变用户设置的存储机制（继续使用 StoreService）
- 不引入外部配置管理框架
- 不实现配置动态更新（当前为静态配置，但预留扩展接口）
- 不实现配置版本管理
- 不实现配置导入/导出功能
- 不改变编译时配置的编译特性

## Decisions

### Decision 1: 三层配置架构

**选择**：建立编译时配置、运行时系统配置、用户设置三层架构

**理由**：
- 清晰区分不同生命周期的配置
- 编译时配置：应用构建时确定，修改需重新编译
- 运行时系统配置：应用级常量，通常不暴露给用户
- 用户设置：用户可配置，持久化存储

**替代方案**：
- 单一配置层：无法区分配置的生命周期和来源
- 两层层：无法清晰区分系统配置和用户设置

### Decision 2: 配置注册表模式

**选择**：创建 `ConfigRegistry` 作为统一访问入口

**理由**：
- 提供单一访问点，便于查找和管理
- 支持配置的集中初始化和验证
- 预留扩展接口，便于未来实现配置动态更新（当前不实现，但接口设计支持）

**扩展性设计**：
- `ConfigRegistry` 接口设计支持未来添加配置监听和更新机制
- 配置类使用常量值，但可通过接口抽象支持动态值（未来扩展）
- 当前实现为静态配置，不增加运行时开销

**替代方案**：
- 分散访问：难以管理和查找
- 依赖注入：过度设计，不符合项目简单性原则

### Decision 3: 配置类组织方式

**选择**：按功能域组织配置类（`NetworkConfig`、`TaskConfig`、`CacheConfig` 等）

**理由**：
- 符合单一职责原则
- 便于查找和维护
- 支持按需加载和初始化

**替代方案**：
- 单一配置类：文件过大，难以维护
- 按层级组织：不符合功能域划分

### Decision 4: 配置访问模式

**选择**：
- 系统配置：`ConfigRegistry.network.connectTimeout`
- 用户设置：`AppSetting.get(Setting.themeColor)`
- 编译时配置：`AppConfig.api.serverBaseUrl`

**理由**：
- 清晰区分不同配置类型
- 类型安全，编译期检查
- 符合现有代码风格

### Decision 5: 渐进式迁移策略

**选择**：保持向后兼容，逐步迁移

**理由**：
- 降低重构风险
- 允许分阶段验证
- 不破坏现有功能

**实施方式**：
- 保留现有 API，标记为 `@Deprecated`
- 提供迁移指南
- 分模块逐步迁移

## Risks / Trade-offs

### Risks
1. **迁移风险**：大量代码需要更新配置访问方式
   - **缓解**：渐进式迁移，保持向后兼容
2. **性能影响**：配置访问可能增加开销
   - **缓解**：系统配置使用常量，编译时优化
3. **配置遗漏**：可能遗漏某些硬编码配置值
   - **缓解**：代码审查和测试覆盖

### Trade-offs
- **简单性 vs 灵活性**：选择简单直接的实现，避免过度设计
- **类型安全 vs 动态性**：优先类型安全，牺牲部分动态性
- **集中管理 vs 分散访问**：选择集中管理，提高可维护性

## Migration Plan

### Phase 1: 建立新架构（不破坏现有功能）
1. 创建 `ConfigRegistry` 和配置类结构
2. 提取硬编码配置值到配置类
3. 保持现有代码继续工作

### Phase 2: 清理配置冲突
1. 统一 SSL 配置来源
2. 移除废弃的配置项
3. 更新相关代码

### Phase 3: 迁移现有代码
1. 逐个模块迁移配置访问方式
2. 验证功能正常
3. 移除废弃的 API

### Phase 4: 完善和优化
1. 添加配置验证
2. 完善文档
3. 性能优化

## Design Decisions

### 配置动态更新
**决策**：当前不实现配置动态更新，但预留扩展空间

**理由**：
- 当前需求为静态配置，动态更新会增加复杂度和运行时开销
- 系统配置作为应用级常量，通常不需要运行时修改
- 用户设置已通过 `AppSetting` 支持动态更新

**扩展性预留**：
- `ConfigRegistry` 接口设计支持未来添加配置监听机制
- 配置类可扩展为支持动态值（通过接口抽象）
- 当前实现保持简单，使用常量值

### 配置版本管理
**决策**：不需要配置版本管理

**理由**：
- 配置变更通过代码版本控制（Git）管理
- 配置结构变更通过代码重构和迁移处理
- 不需要独立的配置版本系统

### 配置导入/导出
**决策**：不需要配置导入/导出功能

**理由**：
- 用户设置已通过 `StoreService` 持久化存储
- 系统配置作为代码的一部分，通过版本控制管理
- 不需要额外的导入/导出机制
