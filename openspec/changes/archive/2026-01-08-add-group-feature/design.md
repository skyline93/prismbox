# Design: 圈子功能架构设计

## Context

后端已经实现了圈子相关的 API（创建圈子、获取列表、成员管理等），但移动端缺少对应的 UI。需要实现完整的移动端圈子功能，包括：

- 创建和管理圈子
- 查看圈子列表和详情
- 成员管理
- 完全在线访问（直接调用 API，不存储到本地数据库）

## Goals / Non-Goals

### Goals
- 实现圈子创建、列表、详情页面
- 实现成员管理功能
- 完全在线访问（直接调用后端 API）
- UI 风格与 Threads 类似，简洁现代
- 预留缓存优化接口（后续可添加内存缓存或本地数据库存储）

### Non-Goals
- 帖子功能（在单独的提案中实现）
- 评论功能（在帖子提案中实现）
- 点赞功能（在帖子提案中实现）
- 通知功能（后续实现）

## Decisions

### Decision 1: 数据存储策略

**选择**：完全在线访问，不存储到本地数据库（前期实现）

**理由**：
- 圈子功能完全是在线功能，不需要离线访问
- 简化架构，减少复杂度
- 数据始终是最新的（直接从服务器获取）
- 减少存储占用

**后续优化预留**：
- 可以在 `GroupService` 中添加缓存层（内存缓存或本地数据库）
- 缓存策略：最近访问的圈子、最近 N 条帖子等
- 缓存失效：基于时间或手动刷新

### Decision 2: 数据获取策略

**选择**：直接调用后端 API，使用 Riverpod Provider 管理状态

**理由**：
- 简单直接，减少架构复杂度
- 数据始终是最新的
- Provider 自动管理状态生命周期
- 支持错误处理和重试

**获取时机**：
- 进入圈子列表页面时
- 进入圈子详情页面时
- 用户下拉刷新时

### Decision 3: UI 风格参考 Threads

**选择**：参考 Threads 的简洁现代风格

**理由**：
- 用户熟悉 Threads 的交互方式
- 简洁的卡片式设计
- 清晰的视觉层次

**设计要点**：
- 卡片式布局
- 圆形头像
- 清晰的间距
- 统一的圆角和阴影

### Decision 4: 页面级状态管理

**选择**：使用 Riverpod Provider 管理页面状态

**理由**：
- 项目已使用 Riverpod
- 支持自动清理（AutoDispose）
- 便于测试和维护

**Provider 结构**：
- `groupListProvider` - 圈子列表状态
- `groupDetailProvider` - 圈子详情状态（使用 family 参数）
- `groupMembersProvider` - 成员列表状态（使用 family 参数）

### Decision 5: 组件拆分策略

**选择**：将 UI 拆分为独立的小组件

**理由**：
- 符合项目 UI 重构规范
- 提高可复用性
- 便于测试和维护

**组件结构**：
- `GroupCard` - 圈子卡片（用于列表）
- `GroupInfoCard` - 圈子信息卡片（用于详情页）
- `MemberListItem` - 成员列表项

## Risks / Trade-offs

### Risk 1: 网络依赖

**风险**：完全依赖网络，离线时无法使用

**缓解措施**：
- 圈子功能设计为在线功能，离线时显示网络错误提示
- 后续可以添加缓存优化（内存缓存或本地数据库）

### Risk 2: 性能问题

**风险**：每次都需要网络请求，可能影响响应速度

**缓解措施**：
- 使用加载状态指示器
- 优化 API 响应时间（后端已优化）
- 后续可以添加缓存层（预留接口）
- 使用虚拟滚动（ListView.builder）
- 图片懒加载

### Risk 3: 网络错误处理

**风险**：网络错误时用户体验差

**缓解措施**：
- 显示友好的错误提示
- 提供重试机制
- 显示网络状态指示

## Migration Plan

### Phase 1: 数据层
1. 创建数据模型（仅用于 API 响应解析）
2. 实现网络层 API 客户端

### Phase 2: 服务层
1. 实现服务层业务逻辑
2. 实现错误处理和重试机制

### Phase 3: UI 层
1. 创建 UI 组件
2. 创建页面
3. 配置路由
4. 实现 Provider 状态管理

### Phase 4: 集成和测试
1. 集成所有组件
2. 测试完整流程
3. 性能优化

### Phase 5: 后续优化（预留）
1. 添加内存缓存层
2. 或添加本地数据库存储
3. 实现缓存策略和失效机制

## Open Questions

  - **决定**：当前不实现，后续可以添加
