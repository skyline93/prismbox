# 设计文档：修复增量同步中收藏状态变化检测

## Context

当前增量同步逻辑在 `_incrementalSync` 方法中：

1. 只处理 `modifiedDateTime.isAfter(lastSyncTime)` 的资产
2. 只处理新资产（`!existingIds.contains(asset.id)`）

但是，收藏状态变化不会改变 `modifiedDateTime`，所以即使收藏状态改变了，资产也不会被包含在 `assetsToProcess` 中，导致收藏状态不会更新。

### Immich 的实现参考

根据 Immich 移动端的架构设计（参考 `docs/immich参考/架构详解/mobile-sync-download-module.md`）：

1. **增量同步优先**：通过 Native API 获取增量变更（新增、删除），无变更时直接跳过
2. **快速路径优化**：仅新增场景只处理新增资源，跳过完整对比
3. **全量对比兜底**：检测到删除或修改时，采用完整差异对比算法

对于收藏状态同步，Immich 在备份模块中会同步收藏状态（参考 `mobile-backup-module.md`：直接构建 `MultipartRequest`，写入收藏状态等字段）。但在增量同步中，Immich 同样面临收藏状态变化不会改变 `modifiedDateTime` 的问题。

**我们的方案与 Immich 保持一致**：
- 使用批量 API 获取收藏状态（与 Immich 的批量操作理念一致）
- 在增量同步中检查所有已存在资产的收藏状态（确保准确性）
- 使用批量处理优化性能（与 Immich 的批量操作策略一致）

## Goals / Non-Goals

**Goals**：
- 在增量同步中检测收藏状态变化
- 即使 `modifiedDateTime` 没有变化，如果收藏状态变化了，也要更新数据库
- 保持性能优化（使用批量 API）

**Non-Goals**：
- 不实现实时监听收藏状态变化（需要系统级监听，成本高）
- 不实现定期全量检查（性能开销大）
- 不实现收藏状态变化的推送通知（超出本次范围）

## Decisions

### 1. 在增量同步中检查所有已存在资产的收藏状态

**决策**：在增量同步中，除了检查 `modifiedDateTime`，还要检查所有已存在资产的收藏状态是否变化。

**理由**：
- **准确性**：确保收藏状态变化能被及时检测到
- **用户体验**：用户期望收藏状态变化能及时反映在 PrismBox 中
- **性能可接受**：使用批量 API，每批 100 个资产只需 1 次原生调用
- **与 Immich 一致**：Immich 在备份时同步收藏状态，我们在增量同步中也应该同步收藏状态，确保数据一致性

**实现策略**：
1. 在增量同步中，收集所有已存在资产的 ID
2. 批量获取这些资产的收藏状态（使用 `getAssetMetadata` 批量 API）
3. 比较数据库中的 `isFavorite` 和系统相册中的 `isFavorite`
4. 如果不同，即使 `modifiedDateTime` 没有变化，也添加到更新列表

**与 Immich 的一致性**：
- **批量操作**：与 Immich 的批量操作策略一致（参考 `mobile-asset-module.md`：提供批量操作 `updateFavorite` 等）
- **增量同步优先**：与 Immich 的增量同步优先理念一致（参考 `mobile-sync-download-module.md`）
- **性能优化**：使用批量 API，每批 100 个资产只需 1 次原生调用，与 Immich 的批量处理优化一致

**替代方案**：
- **定期全量检查**：性能开销大，不推荐（与 Immich 的增量优先策略不一致）
- **实时监听**：需要系统级监听，实现复杂，超出范围（Immich 也未实现）
- **仅检查最近修改的资产**：可能遗漏收藏状态变化，不推荐（准确性不足）

### 2. 优化：只检查可能变化的资产

**决策**：为了性能优化，可以只检查最近一段时间内可能变化的资产，而不是所有资产。

**理由**：
- **性能优化**：减少不必要的原生 API 调用
- **实用性强**：用户通常在最近一段时间内改变收藏状态

**实现策略**：
- 检查最近 N 天内的资产（例如 7 天）
- 或者检查所有资产，但使用批量 API 优化性能

**权衡**：
- 如果只检查最近 N 天的资产，可能会遗漏更早的收藏状态变化
- 但考虑到用户通常只关心最近的资产，这个权衡是可接受的

**最终决策**：先实现检查所有已存在资产的方案，如果性能有问题，再优化为只检查最近 N 天的资产。

## Risks / Trade-offs

### 风险 1：性能影响

**风险**：为所有已存在资产检查收藏状态可能增加增量同步时间。

**缓解措施**：
- 使用批量 API（`getAssetMetadata`），每批 100 个资产只需 1 次原生调用
- 如果性能有问题，可以优化为只检查最近 N 天的资产
- 添加性能监控，量化影响

### 风险 2：边界情况

**风险**：如果资产数量很大（例如 10000+），批量检查可能仍然耗时。

**缓解措施**：
- 增量同步是后台任务，不会阻塞 UI
- 可以分批处理，每批之间添加短暂延迟
- 如果性能问题严重，可以考虑只检查最近修改的资产

### Trade-off：准确性 vs 性能

**Trade-off**：检查所有资产可以确保准确性，但可能影响性能。

**理由**：
- **准确性优先**：收藏状态是用户主动设置的重要属性，应该及时同步
- **性能可接受**：使用批量 API，性能影响可控
- **可优化**：如果性能有问题，可以后续优化为只检查最近 N 天的资产

## Implementation Plan

### 阶段 1：修改增量同步逻辑（1 天）

1. 在 `_incrementalSync` 方法中，收集所有已存在资产的 ID
2. 批量获取这些资产的收藏状态
3. 比较数据库中的 `isFavorite` 和系统相册中的 `isFavorite`
4. 如果不同，添加到更新列表（即使 `modifiedDateTime` 没有变化）

### 阶段 2：测试和优化（0.5 天）

1. 测试增量同步是否能正确检测收藏状态变化
2. 性能测试，确保批量 API 调用不会显著影响同步时间
3. 如果性能有问题，优化为只检查最近 N 天的资产

### 回滚计划

如果遇到严重问题：
1. 回滚增量同步逻辑修改
2. 保留批量 API 调用代码（不影响其他功能）
3. 用户可以通过全量同步来更新收藏状态
