# Design: 帖子功能架构设计（含后台处理和媒体上传）

## Context

后端已经实现了帖子相关的 API（创建帖子、获取 Feed、评论等），但移动端缺少对应的 UI。需要实现完整的移动端帖子功能，包括：

- 创建和发布帖子（后台处理）
- 媒体上传和处理
- 查看 Feed 流
- 查看帖子详情
- 评论和回复
- 完全在线访问（直接调用 API，不存储到本地数据库）

**关键约束**：
- 媒体处理的任务需要先实现添加帖子的功能
- 添加帖子需要能在后台处理
- 用户点击发布后，帖子应该在后台处理发布
- 发布帖子的页面需要参考 Threads 的发布 UI

## Goals / Non-Goals

### Goals
- 实现帖子创建、Feed 流、详情页面
- 实现评论功能
- 实现后台发布功能（媒体上传 + 创建帖子）
- 实现媒体上传功能（复用现有上传服务）
- 完全在线访问（直接调用后端 API）
- UI 风格与 Threads 类似，简洁现代
- 预留缓存优化接口（后续可添加内存缓存或本地数据库存储）

### Non-Goals
- 点赞功能（后续实现）
- 转发功能（后续实现）
- 帖子编辑功能（后续实现）
- 通知功能（后续实现）

## Decisions

### Decision 1: 后台发布流程

**选择**：用户点击发布后，创建后台任务，分阶段处理：
1. **媒体上传阶段**：将选中的媒体文件上传到服务器（使用现有上传服务）
2. **创建帖子阶段**：所有媒体上传完成后，调用创建帖子 API

**理由**：
- 后端创建帖子 API 需要 media_uuids，媒体必须先上传
- 多图上传可能耗时较长，不应阻塞 UI
- 用户可以在后台继续使用应用
- 使用现有上传服务，复用已有优化（断点续传、重试等）

**任务状态流转**：
- `pending` → `uploading_media` → `media_uploaded` → `creating_post` → `completed`
- 任何阶段失败 → `failed`

**任务管理**：
- 使用类似备份上传任务的管理机制
- 创建 `PostTask` 实体存储任务状态
- 使用 `background_downloader` 执行媒体上传
- 任务完成后调用创建帖子 API

### Decision 2: 媒体上传策略

**选择**：复用现有上传服务（UploadService）

**理由**：
- 已有完善的上传服务，支持断点续传、重试、进度跟踪
- 避免重复实现
- 统一的上传体验

**上传流程**：
1. 用户选择媒体后，立即开始上传（可选：也可以等用户点击发布后再上传）
2. 显示上传进度
3. 上传完成后，保存 media_uuid
4. 所有媒体上传完成后，创建帖子任务进入"创建帖子"阶段

**媒体选择**：
- 使用时间线组件在上滑抽屉中显示媒体选择界面
- 复用 `LocalAssetEntity`，与照片页面上传时保持一致
- 使用 `SelectableTimelineSliverListBuilder` 构建可选择的媒体网格
- 支持多选（图片和视频）
- 显示选中媒体的预览
- 允许删除已选中的媒体
- 使用 `DraggableScrollableSheet` 实现上滑抽屉

### Decision 3: Threads UI 风格设计

**选择**：参考 Threads 的发布页面 UI

**设计要点**：
- **顶部导航栏**：
  - 左侧：取消按钮（文字"取消"）
  - 中间：标题"新建串文"
  - 右侧：列表图标、更多选项（三个点）
- **用户信息区域**：
  - 圆形头像
  - 用户名
  - "> 添加话题"入口
- **文字输入区域**：
  - 多行文本输入框
  - 占位符："有什么新鲜事吗?"
  - 支持换行
- **媒体选择工具栏**（底部，键盘上方）：
  - 图片图标
  - GIF 图标
  - 列表图标
  - 引用图标
  - 更多选项（三个点）
- **底部操作栏**（键盘上方）：
  - 左侧：回复选项（文字 + 图标）
  - 右侧：表情开关（开关按钮）、发布按钮（禁用状态直到有内容）
- **媒体预览区域**：
  - 显示选中媒体的缩略图网格
  - 支持删除单个媒体
  - 支持重新排序（可选）

### Decision 4: Feed 流分页策略

**选择**：使用分页加载，每页 20 条

**理由**：
- 减少初始加载时间
- 降低内存占用
- 后端 API 已支持分页

**加载策略**：
- 首次加载：直接调用 API 获取第一页数据
- 下拉刷新：从服务器获取最新数据（重置分页）
- 上拉加载：加载下一页数据（调用 API）

### Decision 5: 媒体显示策略

**选择**：根据媒体数量使用不同布局

**理由**：
- 单图：大图显示
- 2-4 图：2x2 网格
- 5-9 图：3x3 网格
- 更多：显示前 9 张，点击查看全部

**性能优化**：
- 使用缩略图
- 懒加载
- 图片缓存

### Decision 6: 评论显示策略

**选择**：平铺显示，支持回复嵌套

**理由**：
- 简化 UI 复杂度
- 便于阅读
- 后端支持嵌套回复

**显示方式**：
- 主评论：完整显示
- 回复：缩进显示，标注"回复 @用户名"

### Decision 7: 数据获取策略

**选择**：直接调用后端 API，使用 Riverpod Provider 管理状态

**理由**：
- 简单直接，减少架构复杂度
- 数据始终是最新的
- Provider 自动管理状态生命周期
- 支持错误处理和重试

**获取时机**：
- 进入 Feed 流时
- 下拉刷新时
- 上拉加载更多时
- 创建新帖子后（刷新列表）
- 添加新评论后（刷新评论列表）

**后续优化预留**：
- 可以在 `PostService` 中添加缓存层（内存缓存或本地数据库）
- 缓存策略：最近访问的帖子、最近 N 条评论等
- 缓存失效：基于时间或手动刷新

### Decision 8: 媒体选择界面设计

**选择**：使用时间线组件在上滑抽屉中显示媒体选择界面

**理由**：
- **复用 LocalAssetEntity**：选择的媒体来自 `LocalAssetEntity` 表，与照片页面上传时保持一致
- **解决上传问题**：避免了之前"Local asset not found"的错误，因为资产已经在 `LocalAssetEntity` 中
- **用户体验一致**：与照片页面的时间线视图体验一致，用户熟悉
- **准确选择**：时间线视图让用户能够准确知道要上传哪些照片

**实现方案**：
- 点击媒体选择按钮时，显示上滑抽屉（`DraggableScrollableSheet`）
- 在抽屉中使用 `SelectableTimelineSliverListBuilder` 显示时间线视图
- 使用 `timelineSectionsProvider` 获取时间线数据
- 使用 `assetSelectionProvider` 管理选择状态
- 支持多选，最多 9 张
- 选择完成后，关闭抽屉并更新预览区域

**UI 设计**：
- 抽屉初始高度：屏幕的 30%
- 抽屉最大高度：屏幕的 90%
- 抽屉最小高度：屏幕的 12%（显示拖拽手柄）
- 顶部显示拖拽手柄和"选择图片"标题
- 底部显示已选择数量和"确定"按钮

### Decision 9: 任务类型扩展

**选择**：创建独立的 `PostTask` 实体和任务管理系统

**理由**：
- 帖子发布任务与备份上传任务有相似性（都需要上传媒体）
- 但业务逻辑不同（帖子需要创建帖子记录）
- 可以复用任务管理的基础设施
- 保持职责清晰，帖子任务独立管理

**实现方案**：
- 创建独立的 `PostTask` 实体和数据库表
- 创建 `PostTaskManager` 管理帖子发布任务
- 复用 `background_downloader` 执行媒体上传
- 任务完成后调用创建帖子 API

## Risks / Trade-offs

### Risk 1: 媒体选择与 LocalAssetEntity 的依赖

**风险**：如果用户选择的媒体不在 `LocalAssetEntity` 中（例如新拍摄的照片还未扫描），可能无法选择

**缓解措施**：
- 确保照片页面已经扫描了所有媒体到 `LocalAssetEntity`
- 如果媒体不存在，可以提示用户先同步照片
- 或者在选择时自动创建 `LocalAssetEntity` 记录（如果可能）

### Risk 2: 媒体上传性能

**风险**：多图上传可能耗时较长

**缓解措施**：
- 显示上传进度
- 支持后台上传
- 使用现有上传服务（已优化）
- 允许用户关闭页面，任务在后台继续

### Risk 3: 任务状态同步

**风险**：后台任务状态可能与 UI 显示不一致

**缓解措施**：
- 使用 Riverpod Provider 监听任务状态变化
- 任务状态变化时自动更新 UI
- 应用启动时检查未完成的任务

### Risk 4: Feed 流性能

**风险**：帖子数量多时可能影响滚动性能

**缓解措施**：
- 使用虚拟滚动（ListView.builder）
- 图片懒加载
- 分页加载

### Risk 5: 评论嵌套深度

**风险**：深层嵌套可能导致 UI 混乱

**缓解措施**：
- 限制显示深度（最多 3 层）
- 使用缩进清晰显示层级
- 点击展开更多回复

## Migration Plan

### Phase 1: 数据层和任务管理
1. 创建数据模型（仅用于 API 响应解析）
2. 创建帖子任务模型和数据库表
3. 实现网络层 API 客户端
4. 实现帖子任务管理器（类似上传任务管理器）

### Phase 2: 服务层
1. 实现服务层业务逻辑
2. 实现媒体上传集成（复用现有上传服务）
3. 实现后台发布流程
4. 实现错误处理和重试机制

### Phase 3: UI 层
1. 实现 Threads 风格的创建帖子页面
2. 创建 UI 组件
3. 创建 Feed 流和详情页面
4. 集成到圈子主页
5. 实现 Provider 状态管理

### Phase 4: 集成和测试
1. 集成所有组件
2. 测试完整流程（媒体选择 → 上传 → 发布）
3. 测试后台任务处理
4. 性能优化

### Phase 5: 后续优化（预留）
1. 添加内存缓存层
2. 或添加本地数据库存储
3. 实现缓存策略和失效机制

## Open Questions

- 是否需要支持帖子编辑功能？
  - **决定**：当前不实现，后续可以添加
- 是否需要支持帖子删除确认？
  - **决定**：需要，显示确认对话框
- 是否需要支持评论编辑和删除？
  - **决定**：当前支持删除（作者和管理员），编辑功能后续添加
- 媒体选择后是否立即开始上传，还是等用户点击发布？
  - **决定**：等用户点击发布后再开始上传（避免浪费资源）
- 任务失败后是否支持重试？
  - **决定**：支持，提供重试按钮
