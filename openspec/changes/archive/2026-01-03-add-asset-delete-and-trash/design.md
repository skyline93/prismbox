# Design: 媒体资源删除和回收站功能

## Context

PrismBox 需要支持媒体资源的删除和回收站功能。系统当前架构中：
- 本地资产和远程资产完全解耦，独立管理
- 远程资产表已有 `deletedAt` 字段支持软删除
- 后端已实现远程资源的删除、恢复和永久删除 API
- 照片页面支持过滤模式（全部/已备份/未备份/仅云端）

## Goals / Non-Goals

### Goals
- 支持本地资源和远程资源的删除功能
- 实现软删除机制，支持误删恢复
- 本地资源删除时，将文件移动到应用私有回收站空间
- 远程资源删除通过调用后端 API 实现
- 提供统一的回收站管理界面
- 回收站支持过滤（全部/仅本地/仅远程）
- 回收站支持恢复和永久删除操作

### Non-Goals
- 自动清理过期回收站文件（未来可扩展）
- 批量操作的性能优化（未来可扩展）

## Decisions

### Decision 1: 本地资源删除策略

**决策**：本地资源删除时，将文件从系统相册复制到应用私有回收站空间，然后删除系统相册中的原文件。

**理由**：
- 系统相册文件删除后无法恢复（iOS/Android 系统限制）
- 应用私有空间可以永久保存文件，不受系统清理影响
- 保存原始路径信息，便于恢复时还原到系统相册

**替代方案考虑**：
- 仅软删除标记，不移动文件：无法保证文件不会被系统清理
- 移动到系统回收站：iOS/Android 没有统一的系统回收站机制

### Decision 2: 数据库字段设计

**决策**：在 `LocalAssetEntity` 表中添加三个字段：
- `deletedAt` (DateTime, Nullable)：删除时间，用于软删除标记
- `originalPath` (Text, Nullable)：原始路径（删除前在系统相册的路径）
- `trashPath` (Text, Nullable)：回收站路径（在应用私有回收站空间的路径）

**理由**：
- `deletedAt` 用于查询和过滤软删除的记录
- `originalPath` 保存原始路径，恢复时使用
- `trashPath` 保存回收站路径，永久删除时使用

**替代方案考虑**：
- 使用单一 `path` 字段：无法区分原始路径和回收站路径，恢复逻辑复杂
- 使用单独的回收站表：增加查询复杂度，不符合现有架构

### Decision 3: 回收站目录结构

**决策**：使用按日期分组的目录结构：
```
应用私有目录/trash/{YYYY-MM-DD}/{assetId}.{ext}
```

**理由**：
- 按日期分组便于管理 and 未来可能的自动清理
- 使用 assetId 作为文件名，避免文件名冲突
- 简单清晰，易于实现

**替代方案考虑**：
- 单层目录：文件过多时性能下降
- 按用户分组：移动端单用户，无需分组

### Decision 4: 删除行为根据过滤模式决定

**决策**：在照片页面，根据当前过滤模式决定删除行为：
- "全部"、"已备份"、"未备份"：仅支持删除本地资源
- "仅云端"：仅支持删除远程资源

**理由**：
- 符合用户预期：当前过滤模式决定了用户关注的范围
- 避免混淆：不会在不同过滤模式下误删资源
- 简化 UI：选择模式下只显示对应的删除按钮

**替代方案考虑**：
- 始终支持删除所有资源：不符合过滤模式的语义，容易造成用户困惑

### Decision 5: 回收站页面复用照片页面组件

**决策**：回收站页面复用照片页面的展示组件（`SelectableTimelineSliverList`, `TimelineNormalAppBar`, `TimelineSelectionAppBar` 等）。

**理由**：
- 减少代码重复
- 保持一致的 UI/UX
- 降低维护成本

**替代方案考虑**：
- 创建独立的回收站组件：增加代码量，维护成本高

### Decision 6: 后端 API 使用现有接口

**决策**：远程资源删除使用后端已有的 API：
- `DELETE /api/v1/media/:uuid` - 软删除
- `POST /api/v1/media/:uuid/restore` - 恢复
- `DELETE /api/v1/media/:uuid/purge` - 永久删除

**理由**：
- 后端已实现完整的删除、恢复和永久删除功能
- 无需修改后端代码
- 减少开发工作量

## Risks / Trade-offs

### Risk 1: 应用私有空间容量限制
**风险**：回收站文件占用应用私有空间，可能导致存储空间不足。
**缓解**：
- 未来可添加自动清理机制（如30天自动删除）
- 用户可手动永久删除不需要的资源

### Risk 2: 文件复制操作耗时
**风险**：大文件复制到回收站可能耗时较长。
**缓解**：
- 使用异步操作，不阻塞 UI
- 显示进度提示
- 小文件操作快速完成

### Risk 3: 恢复操作可能失败
**风险**：恢复文件时，如果原始路径已被其他文件占用，恢复可能失败。
**缓解**：
- 系统相册通常不会自动重用已删除文件的路径
- 如果恢复失败，提供错误提示
- 可以考虑在应用私有空间保留备份，恢复失败时提示用户

### Risk 4: 远程资源删除需要网络
**风险**：远程资源删除需要调用后端 API，网络异常时可能失败。
**缓解**：
- 显示错误提示，允许重试
- 未来可添加离线队列机制

## Migration Plan

### 数据库迁移
1. 在 `local_asset_entity` 表中添加三个新字段：
   - `deletedAt` (DateTime, Nullable, 默认 NULL)
   - `originalPath` (Text, Nullable, 默认 NULL)
   - `trashPath` (Text, Nullable, 默认 NULL)
2. 所有现有记录的字段值初始化为 NULL（表示未删除）

### 代码迁移
1. 更新 `LocalAssetEntity` 表定义
2. 运行数据库迁移
3. 更新相关 DAO 方法
4. 实现删除和回收站功能
5. 添加回收站页面和路由

### 向后兼容
- 现有代码不依赖新字段，添加字段不影响现有功能
- 软删除查询需要显式过滤 `deletedAt IS NULL`，确保现有查询不受影响

## Open Questions

- 回收站自动清理机制的设计（时间阈值等）
- 批量操作的性能优化策略
