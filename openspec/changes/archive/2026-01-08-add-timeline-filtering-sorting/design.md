# Design: 时间线过滤与排序功能架构设计

## Context

当前时间线系统支持按上传状态过滤（全部/已备份/未备份/仅云端），通过 `PhotoFilterModeEnum` 和 `PhotoFilterModeProvider` 管理。系统需要扩展支持：

- **内容过滤**：收藏、视频等（与上传状态过滤独立）
- **灵活排序**：按创建时间或更新时间排序（当前固定按 `createdAt` 降序）
- **多级过滤**：本地/远程隔离 + 内容过滤的组合

合集页面需要：
- 收藏页面：仅显示收藏资产，支持本地/远程切换
- 视频页面：仅显示视频资产，支持本地/远程切换
- 最近添加页面：按更新时间降序排序，支持本地/远程切换

## Goals / Non-Goals

### Goals
- 支持收藏过滤和视频过滤
- 支持按更新时间排序（用于"最近添加"）
- 所有时间线页面支持本地/远程隔离（复用现有机制）
- 过滤和排序配置独立管理，便于扩展
- 保持照片页面默认行为不变（向后兼容）

### Non-Goals
- **组合过滤暂不实现**：收藏+视频的组合过滤暂不实现，但数据结构预留扩展接口
- 不改变现有的本地/远程隔离机制（复用 `PhotoFilterModeEnum`）
- 不优化数据库查询（当前在内存中过滤，后续可优化）

## Decisions

### Decision 1: 分层过滤设计

**选择**：使用两层过滤机制
1. **第一层**：本地/远程隔离（复用 `PhotoFilterModeEnum`，全局共享）
2. **第二层**：内容过滤（`TimelineContentFilterConfig`，页面级）

**理由**：
- 本地/远程隔离是基础过滤，所有页面都需要
- 内容过滤是页面特定的，每个页面独立配置
- 分层设计清晰，便于理解和维护
- 过滤顺序：先本地/远程隔离，再内容过滤（减少数据量）

**替代方案**：统一过滤配置
- 缺点：配置复杂，难以区分全局和页面级配置
- 缺点：不利于扩展

### Decision 2: 内容过滤使用页面级 Provider

**选择**：使用 `AutoDisposeProvider` 或 `family` 参数实现页面级配置

**理由**：
- 每个页面（收藏、视频、最近添加）需要独立的过滤配置
- 页面切换时自动清理，避免状态污染
- 使用 `family` 参数可以区分不同页面（如 `favoriteTimeline`, `videoTimeline`）

**替代方案**：全局共享配置
- 缺点：页面切换时状态会保留，导致混乱
- 缺点：不同页面无法独立配置

### Decision 3: 排序配置独立于过滤配置

**选择**：排序配置（`TimelineSortConfig`）与过滤配置独立管理

**理由**：
- 排序和过滤是正交的关注点
- 排序可以独立于过滤使用（如"最近添加"只需要排序，不需要过滤）
- 便于扩展（未来可以支持更多排序字段）

**替代方案**：合并到过滤配置
- 缺点：配置复杂，职责不清
- 缺点：不利于扩展

### Decision 4: 本地/远程隔离复用现有机制

**选择**：复用 `PhotoFilterModeEnum` 和 `PhotoFilterModeProvider`，全局共享

**理由**：
- 避免重复实现
- 保持一致性（所有页面使用相同的切换按钮）
- 用户在任何页面切换后，其他页面也同步（符合用户预期）

**替代方案**：为每个页面创建独立的本地/远程隔离配置
- 缺点：状态不同步，用户体验差
- 缺点：代码重复

### Decision 5: 过滤顺序

**选择**：先应用本地/远程隔离，再应用内容过滤

**理由**：
- 本地/远程隔离是基础过滤，数据量较大
- 先过滤可以减少后续处理的数据量
- 逻辑清晰：先确定数据源，再过滤内容

**替代方案**：先内容过滤，再本地/远程隔离
- 缺点：如果内容过滤数据量小，可能效率略低（但差异不大）

### Decision 6: 数据结构预留扩展接口

**选择**：`TimelineContentFilterConfig` 使用可选参数，预留扩展接口

**理由**：
- 当前只实现收藏和视频过滤
- 未来可能需要更多过滤条件（如地点、标签、日期范围等）
- 使用可选参数便于扩展，不需要修改现有代码

**示例**：
```dart
class TimelineContentFilterConfig {
  final bool? favoriteOnly;
  final bool? videoOnly;
  // 预留扩展接口
  // final String? location;
  // final List<String>? tags;
  // final DateTimeRange? dateRange;
}
```

### Decision 7: 组合过滤暂不实现但预留接口

**选择**：当前不实现组合过滤（如收藏+视频），但数据结构支持

**理由**：
- 当前需求不明确，先实现基础功能
- 数据结构已经支持（可以同时设置 `favoriteOnly: true` 和 `videoOnly: true`）
- 过滤逻辑已经支持（会同时应用两个过滤条件）
- 如果未来需要，只需要在 UI 层添加组合选项即可

## Risks / Trade-offs

### Risk 1: 性能问题（内存过滤）

**风险**：当前在内存中过滤，如果数据量很大，可能影响性能

**缓解措施**：
- 先应用本地/远程隔离（减少数据量）
- 如果性能成为问题，后续可以在数据库层过滤
- 当前数据量预计不会太大（单用户设备上的媒体数量有限）

### Risk 2: 状态管理复杂化

**风险**：多个 Provider（本地/远程隔离、内容过滤、排序）可能导致状态管理复杂

**缓解措施**：
- 使用清晰的命名和文档
- 本地/远程隔离全局共享，内容过滤和排序页面级
- 在 `timelineSectionsProvider` 中统一读取所有配置

### Risk 3: 扩展性不足

**风险**：未来可能需要更多过滤条件，当前设计可能不够灵活

**缓解措施**：
- 使用可选参数，便于扩展
- 过滤逻辑使用策略模式，便于添加新过滤条件
- 预留扩展接口（在代码注释中说明）

## Migration Plan

### Phase 1: 创建数据结构和 Provider
1. 创建 `TimelineContentFilterConfig` 类
2. 创建 `TimelineSortConfig` 类
3. 创建 `TimelineContentFilterConfigProvider`
4. 创建 `TimelineSortConfigProvider`

### Phase 2: 扩展 Service 层
1. 修改 `TimelineProviderService.getTimelineAssets()` 支持过滤和排序参数
2. 实现内容过滤逻辑
3. 实现排序逻辑

### Phase 3: 扩展 Provider 层
1. 修改 `timelineSectionsProvider` 读取内容过滤和排序配置
2. 按顺序应用过滤和排序

### Phase 4: UI 层改造
1. 创建收藏、视频、最近添加时间线页面
2. 合集页面绑定过滤/排序配置
3. 确保所有页面显示本地/远程切换按钮

### Phase 5: 测试和验证
1. 测试各种过滤组合
2. 测试排序功能
3. 验证向后兼容性

## Open Questions

- 是否需要为内容过滤添加"反过滤"选项（如"仅非收藏"）？
  - **决定**：当前不需要，如果未来需要，可以通过 `favoriteOnly: false` 实现
- 排序是否需要支持更多字段（如按名称、按大小）？
  - **决定**：当前只支持时间字段，未来可以扩展
- 是否需要支持自定义排序（用户自定义规则）？
  - **决定**：当前不需要，未来可以考虑
