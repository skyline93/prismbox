# 媒体资源优化中期方案文档（基于现有存储系统）

## 1. 方案概述

### 1.1 目标
- 支持动态尺寸缩略图（`?size=200x200`）
- 实现 ThumbHash 占位符优化
- 提升首次加载体验
- 利用现有存储系统，不引入额外中间件

### 1.2 核心策略
采用“预生成 + 按需扩展 + ThumbHash 占位”的混合策略：
- 预生成常用尺寸（thumbnail、preview），存储在现有存储系统
- 按需生成特殊尺寸，通过扩展 Variant 机制存储
- 使用 ThumbHash 提供即时占位符

### 1.3 存储架构
- 主存储：利用现有 `PrimaryStorage`（LocalStorage）
- 缓存：利用现有 `CacheManager`（内存+磁盘）
- 不引入：Redis 等额外中间件

## 2. 架构设计

### 2.1 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    前端请求层                            │
│  GET /api/v1/assets/{uuid}/thumbnail?size=200x200       │
└─────────────────────────────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────┐
│                    API Handler 层                        │
│  1. 解析 size 参数                                       │
│  2. 构建存储 key（基于 hash + variant）                   │
│  3. 检查存储系统（PrimaryStorage）                       │
└─────────────────────────────────────────────────────────┘
                        │
        ┌───────────────┴───────────────┐
        │                               │
        ▼                               ▼
┌───────────────┐            ┌──────────────────┐
│  存储中存在    │            │  需要生成         │
│  直接返回      │            │  检查生成队列     │
│  <10ms        │            └──────────────────┘
└───────────────┘                      │
                        ┌─────────────┴─────────────┐
                        │                           │
                        ▼                           ▼
              ┌─────────────────┐      ┌──────────────────┐
              │  预生成尺寸      │      │  按需生成         │
              │  variant固定     │      │  动态variant      │
              │  thumbnail/preview│      │  thumbnail_200x200│
              └─────────────────┘      └──────────────────┘
                        │                           │
                        └───────────┬───────────────┘
                                    ▼
                        ┌───────────────────────┐
                        │   存储到PrimaryStorage│
                        │   (LocalStorage)      │
                        └───────────────────────┘
```

### 2.2 存储 Key 设计

#### 2.2.1 现有存储 Key 格式
```
{hash[0:2]}/{hash[2:4]}/{hash}[_variant].{ext}
```

示例：
- 原图：`ab/cd/abcdef123456.jpg`
- 预生成缩略图：`ab/cd/abcdef123456_thumbnail.jpg`
- 预生成预览图：`ab/cd/abcdef123456_preview.jpg`

#### 2.2.2 扩展动态尺寸 Variant
```
{hash[0:2]}/{hash[2:4]}/{hash}_thumbnail_{width}x{height}.jpg
```

示例：
- `ab/cd/abcdef123456_thumbnail_200x200.jpg`
- `ab/cd/abcdef123456_thumbnail_400x300.jpg`
- `ab/cd/abcdef123456_thumbnail_1280x0.jpg`（preview，高度为0表示保持比例）

#### 2.2.3 Variant 命名规范
- 预生成：`thumbnail`、`preview`（固定）
- 动态生成：`thumbnail_{width}x{height}`（包含尺寸信息）
- 特殊值：
  - `preview` = `thumbnail_1280x0`（高度0表示保持比例）
  - `thumbnail` = `thumbnail_400x400`（默认缩略图）

### 2.3 数据流设计

#### 上传流程
```
1. 用户上传图片
   ↓
2. 保存原图到存储（PrimaryStorage）
   ↓
3. 后台 Worker 处理
   ├─ 生成 ThumbHash（50-200ms）→ 保存到数据库
   ├─ 预生成 thumbnail (400x400) → 存储 key: {hash}_thumbnail.jpg
   ├─ 预生成 preview (1280px) → 存储 key: {hash}_preview.jpg
   └─ 所有文件通过 PrimaryStorage 存储
```

#### 请求流程
```
1. 前端请求缩略图
   GET /api/v1/assets/{uuid}/thumbnail?size=200x200
   ↓
2. 从 Media 获取 hash
   ↓
3. 构建存储 key
   - size=200x200 → {hash}_thumbnail_200x200.jpg
   - size=thumbnail → {hash}_thumbnail.jpg
   - size=preview → {hash}_preview.jpg
   ↓
4. 检查 PrimaryStorage.Exists()
   ├─ 存在 → 直接返回 (<10ms)
   └─ 不存在 → 按需生成
   ↓
5. 按需生成流程
   ├─ 检查生成队列（防止重复）
   ├─ 异步生成缩略图
   ├─ 存储到 PrimaryStorage（使用动态 variant）
   └─ 返回降级方案（ThumbHash 或预生成缩略图）
```

## 3. 核心功能设计

### 3.1 动态缩略图生成

#### 3.1.1 尺寸参数解析
支持格式：
- 具体尺寸：`200x200`、`400x300`
- 预设值：`thumbnail`（400x400）、`preview`（1280px）
- 单边限制：`200`（宽度 200px，高度按比例）

解析规则：
- 优先匹配预设值（`thumbnail`、`preview`）
- 解析 `WxH` 格式
- 无效时降级到默认 `thumbnail`

#### 3.1.2 存储 Key 构建
利用现有 `StorageAdapter` 扩展：

```go
// 扩展 StorageAdapter 支持动态尺寸
func (a *StorageAdapter) BuildDynamicThumbnailKey(
    hash string, 
    itemType string, 
    width, height int,
) (string, error) {
    // 构建 variant: thumbnail_200x200
    variant := fmt.Sprintf("thumbnail_%dx%d", width, height)
    
    // 使用现有 BuildStorageKey 逻辑
    // 但传入动态 variant
    return a.buildKeyWithVariant(hash, itemType, variant, "jpg")
}
```

#### 3.1.3 存储策略
- 预生成尺寸：存储在固定 variant（`thumbnail`、`preview`）
- 动态尺寸：存储在动态 variant（`thumbnail_{width}x{height}`）
- 统一存储：都通过 `PrimaryStorage` 存储，使用相同的存储池管理

#### 3.1.4 缓存策略（可选）
利用现有 `CacheManager`：
- 内存缓存：热点缩略图（快速访问）
- 磁盘缓存：按需生成的缩略图（临时缓存）
- 主存储：持久化存储（所有缩略图）

缓存层次：
```
L1: 内存缓存（CacheManager.memoryCache）
    └─ 热点缩略图，快速访问
    
L2: 磁盘缓存（CacheManager.diskCachePath）
    └─ 按需生成的缩略图临时缓存
    └─ 可配置 TTL 和大小限制
    
L3: 主存储（PrimaryStorage）
    └─ 所有缩略图持久化存储
    └─ 通过存储 key 访问
```

### 3.2 ThumbHash 占位符

#### 3.2.1 生成时机
- 上传时在后台 Worker 中生成
- 仅图片类型生成
- 生成失败不阻塞主流程

#### 3.2.2 存储设计
- 数据库字段：`medias.thumb_hash`（varchar(200)）
- 编码格式：base64
- 数据量：~100 字节/图片
- 不存储在文件系统（仅数据库）

#### 3.2.3 使用场景
- 远程资源首次加载
- 缩略图生成中时
- 网络较慢时

## 4. 存储系统扩展

### 4.1 StorageAdapter 扩展

#### 4.1.1 新增方法
```go
// 支持动态尺寸的缩略图 key 构建
func (a *StorageAdapter) BuildDynamicThumbnailKey(
    hash string,
    itemType string,
    width, height int,
) (string, error)

// 解析动态 variant（从 key 中提取尺寸）
func (a *StorageAdapter) ParseDynamicVariant(variant string) (width, height int, err error)
```

#### 4.1.2 兼容性
- 保持现有 `BuildThumbnailKey` 方法（预生成尺寸）
- 新增方法专门处理动态尺寸
- 统一使用相同的存储系统

### 4.2 存储访问优化

#### 4.2.1 访问路径
```
1. 检查 PrimaryStorage.Exists(key)
   ↓
2. 存在 → PrimaryStorage.Get(key) 直接返回
   ↓
3. 不存在 → 生成 → PrimaryStorage.Put(key, data) 存储
```

#### 4.2.2 缓存集成（可选）
如果启用 `CacheManager`：
```
1. 检查 CacheManager.Get(cacheKey)
   ├─ 命中 → 直接返回
   └─ 未命中 → 继续
   ↓
2. 检查 PrimaryStorage.Exists(storageKey)
   ├─ 存在 → 读取并写入缓存 → 返回
   └─ 不存在 → 生成 → 存储 → 缓存 → 返回
```

### 4.3 存储空间管理

#### 4.3.1 存储池管理
- 利用现有存储池机制
- 动态生成的缩略图使用相同的存储池
- 通过 `SelectPool()` 自动选择合适池

#### 4.3.2 清理策略
- 预生成缩略图：随原图删除而删除
- 动态生成缩略图：可选定期清理（LRU）
- 清理时机：后台任务定期扫描

## 5. 数据库设计

### 5.1 字段扩展

#### Media 表新增字段
```sql
ALTER TABLE medias ADD COLUMN thumb_hash VARCHAR(200) NULL;
```

字段说明：
- 类型：`VARCHAR(200)`（base64 编码后约 100-150 字符）
- 可空：允许生成失败的情况
- 索引：不需要（查询频率低）

### 5.2 数据迁移
- 新数据：上传时自动生成
- 历史数据：可选批量迁移脚本
- 迁移策略：后台任务，不影响正常服务

## 6. API 设计

### 6.1 接口规范

#### 缩略图接口
```
GET /api/v1/assets/{uuid}/thumbnail?size={size}

参数：
- uuid: 媒体 UUID（路径参数）
- size: 尺寸参数（查询参数，可选）
  - 格式：200x200、preview、thumbnail
  - 默认：thumbnail

响应：
- 200: 返回图片二进制流
- 404: 媒体不存在或权限不足
- 503: 缩略图生成中（可选）
```

#### 响应头
```
Content-Type: image/jpeg
Cache-Control: public, max-age=2592000  # 30天
ETag: "{hash}"  # 可选，用于缓存验证
```

### 6.2 数据返回

#### MediaResponse 扩展
```json
{
  "uuid": "...",
  "thumb_hash": "base64编码的ThumbHash",
  "thumbnail_url": "/api/v1/assets/{uuid}/thumbnail",
  ...
}
```

#### 同步接口扩展
在 `StreamSyncAssets` 返回的资产数据中包含 `thumb_hash` 字段。

## 7. 实施计划

### 7.1 阶段划分

#### 阶段 1：基础功能（2-3 周）
- 数据库模型扩展（添加 `thumb_hash` 字段）
- 实现 ThumbHash 生成功能
- 集成到媒体处理流程
- API 返回 ThumbHash

#### 阶段 2：动态缩略图（2-3 周）
- 扩展 `StorageAdapter` 支持动态 variant
- 实现 `size` 参数解析
- 实现按需生成逻辑
- 利用 PrimaryStorage 存储动态缩略图

#### 阶段 3：性能优化（1-2 周）
- 实现异步生成机制
- 添加生成队列管理
- 集成 CacheManager（可选）
- 实现降级方案（ThumbHash 占位）
- 性能测试与调优

### 7.2 技术选型

#### ThumbHash 生成库
- 推荐：`github.com/evanw/thumbhash/go`（官方 Go 实现）
- 备选：自实现（基于 ImageMagick）

#### 存储方案
- 主存储：现有 `PrimaryStorage`（LocalStorage）
- 缓存：现有 `CacheManager`（可选，内存+磁盘）
- 不引入：Redis 等额外中间件

#### 队列方案
- 内置 channel：轻量级，适合中小规模
- 任务队列（如 gq）：高并发场景可选

## 8. 性能指标

### 8.1 目标指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 预生成尺寸响应时间 | <10ms | 从 PrimaryStorage 直接读取 |
| 按需生成首次响应 | <100ms | 返回降级方案 |
| 按需生成完成时间 | 200-500ms | 实际生成时间 |
| 缓存命中率（如启用） | >80% | 常用尺寸 |
| ThumbHash 生成时间 | 50-200ms | 取决于图片大小 |
| ThumbHash 解码时间 | <5ms | 前端解码 |

### 8.2 存储成本

| 项目 | 单张图片 | 10万张 | 100万张 |
|------|---------|--------|---------|
| ThumbHash（数据库） | ~100 字节 | ~10MB | ~100MB |
| 预生成缩略图（存储） | ~20KB | ~2GB | ~20GB |
| 动态缓存（估算） | ~15KB | ~1.5GB | ~15GB |
| 总计（估算） | ~35KB | ~3.5GB | ~35GB |

### 8.3 存储系统负载

| 操作 | 频率 | 影响 |
|------|------|------|
| 预生成缩略图读取 | 高频 | 低（直接文件读取） |
| 动态缩略图生成 | 中频 | 中（需要处理） |
| 动态缩略图读取 | 中频 | 低（缓存后快速） |
| 存储空间增长 | 持续 | 可控（LRU 清理） |

## 9. 风险与应对

### 9.1 技术风险

#### 风险 1：按需生成导致请求延迟
- 应对：异步生成 + 降级方案（ThumbHash）
- 监控：记录生成时间，优化慢请求

#### 风险 2：存储空间增长
- 应对：LRU 淘汰、定期清理、限制动态缓存数量
- 监控：监控存储池使用率

#### 风险 3：并发生成压力
- 应对：限制并发数、使用队列、资源池管理
- 监控：监控生成队列长度

#### 风险 4：存储系统性能
- 应对：利用 CacheManager 减少存储访问
- 监控：监控存储 I/O 性能

### 9.2 兼容性风险

#### 向后兼容
- API 参数可选，默认行为不变
- ThumbHash 字段可选（`omitempty`）
- 前端处理 `thumbHash` 为 `null` 的情况
- 现有预生成缩略图继续工作

#### 数据迁移
- 新数据自动生成
- 历史数据可选批量迁移
- 迁移不影响正常服务

## 10. 监控与运维

### 10.1 关键指标监控

- 缩略图请求量（按尺寸分类）
- 存储命中率（PrimaryStorage.Exists）
- 按需生成耗时
- 生成队列长度
- ThumbHash 生成成功率
- 存储空间使用率（存储池）
- 缓存命中率（如启用 CacheManager）

### 10.2 告警策略

- 生成队列积压超过阈值
- 存储命中率低于阈值
- 生成失败率超过阈值
- 存储空间使用率超过阈值（存储池）
- 存储 I/O 性能下降

### 10.3 运维操作

- 清理过期动态缩略图（LRU）
- 批量生成历史数据 ThumbHash
- 调整缓存策略参数（如启用）
- 扩容存储池空间
- 监控存储系统性能

## 11. 总结

### 11.1 方案优势
- 性能：预生成常用尺寸快速响应，按需生成满足灵活性
- 体验：ThumbHash 提供即时占位符
- 成本：存储成本可控，利用现有存储系统
- 扩展：支持未来更多尺寸需求
- 架构：不引入额外中间件，利用现有存储系统

### 11.2 实施建议
- 优先实现 ThumbHash（前端已就绪，收益明显）
- 分阶段实施动态缩略图（先基础，再优化）
- 持续监控和优化（根据实际使用调整策略）
- 充分利用现有存储系统（PrimaryStorage + CacheManager）

### 11.3 预期效果
- 首次加载感知速度提升 50-70%
- 常用尺寸响应时间 <10ms
- 支持任意尺寸需求
- 存储成本可控（<100MB/10万张图片 ThumbHash，缩略图通过现有存储管理）
- 不增加系统复杂度（利用现有存储架构）

该方案在性能、体验和成本之间取得平衡，充分利用现有存储系统，避免引入额外中间件，为后续扩展奠定基础。
